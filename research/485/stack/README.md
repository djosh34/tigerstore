# #485: retained-stack native floors

Only GitHub Actions results count. Workflow `exp485-stack` runs arm64 and amd64
on independent GitHub-hosted runners, with native and purego back-to-back on the
same runner. Each Go benchmark has 5 one-second repetitions (medians, ns/op,
B/op, allocs/op). Raw results and hardware are uploaded. Commands are in `run.sh`.
No production source files are edited; `overlay.py` creates an explicit Go overlay
under the ignored `generated/` directory.

## What each measurement means

* `BenchmarkClient` native / purego: **real** `clientv3`, real tigerstore HTTP/2
gRPC implementation (not grpc-go server), TLS, a real single-member `node.Node`
using ordinary file I/O on `/dev/shm` tmpfs. Syncs are enabled. Segment size 1 MiB,
checkpoint threshold 1 GiB; no simulated delay/faults/checkers, no 3-node quorum.
Default core otherwise, tick 10 ms, no process-memory-pressure intervention.
Put and successful compare/version>0-then-put contain 1 KiB values; Range returns
one preloaded key with its 1 KiB value. Serial calls, a warmed persistent
connection, no application deadline allocation per operation.
* `*-stub`: the **same production server**, with `node.SubmitBatch` replaced by
an immediate-answer backend using a Go overlay. Server admission, decoding,
completion queues, flow control, accounting, protobuf reply encoders and metrics
remain real. Fixtures match the response shape (Range uses compact MVCC KVs;
Put uses wire-form reply; Txn has a successful Put result). Node setup/election
still occurs outside timing. This is an artificial backend, not a valid store.
The stub includes fixture construction/allocation in each operation.
* `BenchmarkWatchEvent1KiB` (stub overlay only): inject one 1 KiB PUT event into
the node's outbound WatchStream queue, then wait for clientv3 to deliver it on
a persistent watcher. Includes queueing, real tigerstore watch encoding, HTTP/2,
TLS, grpc-go/clientv3 decode and client channel delivery; excludes Raft and Put.
The stream and watch have been created before timing. Event fixture is reused.
`PutAndWatch1KiB` (real node) is the **composite** Put plus its corresponding
watch event received, not an isolated one-way event; do not add it to Put.
* `BenchmarkPeer/{64,1024,16384}`: actual `peer.Start` transports, TLS 1.3 mutual
certificate verification and tigerstore framing/raftpb, warmed connection,
Send to Deliver. Size is **entry data bytes**, not total serialized frame size.
One outstanding message; includes queues, marshaling, framing, TLS, receiving,
unmarshaling and callback-to-caller handoff. No Raft node work. Shutdown and
handshake are excluded. Payload supplied as a reusable raftpb message.
* Handshake: simulator's P-256 ECDSA certificate, generated by `testcert`, CA
verification and the real config shapes: peer mutual TLS 1.3 with ALPN
`tigerstore-peer/2`; client server-auth TLS with h2 ALPN. Default Go key exchange
is **not forced to X25519**: Go may negotiate its hybrid ML-KEM default. Includes
new TLS objects and buffered stream allocation (2x16 KiB). No session resumption;
excludes tigerstore's peer preface and client HTTP/2 setup. Transport benchmarks
above exercise the actual protocol setup outside their timers.
* Certificates: exactly `network.init`'s NewCA + IssueFor, once per scenario:
P-256 CA key/self-signed cert + P-256 leaf key/cert, SANs node1/node2/node3/member/
updated-member, PEM and TLS parse. Both signing and serialization included.
* Connections use grpc's **bufconn**, 256 KiB each direction (16 KiB for the
handshake test), not TCP. This is explicitly a baseline for production TLS/gRPC,
not simulator scheduler or networking-copy overhead. All operation benchmarks
use GOMAXPROCS=2 on both runners. Memory uses GOMAXPROCS=4 and 1/2/4 independent
workers, each copying 64 MiB source to 64 MiB destination (up to 512 MiB total
working set); includes round barriers. Reported MB/s counts useful bytes copied,
not read+write memory-bus traffic. SHA256/AES-128-GCM use one worker/core and 1 MiB
messages. AES encrypts only; TLS record throughput is not equal to this number.

## Limitations

`purego` removes the architecture-specific crypto/CRC code selected by that tag;
it does **not** emulate gosim: runtime memmove, scheduler, GC and any assembly
not guarded by purego remain native. Therefore its speedup is a measured Go-tag
contrast, not an exact prediction for #464. These measurements are floors of
retained serial components on these runners, not a theorem that all costs add:
peer replication overlaps, and TLS records, HTTP/2 and node submissions batch
under concurrent load. Disk fio is independent from the stack's tmpfs storage;
barriers are enabled explicitly and mount state recorded. Fio sequential tests
are direct 1 MiB, QD1; fsync is buffered 4 KiB write + fsync every write, QD1;
random direct 4 KiB reads use libaio QD32. Five repetitions of 5 s each, after a
1 s ramp; the entire 1 GiB file is prewritten before any test. These are runner
virtual-disk observations, not physical storage specifications.
