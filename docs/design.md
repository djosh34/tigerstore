# tigerstore design

tigerstore is a drop-in etcd replacement for Kubernetes. It serves the etcd v3 API that kube-apiserver uses, reaches consensus with go.etcd.io/raft, and stores data in its own storage engine, designed from what one CPU core can do.

This file is the current design. It starts from the merged starting design ([#32](https://github.com/djosh34/tigerstore/issues/32)), the merged starting test design ([#33](https://github.com/djosh34/tigerstore/issues/33)) and the owner design directions ([#53](https://github.com/djosh34/tigerstore/issues/53)). The architect changes it with evidence ([#37](https://github.com/djosh34/tigerstore/issues/37)), through a pull request, and records each large change in a "Design change" comment on the outcome issue. All numbers are hypotheses until measured.

## Status

Built so far: the Go module, CI with lint, build and test, and the storage pieces of one node: the MVCC index (`internal/mvcc`), the Raft log, checkpoints and their roots on disk (`internal/wal`), the real disk adapter (`internal/osfs`), the simulated disk (`internal/simfs`), the committer (`internal/core`), the deterministic simulator (`internal/sim`), the determinism lint (`internal/lint`), and the real node: its driver (`internal/node`), the peer transport (`internal/peer`), the etcd gRPC server on its own HTTP/2 code (`internal/server`) and the `tigerstore` command. The section "What is built" describes them. Everything else is the design that the next pull requests build.

## Fixed by the owner

These never change:

- The etcd v3 API as kube-apiserver uses it, with client TLS and client certificates.
- Consensus with go.etcd.io/raft.
- Go, one executable per node, 3 nodes in one region.
- Encrypted node-to-node traffic.
- Linearizable reads and writes.
- An acked write and its value bytes survive the loss of one node.
- Tests and benchmarks run on free GitHub runners. The red team does chaos only, no security work.

Goals, in order: the most objects, the highest write throughput, then latency equal to or lower than etcd.

## Core

- One committer goroutine per node owns all state: the Raft `RawNode`, revisions, the index, leases and watch matching. Nothing else touches that state, so the core takes no locks.
- Helper goroutines do the work around it: client TLS, HTTP/2 framing, protobuf decode and encode, peer encryption and framing, and disk I/O. They hand the committer prepared batches. The committer only batches, applies and releases, and never blocks on I/O.
- Raft is go.etcd.io/raft v3.7.0 `RawNode` with `AsyncStorageWrites`, `CheckQuorum`, `PreVote` and `ReadOnlySafe`. With async storage the leader still cannot apply and ack through a stall of its own disk, because `RawNode` does not apply entries that are not stable locally. With async storage, Raft also sends a candidate's vote requests before its own new term and vote are durable. The candidate can then win on the other two votes, lose its term in a failed write, restart in the old term and win the same term again with a different log; the simulator found two different entries at one index this way. So the core holds every message to a peer while an append that changes the term or the vote is on its way to disk (`TestVoteRequestsWaitForTheTerm`). Entries still go out before the leader's own copy is durable, as the Raft thesis (10.2.1) allows.
- Many RPCs are packed into one Raft entry. Each RPC keeps its own revision.
- Every node terminates client TLS and gRPC. The etcd client balances round robin, and kube-apiserver opens one client per resource, so two thirds of requests land on followers. Followers forward packed proposals to the leader and serve reads with one batched ReadIndex per core turn.
- Lease expiry is a replicated mutation.

### Responses prepared before commit

While a batch is being replicated and synced, its responses and watch events are prepared. The committer fixes the results and revisions, and helper goroutines encode the bytes. When the batch commits, the committer releases them at once. Nothing is released before commit. If the entries are lost in a leader change, the prepared bytes are dropped. Replicas only report the log index they have durably accepted, as Raft followers already do.

### Batching

Batching is self-clocked: the committer proposes whatever arrived while the previous local append was in flight, capped by bytes, with no timer. The core does this itself: once the leader proposes a batch, new writes wait until the local append that carries that batch is durable, and the next `Process` then sends all of them as one entry. Appends of proposals that followers forwarded, and appends with only a hard state, such as a moved commit index, hold nothing, so forwarded traffic cannot starve local writes and a single client never waits for an extra fsync. Every write counts its size plus its framing in the entry toward the byte cap (`MaxBatchBytes`, 4 MiB), which sends a full entry early, so even empty requests cannot pile up without limit. A write that timed out while it waited is dropped, not proposed later. Followers forward at once. Heartbeats, votes, ReadIndex, replies and watch events never wait. On the disk side, the driver writes every queued append job with one write and one fsync, so the byte cap bounds one entry, not one disk group. The `tigerstore` process runs with at least two Go processors, even when pinned to one CPU or started with `GOMAXPROCS=1`: an fsync blocks in a system call that can keep its processor until the runtime takes it back, which is not reliably fast, and with only one, the goroutines that take in requests, send to peers and release replies all wait for the disk. The [batch256 pre-work](https://github.com/djosh34/tigerstore/issues/47#issuecomment-6137116710) measured 1.2 writes per leader fsync at 256 clients with one processor, and 53 with two on the same CPU (29,657 Put/s against 5,297). The committer is still one goroutine. The analysis below is the starting point. The benchmarks in outcome 4 replace its symbols with measured values.

Symbols:

- `λ` is the arrival rate of writes at the leader, in operations per second.
- `t_a` is the time for one local append, including the fsync.
- `RTT` is the round trip between nodes. Single region means 1 to 10 ms ([#29](https://github.com/djosh34/tigerstore/issues/29)).
- `c_b` is the fixed core time per batch (Raft bookkeeping, syscalls, one fsync submission). `c_op` is the core time per operation.

How batch size follows load:

- One batch holds what arrived during the previous append, so the batch size is about `λ · t_a`.
- At low load this is one operation. No operation waits for a timer, so one client sees no added latency.
- As load rises, batches grow. The fixed cost per batch is shared, so the core time per operation falls to `c_op + c_b / (λ · t_a)`.
- When the core saturates, queues grow, batches grow, and the per-operation cost falls further. The system settles near `1 / c_op` operations per second instead of collapsing.
- The byte cap bounds the size of one entry. Several entries can share one fsync, because the driver writes every queued append at once.

How batch size follows node-to-node latency:

- The leader does not wait for a batch to commit before it proposes the next one. Replication is pipelined, so `RTT` does not change the batch size.
- `RTT` sets how many batches are in flight: about `RTT / t_a`. The bytes in flight are `λ · RTT · value size`. At 50k writes/s, 10 ms and 10 KiB that is about 5 MB per follower.
- The peer window is bounded by bytes (16 MiB or more), not by entry count, so 10 ms between nodes does not throttle throughput.
- Followers forward what arrived in one core turn and do not wait for the previous forward to be acked.

Write latency for one client is the client round trip, plus at most one batch of queueing, plus the commit path:

- A request that lands on the leader commits after about `max(t_a, RTT + t_a on a follower)`, so about `RTT + t_a`.
- A request that lands on a follower is forwarded to the leader, replicated, and the follower learns the commit afterwards. That is about `2 · RTT + t_a`. Two thirds of requests take this path.

At 1 to 10 ms between nodes, one-client write latency is therefore about 2.3 to 20 ms, dominated by `RTT`.

The batch byte cap and the peer window size are open for measurement.

## Node-to-node transport

Decided in the [design change on #47](https://github.com/djosh34/tigerstore/issues/47): node-to-node traffic is framed TLS 1.3 over TCP. There is one connection per directed peer pair. Length-prefixed frames carry packed Raft messages, with no gRPC or protobuf framing between nodes. The transport sits behind a small interface, so the tournament in #50 and #52 can try others.

Evidence: a loopback experiment where TLS won every batched case and raw AES-GCM over UDP led only at 1 KiB with batch 1, by 8%, within noise; an Astra second opinion agreed. Both measured loopback with one outstanding batch. They pick a default, not batch sizes or in-flight windows.

Rules that come with it:

- Per peer, frame bytes and queued bytes are capped. Control messages (heartbeats, votes, ReadIndex) go between data frames. The peer writers are not the committer.
- A stalled connection hits a write deadline, is dropped and is reported to Raft as unreachable. It never blocks the committer.
- Snapshots stream in bounded chunks to temporary storage and install only when complete and validated, through the durable install path. A separate snapshot connection is allowed if control traffic still starves.
- The codec keeps every Raft field, including the ReadIndex context and snapshot membership. A socket write is never a durable acknowledgement.

## Storage and recovery

- The Raft log is the value store. The full command and value go in the log, written once per node. There is no bbolt and no second copy.
- Values are stored in wire format, so reads and watch events are a short header encode plus a memcpy from the log.
- Truncation of a replaced Raft suffix is persisted before any later ack. The index never points at replaced bytes.
- Recovery starts from consistent checkpoints plus ordered replay of the log. Fuzzy checkpoints are not proven correct for CAS replay and stay an experiment.
- Segment cleaning runs only below the compaction revision. It copies live data, syncs it, installs and syncs a new recovery root, and only then deletes the old segment. It keeps everything that outstanding roots, replay and readers need.
- The index is one arena B+tree with live subtree counts. A key-to-slot hash next to it is an experiment, judged by total bytes per key and core time.
- Compression is an experiment, judged by the ratio on a real Kubernetes dump, the CPU cost and the read latency.

### What is built

**MVCC index.** `internal/mvcc` is the key index of one node. A Google B-tree maps each key to all its versions, oldest first. A version holds the mod revision (main and sub), create revision, version, lease and the position of its value. A tombstone is a version with version 0. Range, Put, DeleteRange and Txn follow etcd v3.7.2 rule by rule, including the quirks: a request that changes nothing keeps the revision, Count ignores the revision filters, the limit goes into the scan only with the default order, compares and checks read the state before the transaction, reads inside a transaction see its earlier writes, and nested transaction responses carry an empty header. The validation that etcd does before a request enters the log (empty key, sort options, too many operations, duplicate keys across nested transactions) is `mvcc.Check*`, and errors are etcd's own `rpctypes` values. After each write, `Store.Changes` lists the changed keys, and `Change.Event` builds the watch event with or without the previous value. `Store.Hash` hashes the whole state so that the simulator can compare replicas.

`Store.Compact(C)` follows etcd: a revision at or below the last compaction is `ErrCompacted`, one above the current revision is `ErrFutureRev`, and the revision does not change. Per key it keeps the newest version at or below C and everything after; a tombstone from before C goes, with the key if nothing is left, and a tombstone at C stays so that a watch from C still gets that delete. Reads below C then fail with `ErrCompacted`, reads at C work. Compact walks every key on the committer: 30 ms at 1M keys with two versions each, so about 0.3 s at 10M keys, once per Kubernetes compaction (every 5 minutes by default). Compact goes through Raft as its own entry kind; physical compaction is the same, since it happens at once.

The index holds no values. Each version names its value by its Raft position (`mvcc.Ref`): the index of the entry that wrote it, the offset and length in the entry's data, and a CRC-32C of the bytes. The position is the same on every node, so `Store.Hash` covers it and replicas still compare. The apply step reads a put in place (`core.ParsePut`, protowire, no `proto.Unmarshal`) and notes where its value starts in the entry. Every other write (transactions, deletes, compactions and lease writes) is decoded with `core.DecodeAlias`, which follows `proto.Unmarshal` rule by rule but makes bytes fields slices of the input instead of copies; the decoder of a transaction notes where the value of each of its puts starts. Transactions and deletes have decoders written out per message; the rest go through protoreflect (`core.UnmarshalAlias`). A key is copied once, when the key is created, so the index keeps no entry alive.

Every value read goes through `mvcc.Values` and checks the length and the checksum: a range, a previous value of a put or delete, a compare on the value, a watch event. Bytes that do not match, such as damaged ones or ones read from the wrong place, are `mvcc.ErrBadValue`; the node stops instead of answering with them. The core's `Values` reads the value from its entry in Raft's in-memory log. A watch event copies its values, since a watcher can hold it for long; a response holds a slice of the entry until it is sent.

The B-tree stands in for the arena B+tree with live subtree counts. Count walks every key in the range, which took 61 ms at 1M keys in the [10M-key experiment](https://github.com/djosh34/tigerstore/issues/47); the B+tree with subtree counts replaces it.

**Raft log on disk.** `internal/wal` is the only durable copy of the data. The log is a sequence of segment files of 64 MiB. Each segment starts with a header of a magic string, the format version (1), its sequence number and the crc that its first record chains from. A record is `u32 length | u32 crc | u8 type | payload`, with four types: an entry (term, index, entry type, data), a hard state (term, vote, commit), a root (the index and term of a checkpoint, and whether a snapshot reset the log there, keeping the entries up to a given index) and a value (the value of an entry this node does not hold, by entry index and offset, which a snapshot brought). The crc is CRC-32C over the type and payload, seeded with the crc of the record before it, so a stale or misplaced record does not verify. Every segment starts with a copy of the newest hard state and root, so the latest term and vote, and the root, survive when older segments go.

An entry record replaces every entry at or after its index. A truncated Raft suffix and its replacement therefore reach the disk in the same write and the same fsync, before any later acknowledgement.

`WAL.Append` only encodes into a buffer. `WAL.Sync` writes the buffer with one write and one fsync, so whoever calls it decides the group commit: the node driver drains every queued append, then syncs once. A failed fsync is never retried; the node stops.

A new segment gets its header written and synced before its directory entry is synced and before any record goes in. So after a crash, a segment either has its full header or holds nothing else.

Recovery (`wal.Open`) first checks that the segment names are consecutive, then reads the segments in order, one in memory at a time, and keeps only where each entry and value record is: per run of entries, the segment, the offset of each record and the crc it chains from. `WAL.Entry` and `WAL.Value` read an entry or a value back by that map with `ReadAt`, and `Entry` checks the record's crc. In the newest segment, a record that does not verify starts a torn tail. If the next record does not verify either, chained from the bad record's stored crc or from its computed one, the write was never synced and never acknowledged, so recovery truncates the tail and syncs. A newest segment that holds no more than a damaged header is removed. Everything else is `wal.ErrCorrupt`, and the node refuses to start without changing any file:

- a damaged record in an older segment;
- a damaged record (body, type or stored crc) followed by a record that verifies;
- a damaged header with records after it, a file name that does not match its header, or a gap in the segment sequence or crc chain;
- an entry that leaves a gap, a log without a root that does not start at index 1, or a gap between the root's index and the entries after it;
- a commit index past the last entry.

It also removes the checkpoint files that the newest root does not name: a checkpoint that a crash cut short, or an older one.

The second rule can also fence a node after a crash in which the disk wrote a later sector of the last write but not an earlier one. Refusing to start is the safe answer there: cutting the tail could roll back a synced vote.

Known limits: damage to a record's length field misframes everything after it and looks like a torn tail, and so does damage to the last synced record. A disk that lies about fsync can lose a synced tail the same way. Recovery cuts the log silently in these cases; they are outside the guarantee until records carry redundant headers.

`WAL.RemoveBelow(mark)` removes the oldest segments whose every entry and value is below `mark`, never the current segment or the one before it, and then syncs the directory; segments go only from the front, so the rest stay consecutive. `RemoveCheckpoints(keep)` removes the checkpoint files below `keep`; newer ones may still be being written.

The WAL does no I/O of its own. It goes through `wal.FS`, a directory with List, Create, Open, Remove and SyncDir, and files with ReadAll, ReadAt, Write (append), Truncate and Sync. It takes no locks: the node driver holds one lock around the appends and the reads, not around the fsync. `internal/osfs` implements it on the local file system. `internal/simfs` implements it in memory for the simulator.

**Simulated disk.** `simfs.Disk` keeps volatile and durable state per file and per directory. Write and Truncate change the volatile content; Sync makes it durable. Create and Remove change the volatile directory; SyncDir makes it durable. `Crash` keeps the durable state plus a random prefix of each file's unsynced appends, and one time in four turns the last kept bytes into garbage, like a torn sector. `Erase` empties the disk for the erase-one-disk checks. A `Fault` hook runs before every operation and can fail it, which is where ENOSPC, EIO and stalled fsyncs come in. A sync that fails with EIO leaves zeros on the disk where its unsynced bytes were, while reads still see them, and a later sync does not write them, as Linux does after a writeback error.

The WAL crash test runs 500 seeds of random appends, suffix replacements and crashes, including crashes between the write and the fsync of one sync, and repeated crashes at the first writing operations of recovery (truncate and sync of a torn tail). A separate test crashes at each of the six writing steps of replacing a damaged header-only newest segment (remove, directory sync, and the create, write and syncs of the new segment). After each crash, recovery must return the synced log plus a prefix of the unsynced records. The test fails if recovery skips the torn-tail truncation or the crc check. Separate tests damage the body, type and stored crc of a record in the middle of the newest segment and the header of the newest segment, and remove a middle segment, also right before an empty newest one; each must give `ErrCorrupt` and leave the files alone.

`osfs.New` creates the data directory and its missing parents, and on every start syncs the directory and every ancestor up to the root, so a setup that crashed halfway is finished by the next start.

**Design E: values in the log, a window in memory, checkpoints.** Decided on [#117](https://github.com/djosh34/tigerstore/issues/117) after the prototypes on [#133](https://github.com/djosh34/tigerstore/issues/133); it replaces the checkpoint design of [#111](https://github.com/djosh34/tigerstore/issues/111), which copied every value into each checkpoint.

- **Values stay where Raft wrote them.** The index names each value by its Raft position and checksum (see the MVCC index). Every node holds the same entries at the same indexes, so the index, and every checkpoint of it, is the same on every node.
- **A window of entries in memory.** Raft's in-memory log (`core.storage`, a `raft.MemoryStorage`) holds the applied entries of the last `WindowBytes` (64 MiB) and those not applied yet. On the leader the window grows up to `WindowMaxBytes` (128 MiB) while a follower still needs older entries. Applied entries leave memory by an eighth of the window at a time, whether or not a checkpoint holds them: the log on disk still has them. A value whose entry left memory is read from the log (`core.Log.Value`); in this outcome that read runs on the committer. Every value read is a copy, from memory too, since a response or a watch event can wait behind a slow client long after its entry left memory. Entries not applied yet, those on their way to disk included, are bounded by `UnappliedBytes` (64 MiB): writes wait in the queue while it is full, and Raft's limits on uncommitted entries and on bytes in flight to a follower come from it. `TestWindowBound` writes 1 GiB through three in-memory nodes and checks after every step, also while the leader gets no acknowledgements and while a disk holds back its writes, that no node holds more entry bytes than the window maximum, the budget for unapplied entries and one entry.
- **Checkpoints.** A checkpoint is the replicated state at one applied index: the index with every version and the Raft position of its value, the revisions, and the leases with their stamps; never a value. Its file `ckpt-<index>` is a header (magic, the format version, the index and its term, the voters, the revision, the compaction revision, the lease stamps, the base and the leases), the keys in order, and a CRC-32C trailer. Every node cuts one after applying the entry at which the entry bytes applied since the last one pass `CheckpointBytes` (256 MiB) and `CheckpointRatio` (64) times the base, the size of the newest checkpoint finished when the last one was cut, which the header records. Every node knows that size however far its own copy got, so all nodes cut at the same index and, from the log alone, write the same bytes; a copy still running at the next cut is finished then. A checkpoint writes the whole index again, every version included, so the ratio keeps its bytes to about 1/64 of the log's while the index does not grow much between cuts. With 16, Put at max in the bench, which never compacts, wrote 4.4% more bytes per write than `main` before E on the shared disk and its p99 was 11% higher; with 64 it wrote 2.7% more and its throughput and p99 were within the noise ([#143](https://github.com/djosh34/tigerstore/issues/143)). A restart replays about `max(CheckpointBytes, 64 × base)` of log, plus what was applied while the next checkpoint was being written and its root synced. The committer freezes the index at that revision and copies it in parts of `CheckpointChunk` (32 KiB), one part per `CopyCheckpoint`; the node driver calls it every millisecond while a copy runs and the writer has taken the last part. While the copy runs, compaction leaves versions in place and the copy leaves out versions after the frozen revision, so the parts add up to the index at that revision however they are paced. The driver writes the parts (`Effects.Checkpoint`) to the file on a goroutine of its own, syncs it and the directory, and reports `CheckpointWritten`. The core then asks for a root (`PersistJob.Root`), which goes into the log in order with the appends. Once the root is synced, the driver removes the segments below the lowest entry that a value of the checkpoint is in, and below the checkpoint's index, and the older checkpoint files. While a follower may be fetching a snapshot from the leader, the leader's roots remove nothing, and the driver skips the removal of any root while a fetch from it is under way; the next root removes it all. A follower that needs one snapshot after another keeps the leader from removing anything until it catches up. A checkpoint counts only once a synced root names it.
- **Restart.** `wal.Open` scans the segments and returns the newest root, the hard state and the last index; it keeps no entries in memory. `core.New` loads the checkpoint the root names and checks its trailer and that its header matches the root, then applies the committed entries after it, read one at a time from the log, and hands Raft the rest. No summary log exists. A damaged checkpoint that a root names keeps the node from starting, like a damaged log.
- **Snapshots.** A follower that needs entries the leader no longer holds in memory gets a Raft snapshot with no data: the leader's newest durable checkpoint if it is past the window's start, otherwise the window's start (`core.storage.Snapshot`). Raft hands the follower's core the snapshot in its append message; the core turns it into a persist job with an `Install`, and holds the job's responses until the state is there. The follower's driver opens a separate connection to the leader (`peer.Transport.Fetch`) and asks for the entries after its applied index up to the snapshot's index. The leader's driver (`core.ServeSnapshot`) sends them from its segments, or, when some are gone, its newest durable checkpoint at or before the snapshot's index whose file it still has, the values it names in entries after the follower's applied index, and the entries after the checkpoint. Every item of the stream carries a CRC-32C. The follower (`core.ReceiveSnapshot`) checks each item, that the entries follow each other up to the snapshot's index and term, that each value matches its checksum, and the checkpoint's trailer and header, writes it all to its own log (entries, value records, the checkpoint file), and only then writes the root, which resets its log to after the checkpoint. Entries the follower already holds with the leader's term are the leader's, and it may have acknowledged them, so it skips them and the root keeps them; the first entry it lacks replaces those after it. The core then empties memory at the snapshot, loads the checkpoint if one came, applies the entries after it from the log, and steps the job's responses: the state is at Raft's snapshot, and the root names the checkpoint below it. A follower whose state a checkpoint replaced ends its watch streams; the clients watch again from where they were. The leader reports `ReportSnapshot` when a fetch from it ends, or as failed when no fetch started within `SnapshotTicks` (20 s) or the message could not be sent. A root that becomes durable after Raft sent the snapshot therefore does not keep the leader from serving the checkpoint the snapshot named, as long as that checkpoint's file is still there: the leader's roots remove nothing while a follower waits to fetch (`snapWait`), and its driver removes nothing while a fetch runs. Raft cannot take back a snapshot it handed the follower, so when the fetch fails, because the leader crashed, could not serve the snapshot any more, or sent bytes that do not check out, the follower's driver syncs what the stream wrote and starts a new core from its log, as a restart does, without exiting. Its waiting requests fail with "server stopped" and its watch streams end; the clients try again. The leader hears that the fetch failed, and Raft sends another snapshot. A failed write during an install still stops the follower, except the creation of a checkpoint file that is already there: an install queued before this one wrote it, and this one asked from an older applied index, so it ends the run for the same restart from the log.
- **Garbage collection.** With the values on disk, the heap is mostly the index, and every collection scans its pointers. At Go's default `GOGC` of 100 a node under load collected every few seconds, and with each node pinned to one CPU in the bench, each collection held up requests: mixed-k8s p99 at half of etcd's rate went from about 5 ms to 17 ms. `main` before E kept every entry in the heap, which put its next collection far off. `cmd/tigerstore` therefore runs with `GOGC` 400 unless `GOGC` is set; `GOMEMLIMIT`, when set, still caps the heap.

Not built yet, for the next outcome: cleaning (copying the live values out of mostly dead segments), value reads off the committer, a value cache, compression.

**Committer.** `internal/core` is one node's committer as an event and effect machine. Its inputs are method calls: `Submit` (a client request), `Step` (a Raft message from a peer), `Tick` (one clock tick) and `Persisted` (a disk write finished). `Process` runs Raft until it has nothing left to do and returns `Effects`: persist jobs, messages to send and replies. The driver calls these from one goroutine and carries out the effects. In the real node that driver is the committer goroutine; in the simulator it is the event loop.

- **Writes.** `Submit` validates the request with `mvcc.Check*` and then, like etcd, limits the size of the marshaled `InternalRaftRequest` that wraps a write to 1.5 MiB. Its header holds a request ID; the core sizes it with a 10-byte varint ID. That is etcd v3.7.2's strictest case (a member ID with bit 15 set, as in the difftest), which this matches to the byte (#62); for other member IDs etcd accepts one or more bytes more. With client certificates required (`--client-cert-auth`), etcd also puts the certificate's common name and the auth revision (1, since tigerstore never changes auth) into that header as `username` and `auth_revision` fields, even with auth disabled, so a client's writes have the size of those two encoded fields less room (#99), except for requests with `grpcgateway-accept` metadata, for which etcd ignores the certificate. The server computes that size once per connection from the leaf of the first verified chain (`core.Caller`). Reads do not go through Raft and have only gRPC's limit. Then it queues the write. `Process` packs the queued writes into entries of at most `MaxBatchBytes` (4 MiB), so a batch holds whatever arrived since the last call. While Raft knows no leader the node proposes nothing: as in etcd, whose raft.Node takes no proposal without a leader, writes wait for one, up to their deadline, instead of failing at once with "no leader" (#105). There is no timer. Each write in the entry carries its origin node, the origin's boot ID and the request ID (`core/codec.go`). Every write a client sends keeps its wire form in the entry: the connection reader decodes it with the generated decoder only to check it, `Submit` checks the decoded request, and `Process` copies the body into the entry instead of marshaling the request again. A Put goes further and is never decoded into a struct: the connection reader checks it with `core.ParsePut`, `Submit` validates and sizes it from its fields, and `Process` copies the client's bytes into the entry, the one encode of the batch. The entry keeps the client's encoding, so a write that repeats a field logs more bytes than etcd's re-encoding would, up to the 2 MiB receive limit; the size limit counts the decoded request. Its reply is the revision, term and previous key, which the connection writer encodes as a PutResponse without building a protobuf message. Raft is `RawNode` with `AsyncStorageWrites`, so the local append comes out as a `PersistJob`. The driver appends every queued job to the WAL, syncs once and reports each job with `Persisted`. The core then appends the entries to its in-memory Raft log and steps the responses. When an entry commits, the core applies it to the index on the spot and answers the requests whose origin and boot match its own. A boot ID is random per process start, so an entry proposed before a restart never answers a request made after it. Within one boot, the driver never reuses a request ID, because a write that timed out can still commit later. A write that the index rejects at apply time (an unknown lease, a missing key for `ignore_value`, a range at a compacted or future revision) is answered with etcd's error on every replica and changes nothing.
- **Reads.** Linearizable reads and read-only transactions queue up, and each `Process` turns the queue into one `ReadIndex` request. The reads run against the index once the applied index reaches the read index. Raft drops a `ReadIndex` without a word when a follower knows no leader, when a message is lost, and on every term change. So a batch without an index asks again every 3 ticks and at once when a new leader appears, and batches are served in any order. Serializable reads run at once against local state. The read context carries the boot ID too.
- **Timeouts.** Every request has a deadline in ticks (`RequestTicks`, 7 s). After it, the request fails with etcd's "request timed out", which is ambiguous: it may still commit. Without a leader nothing is proposed and writes wait (see Writes); a write whose deadline passes before it was proposed leaves the queue and fails with `DeadlineExceeded`, "context deadline exceeded", as etcd v3.7.2 answers a write whose context ends while it waits for a leader. The core does not see the client's own deadline or a cancel: a write whose client gave up can still be proposed later, an outcome its client's answer already allowed. A proposal that Raft drops while a leader is known, during a leadership transfer, fails at once with "no leader".
- **Membership is fixed.** The Raft storage wrapper reports the 3 voters as its configuration, and there are no configuration entries. Restart is described under design E below.
- **Fatal errors stop the node.** A failed disk write, an entry that does not decode, a value that does not match its checksum, or a snapshot whose checkpoint or entries do not apply stops the core. (A snapshot that cannot be fetched makes the driver start a new core from its log instead; see Snapshots.) So does a leader whose own append has been on its way to disk for two election timeouts (`ErrDiskStalled`): a stalled leader still heartbeats, so the others would never replace it, and its own clients would hang; the followers still commit without it, because two of their acknowledgements are a quorum. So does a leader whose own entries have waited three election timeouts to commit (`ErrCommitStalled`): a gray leader whose heartbeats get through but whose appends do not passes Raft's quorum check while nothing commits. Three is above the disk watchdog's two, so a stalled disk is usually caught first; an entry that already waited before the stall can reach three first. `Process` then returns the error, and every waiting request fails with "server stopped". Neither applies to a one-node cluster: with no other voter to lead in its place, stopping would only turn a slow disk into an outage, so the node waits for its disk. Raft's own logger is silenced but still panics on broken invariants. Tests can lower the three (`CommitStallElections`); the stress job sets it to one, at a real node's 100 ms ticks, to catch shorter stalls while values near the request limit are written from every node. To show where the time went, a node logs a log write that took longer than a tick, each change of leader or term, and, at most once a second per peer, messages that waited longer than 100 ms in their peer queue.
- **Responses are not prepared before commit yet.** Every node computes the results when it applies an entry, and the origin node replies right away. The apply step is a function of the index and the entry alone, so the leader can later run it ahead on a copy and hold the encoded replies until commit (see Seams).

**Leases.** The replicated state is `core.State`: the index and the leases, and `State.Apply` runs one committed write against both. The rules follow etcd v3.7.2 and the semantics pre-work on #47:

- **Grant.** A grant with ID 0 gets an ID from the node that takes the request, before it is proposed, so every replica applies the same one; it is positive and differs per node and boot. TTLs below 1.5 election timeouts, rounded up (2 s by default), become that; above 9,000,000,000 s is `too large lease TTL`; a taken ID is `lease already exists`; negative IDs are allowed. A grant does not move the revision.
- **Attach and detach.** After every write, the keys it changed leave the lease of their old version and join the lease of their new one, so a put without a lease or a delete detaches a key, and `ignore_lease` keeps it.
- **Revoke.** The lease's keys, in order, go in one transaction, so they share one new revision and watchers see all the deletes in it; a lease without keys moves no revision. A missing lease, lease 0 included, is `requested lease not found`.
- **Expiry.** Only the leader keeps expiry times, in ticks of its own clock. When a lease expires, the leader proposes an expiry like a write, again every 10 ticks until it applies, so every replica deletes the keys at the same revision. The expiry carries the lease's stamp, in a `LeaseCheckpoint` (etcd's only message with a lease ID and a number), and applies only if the stamp is still current. Every grant and keepalive takes a new stamp from one counter. So a keepalive that commits before the expiry keeps the lease, one that commits after it answers TTL 0, and a later grant of the same ID is a new lease that the old expiry cannot touch, the same on every replica. The leader arms a lease for its TTL plus one tick, since the current tick may be nearly over, so a lease never expires early. A node that becomes leader gives every lease its full TTL again; a leader change can make a lease live longer, never shorter.
- **Keepalive** is a Raft entry too: it is a write without a revision, and on the leader it renews the expiry when it applies. A missing lease answers TTL 0. **TimeToLive** and **Leases** are linearizable reads; TimeToLive reports the leader's remaining whole seconds, rounded down as in etcd, the granted TTL on other nodes, and TTL -1 for a missing lease.
- **Differences from etcd.** etcd renews a lease on the leader without Raft, so a keepalive here costs a WAL entry, in a log that nothing cleans yet. etcd forwards TimeToLive to the leader, so `etcdctl lease timetolive` counts down on any endpoint; here a follower reports the granted TTL. Kubernetes uses neither.

The gRPC Lease service serves all five, with KeepAlive as a stream of one request at a time.

**Watches.** Watchers live in the core (`core/watch.go`) and follow etcd v3.7.2's watch server. A driver hands the core the requests of a watch stream (`Node.Watch`) and closes the stream with `CloseWatchStream`; the responses come back as `Effects.Watch`. On create, watch ID 0 picks the next free ID of the stream, starting at 0. A taken ID, an empty range (an end at or below the key, other than `\x00`) and a negative start revision get etcd's created-and-canceled response with watch ID -1. A start revision below the compaction revision gets a response with `CompactRevision` that cancels the watch. A watcher that starts in the past catches up from `Store.History` at once, inside the call, in responses of at most 1,000 revisions that never split a revision, as etcd does. Then it is synced: after each applied write, the core matches the write's changes against every watcher and queues the events, and at the end of `Process` it sends each watcher one response with all of them and the current revision as header. `prev_kv` comes from the key's version list, so a create has no previous value and every update and delete has one. The NOPUT and NODELETE filters work. Progress follows etcd's `progressIfSync`: every watcher is always synced, so a progress request is answered at once with watch ID -1, except on a stream with no watchers or with a watcher that asked to start above the current revision. clientv3 resumes from a progress revision plus one, so a progress answer below a watcher's start would make it go back. Watchers that ask for progress notifications get one every `ProgressTicks` (etcd's 10 minutes; `--watch-progress-notify-interval` sets it, as in etcd) unless they got events since the last one or start above the current revision. A watch from below the compaction revision C gets the created response, then a cancel with `compact_revision` C, an empty reason and header revision 0, as in etcd. A watch with `prev_kv` from C itself is canceled the same way: the versions before C are gone, and etcd would send its first events without previous values, which Kubernetes rejects. The difftest allows exactly this answer for those steps.

The node driver keeps a queue of 4096 responses, and at most 64 MiB of them, per stream. A stream whose client falls further behind is closed with `Unavailable`, the code after which clientv3 resumes each watcher from its next revision. The gRPC handler honours etcd's `hasleader` metadata: it refuses to open without a leader, and like etcd's `monitorLeader` it closes the stream after three checks one election timeout (1 s) apart find no leader.

Matching walks every watcher for every change. An interval index over the watchers' ranges replaces that when Kubernetes' hundreds of watchers show up in profiles. Responses are never split into fragments.

**Deterministic simulator.** `internal/sim` runs the real `core.Node`, `wal.WAL` and `mvcc.Store` of all 3 nodes in one process. Everything is an event in one queue ordered by virtual time and sequence number:

- Ticks every 100 ms per node, with a random phase.
- A disk write writes at once and finishes its fsync 50 µs to 1 ms later, or 20 to 100 ms later for 2% of writes. A crash in between leaves a torn tail.
- Directed links are ordered streams: a message never overtakes an earlier one on the same link. Messages are marshalled at the sender and unmarshalled at the receiver, so nothing is shared between nodes. The simulator numbers the messages on each link and fails the run if one arrives after a later one. During the faults, delays come from each link's own profile (below), and 10% of messages take up to 5 ms; after healing, delays are 20 to 220 µs. A link that goes down, and every link of a node that crashes, drops what it carries.
- Faults in the first 20 virtual seconds: a node crash about every 3 s with a restart up to 2 s later, and a change of the set of up links about every 2 s, and at most 6 s apart. Half of those link changes heal every link; the other half pick a random one of the 64 directed-link masks.
- Disk faults in the same 20 s: about every 6 s, and once more in every run, the next write or sync of a node fails, with EIO on a sync, EIO on a write, or a short write with ENOSPC. The node stops at once, never retries the fsync, and restarts from its disk. A fault that hits recovery, which can truncate and sync, is a failed boot, and the node tries again later. About every 8 s a node's disk stalls for 1.5 to 4 s; healing ends a stall, and a write held back by it finishes then. At one crash in two, until it happens once, the crashed node gets a misdirected write: 16 to 64 synced bytes copied from another file or offset over a sealed segment. The simulator uses 8 KiB segments, so most of the log is sealed, and leaves the newest segment alone, where damage can look like a torn tail. The node must refuse to start (`wal.ErrCorrupt`) and stays fenced for the rest of the run, as if its disk awaited replacement. Lost writes are a lying disk and outside the guarantee. The extra fault becomes due in the first 5 s and fails the write of the next append with entries on any node; a write fault fires at once, while a sync can wait out a stall. If no node appends until healing, it stays due and fires on the first append after healing; the liveness rule then starts once the node is back (the restart bound plus 4 s), and the clients keep going until 3 s after that. The same holds for a node a watchdog stops after healing, if it stops within 4 s of healing; a later stop counts against the rule. `TestSeeds` requires a disk fault in every run, and a fenced node and a stalled leader that stopped somewhere in every set of 64 seeds or more.
- Network and process faults: every change of the link set also draws new delays for each directed link (a base of 20 µs to 2 ms plus jitter up to the base), so delays switch and the two directions of a pair differ; about every 4 s one directed link stalls for 0.5 to 2 s, including what is already on it, and then delivers everything in order, like a stalled TCP stream; about every 6 s a process pauses for 0.2 to 2 s and then handles everything at once, in order (a second pause can only make it longer, a crash ends it, and the simulator fails the run if a paused node does any work, closing a watch stream included); about every 8 s one directed link goes half-open: the sender still sees its connection, but what is on the link and what it sends vanish until, after 0.5 to 5 s (the peer write timeout), its connection fails and Raft hears that the peer is unreachable. Stalls and pauses end by healing at the latest, and healing ends half-open links. Each of these faults also comes once at a random time in every run, retried until it takes effect, and `TestSeeds` requires every one of them in every run, and a link at least 10 times slower than its other direction somewhere in every set of 64 seeds or more. Clocks run up to 5% fast or slow per node, and about every 6 s a node's clock jumps forward by up to 3 ticks, at most once per node in 10 s. That is the declared clock envelope: lease expiry is checked against it.
- Gray faults in the same 20 s: about every 8 s a gray period of 2 to 6 s starts. In half of them the leader is gray for the whole period; in the rest one node at a time is gray, and every 1 to 3 s the gray node may change to another one. Raft heartbeats, votes and responses to and from a gray node get through, but appends do not, and in half the cases its fsyncs take 0.5 to 3 s. One more gray period in every run lasts, past healing if need be, until its gray node has lost an append, and moves on from a node that is down. A gray fsync already in flight can finish after healing; the liveness rule below counts from it. A gray client opens a stream with 10 watches on the key range, a quarter of them from revision 1, and reconnects to a random node every 50 to 300 ms until healing; at the end every node must hold only the watchers of open streams. The core has no queue toward a client, so a client that reads slowly costs it nothing; the node driver's bounded watch queue (`ErrWatchTooSlow`) is left to the real-process tests. Restarts of a node with a log crash again inside `wal.Open`, at the first to sixth writing disk operation and every one after it: every restart until one such crash happened, then one in three. The repair of a torn tail writes twice and that of a damaged newest header six times, so until the first crash the cut is at one of the first two. Until then, the next node to write entries also crashes between the write and its sync, which leaves a torn tail to repair. `TestSeeds` requires a gray node that lost an append and gray-client streams in every run, and a gray leader stopped by the commit watchdog and a crash in recovery in every set of 64 seeds or more.
- Six clients, each with one call in flight, on 8 keys, also compacting about once in 100 calls a little behind the newest revision they saw, and granting leases of 2 to 4 s, putting keys with the newest one, keeping it alive and revoking leases now and then: puts and deletes with and without previous values, range deletes of up to 3 keys, compare-and-swap transactions with a failure-branch range, transactions that put two keys, linearizable and serializable reads, prefix reads with limits, and reads at past revisions. A client gives up after 3 s.
- Four watch clients: a prefix and a single key with `prev_kv`, a sub-range with `prev_kv` and progress notifications, and an open-ended range with progress notifications. Each starts from revision 1 or from now. When its node crashes, and on purpose about every 3 s, it closes its stream and opens a new one on a random node up to 2 s later, from the revision after its last event or progress notification, as clientv3 does. The simulator sends progress notifications every 2 s instead of 10 minutes, and every response must carry the watch ID of the stream's watcher.
- Design E with tiny limits, so every seed uses it: a window of 16 bytes of applied entries (32 while a follower lags), a checkpoint after 256 bytes of entries and twice the base, copied 32 bytes at a time, 8 KiB segments, and a snapshot given up after 1 s without a fetch. A snapshot is fetched from the leader's simulated disk when the follower's install job starts; it fails if the leader is down, paused or cut off. A failed fetch syncs the follower's disk and starts a new core on it at once, as the real node does. Faults of E in the same 20 s: once per run a follower is kept down for 3 to 5 s, so it falls behind the window; the leader serving the first snapshot stream of a run crashes partway through it; the first stream that arrives whole, and one in four after it, arrives with a damaged byte; half the fetches start 0.2 to 2 s late, so the leader may make a newer checkpoint durable first, or give up on the snapshot and remove what it needs (`TestSlowFetch` requires both across its seeds); once per run a node crashes at a step of a checkpoint (after a part is written, after the file's sync, after the directory's sync, after the root), of a removal, or of an install (after each item it writes); and once per run, as the run's damage if it has none yet, a bit of the newest value of a key flips on the disk of a running node, in a sealed segment or with a durable entry after it in the newest one, so it never looks like a torn tail. The node must stop when it reads it and refuse its log on the next start.
- Then 10 healthy seconds with the clients still running, and 10 quiet seconds, so the last leases expire and their watch events arrive.

The seed drives a PCG generator for every choice. Raft draws its election timeouts from `crypto/rand`, which the test makes deterministic with `cryptotest.SetGlobalRandom` seeded from the same seed. Each event, each message, each reply and each restart goes into an FNV-64a trace hash. `TestSeeds` runs every seed twice and fails if the hashes differ.

The simulator keeps its own record of the committed history, apart from what the nodes retain: every entry as the first node applied it, and the hash of the state after it (`core.Config.Record` makes the core report both). Each time a node applies an entry, or loads a checkpoint at an index, its entry and its state's hash must match the record at that index. Each time a node writes a checkpoint, its bytes must match what the other nodes wrote at that index. A node must never hold entries in memory past its applied index plus one.

After a run, the simulator checks the following. Its own checks do not validate compaction errors or compaction cancels; those calls and watch parts are checked only by #56's `check.Revisions` and `check.Watches`. Because the cluster compacts, the checks read history from a model: the recorded committed log replayed into a fresh store without compactions, which must end at the cluster's revision with its keys and values, read through a node's own value reads.

- every node is up, has applied to the same index, and has the same state hash as the record;
- every successful read returns exactly what the final index holds at the revision the read saw, including reads inside transactions;
- every acknowledged put is in the final index at its revision, its previous value is the final index's value at the revision before, and an acknowledged delete removed a key that existed and left none behind;
- every compare-and-swap held at the revision before its write, or failed at the revision it saw;
- no call sees a revision older than one that another call returned before it started, every write gets a newer revision than that, and no two writes share a revision;
- every write is in the committed log at most once, every acknowledged write is in it, and no write that failed for certain is (each written value belongs to one call);
- every logical watch delivered exactly the history of its range from its start revision, to the final revision for the current one and up to its last event for one that a compaction canceled (the client then starts a new logical watch from now, as Kubernetes does), in order, without duplicates, with previous values where asked, and no event above its response's header revision;
- every lease still granted at the end was granted or kept alive within the last 8 s, the largest TTL plus a leader change, so leases do expire; and no lease expired, on any node, before its TTL ran out since its last successful grant or renewal, less what the clock envelope allows (5% of the TTL and one jump of 3 ticks);
- erasing each node's disk in turn, at a checkpoint during the faults and at the end, and cold-starting the other two alone from their synced bytes applies at least every entry that any node had applied by the checkpoint, and every entry and state the two reach up to there, from their checkpoints or by applying, is the one in the run's record. An acknowledged call was applied before it was answered, so this covers every acknowledged write, delete and lease change with its revision: the guarantee that an acknowledged write survives the loss of one node;
- every call that starts 4 s or more after healing, or after the last gray fsync that outlasted healing, gets a definite answer, except calls to a fenced node, which a real client would leave for another endpoint, and to a node whose disk is stalled at the call (success, or an answer such as a compacted revision), and at least 50 do. Four seconds is four election timeouts: a node restarted at healing may need two to elect, and a node that comes out of the faults with a higher term and a shorter log can then make the new leader step down once, which costs another election (seed 721530481). A gray fsync in flight at healing can finish up to 3 s after it. Until then its node's term and vote changes, and the peer messages that wait for them, are held, so a higher term can reach the new leader late and cost one more election (seed 745672193, before writes waited for a leader: an fsync started at 19,892 ms finished at 22,701 ms, and the delayed rejection of a pre-vote made the leader step down). So the rule starts 4 s after healing or after the last such fsync, whichever is later, and the clients run for at least 3 s under it. The guaranteed gray period's append drop does not move it: votes and heartbeats pass a gray node, and that drop can come only after an election, which the rule must bound. With a node fenced, the rule starts 2 s later: every election then needs both remaining nodes, and when one has the longer log and the other the higher term, they reject each other's pre-votes until the first learns the term from a rejection.

These checks catch a stale read (linearizable reads served without `ReadIndex`), a WAL that skips fsync, a transaction compare that is off by one, a proposal applied twice, watch events without previous values, a watcher that skips history, a watcher that gets only the first change of a write, a watcher that starts one revision late, a matcher that ignores the range end, and a progress notification 5 revisions ahead; each was planted by hand and failed. `core/watch_test.go` covers create rules, filters, cancel, progress, and catch-up of 1,100 revisions of three keys, which fails if a response is cut by event count instead of by revision. The checkers of package `check` ([#56](https://github.com/djosh34/tigerstore/pull/56)) are the independent oracle. `Result.Checkable` converts a run into their `history.History`: every call, the committed log, the watches with every response, and the final revision as the watch target. `TestSeeds` runs the durability, revision and watch checkers on every seed. Porcupine gets its own short runs in `TestLinearizable` (5 virtual seconds of faults with 4 clients, then 8 s of healing, without leases), because it searches too long on full runs: one 7,263-call history of seed 9 timed out after a minute, and with 6 clients one 1,481-call history took 12 s. With 4 clients, 200 seeds each checked in under a second. Leases are left out of these runs: every granted lease becomes an ambiguous expiry op that may apply at any time, and with leases two of three short runs timed out. The full runs keep leases, and the durability, revision and watch checkers see them. In the history, every granted lease gets such an expiry op from its own client, called with the grant, and keepalives are left out, since the format has none and they change no key. An ambiguous write that the committed log does not hold is left out. One that the log holds once, from a call whose request no other call has, gets an `Effect`: the revision the log gives it, and the time the next write after it in the log was acknowledged, by which it took effect. Porcupine then applies it without forking it into took effect or not, as etcd's robustness tests do with persisted requests. Seed 1320469923, with 8 such writes in its first 7.3 s, timed out after a minute without them and checks in 5 ms with them. `TestAllLinkMasks` holds each of the 64 sets of directed links for 3 s with no other fault, then heals for 8 s, and runs every checker, Porcupine included; each must be installed once. `TestSwitchingLinks` switches to a random set about every 300 ms for 10 s. `TestEachFaultTakesEffect` runs each network, process, gray and recovery fault alone and requires that it happened. `TestGrayClient` runs the gray client alone: every other call must succeed in under a second. `TestGrayLeaderIsReplaced` makes the leader gray for good with no other fault: it must stop within three election timeouts plus two ticks, and every call to the other two nodes that starts three election timeouts after that must succeed in under a second. `TestGrayHealingSeed` replays seed 2507 twice, whose gray fsync ends at 22,285 ms, runs the independent checkers, and requires definite answers from 22,400 ms, before the general recovery allowance ends. `TestGrayFsyncRecoveryBound` checks that only a gray fsync that outlasts healing moves the bound, that a healthy fsync and a crashed node's canceled fsync do not, and that clients still run long enough to check it; `TestGrayAppendRecoveryBound` checks that the gray period's append drop after healing does not move it. `TestDiskFaultAfterHealing` cuts every link before the first election, so the guaranteed disk fault fires after healing, and the run must still pass. `TestHalfOpenLink` makes the link from the leader to a follower half-open for 5 s: every call to the leader and the other follower must succeed in under a second, and the cut-off follower must serve again 2 s after its connection fails. `TestStalledLeaderIsReplaced` stalls the leader's disk for good with no other fault: the leader must stop within two election timeouts of the stall plus two ticks (one for an append already queued, one for the next client write), and every call to a healthy node 10 election timeouts later must succeed. A planted stale read fails both Porcupine and the revision checker on seeds 1 to 4 of the full runs and 1 to 3 of the short runs, with the simulator's own checks bypassed. The converter refuses anything the format cannot hold (a compare over a range, nested transactions, sort options, revision filters, `ignore_value`, `ignore_lease`, an unknown event type) instead of dropping it.

**Determinism lint.** `internal/lint` is a test that parses the non-test files of `history`, `internal/core`, `internal/mvcc`, `internal/wal`, `internal/simfs` and `internal/sim`. It fails on a `go` statement, a dot import, a call to a global `math/rand/v2` function, a `log` function that writes to standard error, an import of a module package outside the core list, and imports of `time`, `os`, `syscall`, `net`, `path/filepath`, `crypto/rand`, `math/rand`, `sync`, `runtime` and `unsafe`. It does not see a range over a map, which Go randomizes; the cross-process trace diff in CI catches that. A second test feeds it a file with each violation and requires each to be reported. CI runs it as its own job.

**Real node.** `internal/node` is the driver of `core.Node` outside the simulator. One committer goroutine owns the core. It waits for an input (a client request, a peer message, an unreachable report), a finished disk write or a 100 ms tick, takes up to 4096 more inputs that are already queued, calls `Process` once, and carries out the effects. One disk goroutine takes every queued persist job, appends them to the WAL, syncs once and hands them back on its own channel. That is the group commit: while one fsync runs, the next batch builds up. The committer never blocks on the disk: persist batches wait in a list that it hands to the disk goroutine as space frees up. With 64 batches waiting, it stops taking new inputs but keeps ticking and taking finished writes, so a slow disk slows down clients and peers instead of stopping the node. gRPC handlers call `Node.Do(ctx, op)`, which queues the request with a reply channel and waits for the reply or the context. A request whose client gave up still runs; its reply is dropped. A failed write or sync stops the node. A third goroutine writes checkpoint parts, which the committer hands it the same way, and reports each written checkpoint back through the inbox. A persist job with a snapshot makes the disk goroutine fetch it from the leader and write it to the log before the rest of the job, syncing every 16 MiB; a job with a root makes it remove the old segments and checkpoints once the root is synced. `Node.Serve` answers a follower's snapshot fetch from the WAL and the durable checkpoints whose files are still on disk, which the disk goroutine records when a root or an install is synced; while a fetch is under way, it removes nothing. When a fetch fails, the disk goroutine syncs what it wrote and ends the run; `Run` fails the waiting requests, ends the watch streams, reopens the WAL and starts a new core from it, and runs again with the same inbox. The WAL's map of entries is behind one lock that the appends and the reads take, the committer's value reads included, but not the fsync.

**Peer transport.** `internal/peer` implements the decided transport. `peer.Transport` has three methods, `Send`, `Fetch` and `Close`, so other transports can replace it. The TCP implementation keeps one outbound TLS 1.3 connection per peer, with the peer CA verified on both ends. The dialer first sends its Raft ID as 8 bytes, then frames of a 4-byte length and a `raftpb.Message` in its protobuf encoding, so every Raft field survives. The decision said no gRPC or protobuf between nodes; the architect accepted protobuf frames for now ([clarification on #47](https://github.com/djosh34/tigerstore/issues/47)), since raft v3.7's message types are protobuf and the writer goroutines, not the committer, do the encoding. A hand-written codec is an outcome-4 experiment. Each peer has a writer goroutine with two queues: appends and snapshots, empty appends included, go on the data queue so they stay in order, and so do proposals that a follower forwards with whole write batches; everything else (heartbeats, votes, ReadIndex and their responses) goes on the control queue, which the writer empties first. Each queue holds at most 64 MiB of entries and contexts. A message over the 64 MiB frame limit is dropped before it is sent, received frames are capped at 64 MiB, and each write has a 5 s deadline. `Send` never blocks: a full queue or a broken connection drops the message and reports the peer unreachable to Raft, which falls back to probing. The writer marshals messages, not the committer. A `MsgSnap` carries no data. A follower fetches what it lacks on a connection of its own: it sends its ID with the top bit set and the first and last index it needs, and reads the snapshot stream until the leader closes it (`Transport.Fetch`, `Config.Serve`); each read and each write has the 5 s deadline.

**gRPC server.** `internal/server` serves the client port with its own HTTP/2 and gRPC code on x/net's Framer and HPACK, decided in the [design change on #50](https://github.com/djosh34/tigerstore/issues/50). grpc-go's server is not used; clients and tests still use grpc-go's client. It serves etcd's KV service (Range, Put, DeleteRange, Txn, Compact), Lease (Grant, Revoke, TimeToLive, Leases, and KeepAlive as a stream of one request at a time), Watch as described above, Cluster.MemberList, Maintenance.Status and Maintenance.Alarm. KV.RangeStream is served as etcd v3.7.2 serves it: chunks of keys, the first of 10 and each next one doubled below half of 1.5 MiB or halved above twice that, every chunk read at the revision of the first, and the header (with the store's revision at the first read), count and more on the last chunk only; custom sort orders and revision filters answer Unimplemented, as in etcd. Every other method of etcd's services, including Auth and member changes, answers Unimplemented with grpc-go's message. `/metrics` answers in Prometheus' text format with the etcd metrics that scrapers read most, under etcd's names: `grpc_server_started_total` and `grpc_server_handled_total` by method and code (every code of every method, at 0 too; a call the client cancels counts as Canceled; calls of methods tigerstore does not serve are not counted, though etcd counts its own), the protobuf bytes of client messages in and out, `etcd_server_has_leader`, leader changes, the committed and applied indexes as `etcd_server_proposals_committed_total` and `_applied_total` `etcd_mvcc_put_total`, `_delete_total` and `_range_total` (ranges include the reads etcd makes for compares, prev_kv and the ignore flags), and `process_start_time_seconds`; it does not have every etcd metric. Status reports version 3.7.2, storage version 3.7.0, the leader, the term, the commit and applied indexes, the 2 GiB default quota, "etcdserver: no leader" in Errors without a leader, and the estimated log size as the database size, never 0 because etcdctl divides by it.

Each connection has a reader goroutine, which decodes frames and copies each request message once out of the Framer into a buffer of its own size, and a writer goroutine, which is the only one that writes and which keeps to the client's flow-control windows. A streaming call runs in a goroutine from its first headers. Status and MemberList run in a goroutine of their own.

The unary calls that the node runs (KV, Compact and the unary Lease calls) take the whole-batch path. The reader decodes each complete request and hands all of them to the committer with one `Node.SubmitBatch` call. It does this when reading the next frame could wait for the client, because that frame is not buffered whole or starts a header block that continues in later frames, or at 256 requests or 4 MiB. There is no timer. The committer submits each request to the core, and after each `Process` it hands every connection all of its replies of that turn with one `Complete` call. `Complete` only pushes them onto a lock-free list, adds their size (`proto.Size`, or a fixed estimate) to the connection's count of waiting replies, and wakes the writer, which encodes the replies. So such a call costs no goroutine, context, channel or inbox send of its own. Each call holds its request bytes plus 512 from when the reader hands it over until the node answers, and its reply bytes from then until the reply is sent or the client resets the call. A call whose deadline passed before its batch goes out is not handed over. Once a connection's calls and its waiting replies hold more than 64 MiB, its receive window is not credited back, so the client stops sending while the reader still reads pings, resets and window updates. If the node stops, every call it held fails with "server stopped" after the replies it already gave are sent. Response header and trailer blocks are HPACK literals that are never indexed, each after a dynamic table size update to 0, so they are built once and are valid whatever table size the client set. The server follows grpc-go and etcd where clients can see it:

- The receive limit is etcd's 1.5 MiB request limit plus 512 KiB, with grpc-go's ResourceExhausted "received message larger than max". Compressed messages are refused with Unimplemented.
- `grpc-timeout` ends the call with DeadlineExceeded when it passes, whether or not the request is complete or the handler started; `0n` has passed already. etcd's `hasleader` metadata fails a call without a leader with "etcdserver: no leader", unary calls included, and ends a Watch or LeaseKeepAlive stream after three checks one second apart find no leader, as etcd's interceptors do.
- A stream the client resets is canceled, and a reply that comes after the reset is dropped. When the server ends a stream that the client has not ended, it sends RST_STREAM with NO_ERROR, as grpc-go does.
- A streaming call may queue 4 MiB of replies for the writer; a watch stream that cannot send waits there, and the node closes it when it falls 4096 responses behind (see Watches), which also ends the waiting send. A stream that fails drops the replies its client has not taken, so its status goes out at once. A unary reply is queued whole, as grpc-go does, so a client that stops granting flow-control window keeps its unary replies in memory until it goes away. At most 10,000 control frames (ping and settings acknowledgements, resets, window updates) wait for the writer; past that the connection closes. A write that blocks for 20 s closes the connection.
- The reader decodes header blocks with one HPACK decoder per connection, which fills the request's fields without allocating once they are in the dynamic table. It keeps x/net's checks: a string over 1 MiB, or a fragment that could decode past 1 MiB for the block, ends the connection; so does a fragment after a broken field and a HEADERS frame that cannot be parsed. A malformed block (a field name that is not a lowercase token, an invalid value, a pseudo-field after a regular one, an unknown or repeated pseudo-field, a block over 1 MiB) on a new stream, or as trailers on an open one, resets that stream with PROTOCOL_ERROR; on any other stream ID it ends the connection.
- The writer sends at most one frame of each ready stream per turn, so one large reply does not hold up the others.
- A second end of a stream (DATA or trailers after END_STREAM) resets it with STREAM_CLOSED, and data past a stream's 4 MiB window resets it with FLOW_CONTROL_ERROR. Padding is credited back at once. HEAD gets headers without a body.
- The receive window is 4 MiB per stream, above the largest request, and 16 MiB per connection, credited back as data arrives. A connection allows 1,048,576 concurrent streams.
- Stop sends GOAWAY, lets streams in flight finish for one second, and then closes every connection.

The same port answers `GET /version` and `GET /health`, over HTTP/2 and, for a TLS client that does not offer h2, over HTTP/1.1. `/version` answers `{"etcdserver":"3.7.2","etcdcluster":"3.7.0","storage":"3.7.0"}`, which kubeadm's preflight reads. `/health` follows etcd: without `?serializable=true` it needs a leader, then it makes a one-key keys-only read with etcd's 7 s request timeout, and it answers `{"health":"true","reason":""}`, or 503 with `RAFT NO LEADER` or `RANGE ERROR:<error>`, written as `http.Error` writes them; `health` is a JSON string. Without TLS, the port serves HTTP/2 with prior knowledge only, which is for tests. Client TLS takes a certificate, and with `--client-cert-auth` it requires client certificates from `--trusted-ca-file`.

**Command.** `tigerstore` runs one node with etcd's flag names: `--name`, `--data-dir`, `--initial-cluster`, `--initial-cluster-token`, `--listen-peer-urls`, `--listen-client-urls`, `--advertise-client-urls`, `--cert-file`, `--key-file`, `--trusted-ca-file`, `--client-cert-auth`, and the `--peer-*` versions. A node's Raft ID is its position in `--initial-cluster`, and the cluster ID is a hash of the token and that list. Peer URLs must be https. As in etcd v3.7.2, `--peer-cert-allowed-cn` and `--peer-cert-allowed-hostname` take comma-separated lists, and at most one of them may be set. When one is set, both ends of a peer connection also require the other node's certificate to have one of those common names, or to be valid by its SANs for one of those hostnames (`internal/peer/cert.go`). `scripts/dev-certs.sh` and `scripts/local-cluster.sh` start a local cluster. CI's `smoke` job runs etcdctl v3.7.2 put, get, del, watch and endpoint status against it over TLS, reads `/version` and `/health`, and checks that a client without a certificate is refused. `internal/server` has a Go test that runs 3 nodes in one process over real TLS, restarts one from its disk and reads its data back.

**Benchmarks.** `cmd/loadgen` is the load generator for etcd and tigerstore alike. It speaks gRPC over raw HTTP/2 and TLS 1.3 with client certificates, with many streams per connection, fixed-size requests stamped out from prebuilt frames (mixed encodes and frames each variable-size request at send time), and either every stream busy or open-loop Poisson arrivals. Its workloads are Put, CAS Txn, Delete, Range, LIST, Watch and mixed Kubernetes operations on Kubernetes-shaped keys. Latency covers every request that arrived in the window, from its scheduled send time, however late it completes. A unary call succeeds only with exactly one response message, and any error, including a failed CPU sample, marks the result invalid. It reports server CPU per operation per node from `/proc` and its own CPU per operation. `bench/run.sh` runs named targets (etcd and two tigerstore builds) back to back, in reversed order on even repetitions, each on a fresh 3-node cluster with client and peer TLS. `bench/cluster.sh` pins the generator, the leader and the followers to their CPUs after the election, and `cmd/benchreport` makes the tables and refuses invalid results. The `bench` workflow, started by hand, does this on an `ubuntu-24.04-arm` runner with disk write barriers on: generator on CPU 3, leader on CPU 0, followers on CPUs 1 and 2, 5 repetitions per target. Every reported statistic has its minimum, median and maximum over those repetitions, including generator CPU in both modes. Invalid results and unequal target run counts stop the report.

`mixed-k8s` preloads 1,000,000 keys, then grows the live set with creates during the run. Namespaced keys have the form `/registry/<resource>/<namespace>/<name>`, across about 1,024 namespaces. Cluster-scoped resources instead use `/registry/<resource>/bench-<owner>-<group>-object-<id>`, with owned group prefixes ending in `-` rather than `/`. `cmd/loadgen/k8s_sizes.go` embeds the resource and size-bin counts, observed minimum and maximum, and mean from the [Kubernetes 1.37 dump on #50](https://github.com/djosh34/tigerstore/issues/50#issuecomment-6134373626). The table has 6,261 source objects and 9,217,907 value bytes. Resource shares use object counts. Within a resource, bins use their object counts. The inventory has no finer within-bin histogram. Each nonconstant bin uses a scaled beta model on its exact observed min/max, with alpha `8*p`, beta `8*(1-p)` and `p=(mean-min)/(max-min)`. Stochastic integer rounding preserves the exact bin mean in expectation. Constant bins keep their observed size. This is a fitted smooth distribution, not empirical resampling. This is a size model, not a copy of object content. Values use disjoint windows of random bytes from each worker's pool, as the other workloads do.

The default mix is 25% point GET, 10% namespace LIST, 40% update, 15% create and 10% delete. `-mix` takes those five percentages in that order, and `MIX` passes them through `bench/run.sh`. Create compares create revision with zero in a Txn. Update and delete compare with the key's known mod revision. Ten percent of GETs read known absent keys when any exist, so deletes are checked by Range too. LIST asks for the first 500 keys, including the full count and more flag. Each worker owns its namespaces and keys, and selection skips LIST groups with active calls and keys whose group is already LISTing. A started LIST blocks that group's mutations until it completes, without holding back arrivals for other groups. That permits exact validation of count, ordering, values and every KV revision field without a global state lock. Deletes make keys absent; creates reuse some absent keys and allocate new ones too. Watches run on every resource prefix from the revision after preload. Every event, including its previous value, matches an acknowledged mutation and is checked in revision order. Missing, duplicate or changed events fail the result.

Preload uses Txns of up to 128 puts, capped at 60 KiB and the connection's stream window, with at most eight in flight per connection and 300 Txn arrivals/s over all connections by default. `-preload-rate` changes the setup rate. Preload is not a maximum-throughput measurement. It does not raise etcd v3.7.2's default transaction limit. Preload and watch setup finish before CPU and latency measurement. Mixed opens six request connections round robin across all three endpoints, rather than only the leader. Server CPU still sums all three node processes. A rate-only mixed job first measures one maximum-throughput run per store at the same six connections and 16 streams. Its open-loop rate is half of etcd's median maximum from those calibration results (one sample by default), rounded down; `MIXED_RATE` can override it. All three stores then get five rate repetitions at that same measured load. In [run 38444109849](https://github.com/djosh34/tigerstore/actions/runs/38444109849), etcd's one max sample was 2,838.7 ops/s, so the five rate runs used `floor(2838.7/2) = 1419` arrivals/s. The baseline and candidate max samples were 12,148.8 and 12,711.8 ops/s; neither was used to choose the rate. The workflow allows 75 minutes for the extra preloads; it does not reduce the five repetitions. The other benchmarks keep max mode and rate mode at half of etcd's median maximum throughput. The default three-second warmup and ten-second measurement keep log growth small. The preload holds about 1.47 GB of value bytes per node before log and index overhead. Servers have a 3 GiB Go memory target for this workload. Targets run sequentially, with fresh data directories, so values and logs from earlier targets do not remain on the 16 GB runner. The GitHub run checks the actual fit; this is not a capacity test.

## Testing

### Deterministic simulation

- The core is an event and effect machine. Inputs are requests, cancels, peer bytes, ticks, and I/O and send completions. Outputs are disk operations, sends, replies and timers.
- Four adapters sit at the edge: disk, network, clock and randomness. Core packages may not call `time.Now`, use global randomness, make syscalls or start goroutines. A lint in CI enforces this.
- The simulator runs the real core of all 3 nodes in one process from one seed. Stock raft v3.7.0 becomes deterministic through `testing/cryptotest.SetGlobalRandom`, with one seed per process and a pinned Go version. Every PR replays seeds twice and compares trace hashes.
- Buffers are poisoned after release at every asynchronous boundary.

### Simulated faults

- A byte-level disk with volatile and stable state and directory operations: torn, lost and misdirected writes, slow, stalled and failing fsync, and ENOSPC. Disks that lie about fsync are outside the guarantee, but detectable damage must fence the node.
- TCP as ordered streams: head-of-line blocking, stalls and half-open connections. All 64 directed-link reachability masks run on every PR, plus switching between them. Short, long, switching and asymmetric delays, and one link much faster than another.
- Crashes at every persistence step, and repeated crashes during WAL recovery and snapshot install. At checkpoints, each node's disk is erased in turn and the other two cold-restart.
- Gray nodes and barely alive clients, each with a numeric liveness bound. For example, writes commit within 10 election timeouts while two nodes are healthy. A gray leader is fenced, not only asked to transfer leadership.
- Process pauses, clock skew and clock jumps.

### Checkers

- Porcupine with the ported etcd model, on isolated small histories, as the independent oracle.
- A revision-witness checker for large histories, added only after the differential tests settle historical Range and failed-branch revision semantics.
- A strict watch checker. The previous value is required on update and delete events of watches that ask for it, and not on creates. Kubernetes rejects a non-create event without it. Each watch must be complete up to a target revision, in order and without duplicates.
- Durability of acked and returned data, revision rules, always-on invariants and a coverage floor.
- Sequential differential tests against etcd v3.7.2 for the boundaries: compaction at R-1, R and R+1, error codes, and the maximum request size, for a Put and a Put inside a Txn with keys of 37, 39, 136 and 3,036 bytes. etcd runs there with client TLS and `--client-cert-auth`, as tigerstore does, so the certificate's name counts on both. A watch step ends on a progress notification, which both servers send only for a caught-up watch, never on a timer; only a watch that starts above the current revision, which neither server confirms, ends after 500 ms without a response.
- About 18 planted bugs behind a test-only build tag. CI fails if one is not caught within its fixed seed budget.

### Real processes

The fault proxy on every link, tc netem, SIGKILL, SIGSTOP, CPU throttling and a fault-injecting file layer. Each job checks that every requested fault was actually installed. Bugs in TLS, HTTP/2 or the Go scheduler get their regression test at the layer that reproduces them.

### Budgets and regressions

The first measurement is the full harness cost per seed on `ubuntu-24.04-arm`, capped at 256 MiB per simulator worker. PR, nightly and release campaigns are sized from that. A failing seed becomes a shrunk schedule and a named scenario test that fails on the bad commit.

## Seams for later pieces

Later pieces plug in here without reshaping what exists.

- **Values point into the log.** Every write applies from its entry without copying values. Writes other than puts are still decoded into request structs on every replica. Transactions and deletes use decoders written out per message (`core.DecodeAlias`), which took 445 ns for a 1 KiB compare-and-swap where `proto.Unmarshal` took 1,021 ns and the protoreflect `UnmarshalAlias` 1,796 ns on this host; executing them without structs is the next step. LeaseKeepAlive, a stream, still goes through `Node.Do` and is marshaled into the entry. Segment cleaning has to copy live values out before it frees a segment.
- **Segment cleaning.** A synced root lets the node remove the oldest segments that hold no value its checkpoint names. A segment that still holds one live value stays, and so do all after it. Cleaning copies the live values of mostly dead segments into value records or packed files that keep their Raft positions, then removes them; it comes with the next outcome.
- **Disk faults.** `simfs.Disk.Fault` can fail any operation on any file; the simulator fails only writes and syncs so far. Not covered yet: read errors; random crashes inside the steps of `wal.Open` in the simulator (the WAL crash tests cover them); replacing a fenced node with a fresh member that catches up by snapshot; and restarting an erased node with an empty disk, which with fixed membership can lose an acknowledged write, so it waits for member changes.
- **More simulated faults.** `sim.Faults` holds the fault rates. A gray node, with slow disk writes and delayed links at once, is not a fault of its own yet. The half-open model trusts the peer transport to fail a dead connection within its 5 s write timeout; with only small Raft messages on it, a real socket buffer may not fill, and Go's default TCP keepalive takes longer than 5 s to notice. Peer connections need `TCP_USER_TIMEOUT` or a heartbeat timeout of their own; they have neither yet.
- **Responses prepared before commit.** `core.Node.apply` runs one entry against the index and answers its requests. To prepare responses before commit, the leader runs the same function on its proposals while they replicate, keeps the encoded replies, and releases them when the entry commits at the expected index and term. A leader change drops them. The followers keep applying at commit.
- **Other transports.** The core only produces and consumes `raftpb.Message` values, and `node.Node` only needs a `peer.Transport` for sending and `Node.Deliver` for receiving. A tournament transport implements those two.
- **Alarm.** Tigerstore raises no alarms. Status reports etcd's 2 GiB default quota, but tigerstore does not enforce it, and it has no hash check between members, which is what makes etcd raise CORRUPT. So it never raises NOSPACE or CORRUPT. A full or failing disk stops the node instead, and a corrupt log keeps it from starting. `Maintenance.Alarm` answers after a linearizable read, as etcd answers after Raft. A GET lists no alarms, and a DEACTIVATE, or an ACTIVATE of NONE, changes nothing, which is what etcd v3.7.2 answers when no alarm is active. `etcdctl endpoint health` lists alarms after its health read, so it needs this. Activating NOSPACE or CORRUPT by hand answers Unimplemented.
- **The rest of the API.** Auth, Defragment, Snapshot, HashKV and member changes stay Unimplemented; Kubernetes does not use them.
- **Backpressure.** With 64 persist batches waiting, the committer takes no new inputs. A peer connection then blocks in `Node.Deliver` once the inbox of 8192 inputs is full, and client requests wait in `Node.Do`.
- **Membership details.** MemberList reports client URLs only for the node that answers, because nodes do not tell each other their client URLs yet; `etcdctl --cluster` and clientv3's `Sync` see one endpoint. `--listen-client-urls`, `--advertise-client-urls` and `--listen-peer-urls` take one URL each, where etcd takes lists; a list is refused with an error.

## Open for the architect

- How the committer prepares responses before commit: which node executes a batch, and when, so that the prepared revisions and results match the committed order.
- The hash index, fuzzy checkpoints, compression, and the batch byte cap.

## Expected numbers

Hypotheses from [#32](https://github.com/djosh34/tigerstore/issues/32), for a GitHub runner with one pinned core per replica and one for the load generator:

- At 1 KiB, about 90k writes/s with the lean generator (the shared disk caps near 98k/s), and about 30k/s with the stock etcd client. etcd measured 27k/s ([#26](https://github.com/djosh34/tigerstore/issues/26)).
- At 10 KiB, about 11k writes/s, or about 20k/s if compression reaches 2x.
- Besides throughput, the benchmarks report server CPU microseconds per operation per node.
