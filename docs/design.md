# tigerstore design

tigerstore is a drop-in etcd replacement for Kubernetes. It serves the etcd v3 API that kube-apiserver uses, reaches consensus with go.etcd.io/raft, and stores data in its own storage engine, designed from what one CPU core can do.

This file is the current design. It starts from the merged starting design ([#32](https://github.com/djosh34/tigerstore/issues/32)), the merged starting test design ([#33](https://github.com/djosh34/tigerstore/issues/33)) and the owner design directions ([#53](https://github.com/djosh34/tigerstore/issues/53)). The architect changes it with evidence ([#37](https://github.com/djosh34/tigerstore/issues/37)), through a pull request, and records each large change in a "Design change" comment on the outcome issue. All numbers are hypotheses until measured.

## Status

Built so far: the Go module, CI with lint, build and test, and the storage pieces of one node: the MVCC index (`internal/mvcc`), the Raft log, checkpoints and their roots on disk (`internal/wal`), the real disk adapter (`internal/osfs`), the simulated disk (`internal/simfs`), the committer (`internal/core`), the deterministic simulator (`internal/sim`), the determinism lint (`internal/lint`), and the real node: its driver (`internal/node`), the peer transport (`internal/peer`), the etcd gRPC server on its own HTTP/2 code (`internal/server`) and the `tigerstore` command. The real-process chaos job (`chaos/proxy`, `cmd/chaos`) runs the cluster under a fault proxy and signals. The section "What is built" describes them. Everything else is the design that the next pull requests build.

## Fixed by the owner

These never change:

- The etcd v3 API as kube-apiserver uses it, with client TLS and client certificates.
- Consensus with go.etcd.io/raft.
- Go, one executable per node, 3 nodes in one region.
- Encrypted node-to-node traffic.
- Linearizable reads and writes.
- An acked write and its value bytes survive the loss of one node.
- Tests and benchmarks run on free GitHub runners. The red team does chaos only, no security work.

Goals, in order: the most objects, the highest write throughput, then latency equal to or lower than etcd.

## Core

- One committer goroutine per node owns all state: the Raft `RawNode`, revisions, the index, leases and watch matching. Nothing else touches that state, so the core takes no locks.
- Helper goroutines do the work around it: client TLS, HTTP/2 framing, protobuf decode and encode, peer encryption and framing, and disk I/O. They hand the committer prepared batches. The committer only batches, applies and releases, and never blocks on I/O.
- Raft is go.etcd.io/raft v3.7.0 `RawNode` with `AsyncStorageWrites`, `CheckQuorum`, `PreVote` and `ReadOnlySafe`. With async storage the leader still cannot apply and ack through a stall of its own disk, because `RawNode` does not apply entries that are not stable locally. With async storage, Raft also sends a candidate's vote requests before its own new term and vote are durable. The candidate can then win on the other two votes, lose its term in a failed write, restart in the old term and win the same term again with a different log; the simulator found two different entries at one index this way. So the core holds every message to a peer while an append that changes the term or the vote is on its way to disk (`TestVoteRequestsWaitForTheTerm`). Entries still go out before the leader's own copy is durable, as the Raft thesis (10.2.1) allows.
- Many RPCs are packed into one Raft entry. Each RPC keeps its own revision.
- Every node terminates client TLS and gRPC. The etcd client balances round robin, and kube-apiserver opens one client per resource, so two thirds of requests land on followers. Followers forward packed proposals to the leader and serve reads with one batched ReadIndex per core turn.
- Lease expiry is a replicated mutation.

### Responses prepared before commit

While a batch is being replicated and synced, its responses and watch events are prepared. The committer fixes the results and revisions, and helper goroutines encode the bytes. When the batch commits, the committer releases them at once. Nothing is released before commit. If the entries are lost in a leader change, the prepared bytes are dropped. Replicas only report the log index they have durably accepted, as Raft followers already do.

### Batching

Batching is self-clocked: the committer proposes whatever arrived while the previous local append was in flight, capped by bytes, with no timer. The core does this itself: once two local appends that carry the leader's batches are on their way to disk (`ownDepth`), new writes wait until the older one is durable, and the next `Process` then sends all of them as one entry. With two, the next append is already queued when a sync ends, so the disk does not stand idle while the leader proposes again and the followers receive it; with one, all three nodes wrote in lock-step and left the shared disk idle about 14% of the time ([#134](https://github.com/djosh34/tigerstore/issues/134)). Appends of proposals that followers forwarded, and appends with only a hard state, such as a moved commit index, hold nothing, so forwarded traffic cannot starve local writes and a single client never waits for an extra fsync. Every write counts its size plus its framing in the entry toward the byte cap (`MaxBatchBytes`, 4 MiB), which sends a full entry early, so even empty requests cannot pile up without limit. A write that timed out while it waited is dropped, not proposed later. Followers forward at once. Heartbeats, votes, ReadIndex, replies and watch events never wait. On the disk side, the driver writes every queued append job with one write and syncs it on a goroutine of its own while it writes the next, so the byte cap bounds one entry, not one disk group. The `tigerstore` process runs with at least two Go processors, even when pinned to one CPU or started with `GOMAXPROCS=1`: an fsync blocks in a system call that can keep its processor until the runtime takes it back, which is not reliably fast, and with only one, the goroutines that take in requests, send to peers and release replies all wait for the disk. The [batch256 pre-work](https://github.com/djosh34/tigerstore/issues/47#issuecomment-6137116710) measured 1.2 writes per leader fsync at 256 clients with one processor, and 53 with two on the same CPU (29,657 Put/s against 5,297). The committer is still one goroutine. The analysis below is the starting point. The benchmarks in outcome 4 replace its symbols with measured values.

Symbols:

- `λ` is the arrival rate of writes at the leader, in operations per second.
- `t_a` is the time for one local append, including the fsync.
- `RTT` is the round trip between nodes. Single region means 1 to 10 ms ([#29](https://github.com/djosh34/tigerstore/issues/29)).
- `c_b` is the fixed core time per batch (Raft bookkeeping, syscalls, one fsync submission). `c_op` is the core time per operation.

How batch size follows load:

- One batch holds what arrived during the previous append, so the batch size is about `λ · t_a`.
- At low load this is one operation. No operation waits for a timer, so one client sees no added latency.
- As load rises, batches grow. The fixed cost per batch is shared, so the core time per operation falls to `c_op + c_b / (λ · t_a)`.
- When the core saturates, queues grow, batches grow, and the per-operation cost falls further. The system settles near `1 / c_op` operations per second instead of collapsing.
- The byte cap bounds the size of one entry. Several entries can share one fsync, because the driver writes every queued append at once.

How batch size follows node-to-node latency:

- The leader does not wait for a batch to commit before it proposes the next one. Replication is pipelined, so `RTT` does not change the batch size.
- `RTT` sets how many batches are in flight: about `RTT / t_a`. The bytes in flight are `λ · RTT · value size`. At 50k writes/s, 10 ms and 10 KiB that is about 5 MB per follower.
- The peer window is bounded by bytes (16 MiB or more), not by entry count, so 10 ms between nodes does not throttle throughput.
- Followers forward what arrived in one core turn and do not wait for the previous forward to be acked.

Write latency for one client is the client round trip, plus at most one batch of queueing, plus the commit path:

- A request that lands on the leader commits after about `max(t_a, RTT + t_a on a follower)`, so about `RTT + t_a`.
- A request that lands on a follower is forwarded to the leader, replicated, and the follower learns the commit afterwards. That is about `2 · RTT + t_a`. Two thirds of requests take this path.

At 1 to 10 ms between nodes, one-client write latency is therefore about 2.3 to 20 ms, dominated by `RTT`.

The batch byte cap and the peer window size are open for measurement.

## Node-to-node transport

Decided in the [design change on #47](https://github.com/djosh34/tigerstore/issues/47): node-to-node traffic is framed TLS 1.3 over TCP. There is one connection per directed peer pair. Length-prefixed frames carry packed Raft messages, with no gRPC or protobuf framing between nodes. The transport sits behind a small interface, so the tournament in #50 and #52 can try others.

Evidence: a loopback experiment where TLS won every batched case and raw AES-GCM over UDP led only at 1 KiB with batch 1, by 8%, within noise; an Astra second opinion agreed. Both measured loopback with one outstanding batch. They pick a default, not batch sizes or in-flight windows.

Rules that come with it:

- Per peer, frame bytes and queued bytes are capped. Control messages (heartbeats, votes, ReadIndex) go between data frames. The peer writers are not the committer.
- A stalled connection hits a write deadline, is dropped and is reported to Raft as unreachable. It never blocks the committer.
- Snapshots stream in bounded chunks to temporary storage and install only when complete and validated, through the durable install path. A separate snapshot connection is allowed if control traffic still starves.
- The codec keeps every Raft field, including the ReadIndex context and snapshot membership. A socket write is never a durable acknowledgement.

Versions, decided in [#119](https://github.com/djosh34/tigerstore/issues/119) from the findings on [#107](https://github.com/djosh34/tigerstore/issues/107): each binary speaks a range of peer protocol versions. Both ends offer them in TLS ALPN as `tigerstore-peer/<version>`, highest first, so ALPN lands on the highest version both speak, and disjoint ranges fail the TLS handshake. After the handshake, the dialer writes a 12-byte preface: the magic `TS`, its lowest and highest version, and its Raft ID as 8 bytes, big-endian. The acceptor replies with 1 byte, the highest shared version, which must be the one ALPN chose, or 0 followed by a close. Version 1 is today's framing. The unversioned protocol from before it is not supported, so moving to version 1 takes one restart of the whole cluster. A release that raises its highest version keeps its lowest version at or below the previous release's highest, so nodes can be upgraded one at a time. Both ends log a failed handshake with their own range, at most once a minute per peer, which the acceptor names by its host. The tigerstore formats inside Raft entries are versioned separately, by a cluster version.

## Storage and recovery

- The Raft log is the value store. The full command and value go in the log, written once per node. There is no bbolt and no second copy.
- Values are stored in wire format, so reads and watch events are a short header encode plus a memcpy from the log.
- Truncation of a replaced Raft suffix is persisted before any later ack. The index never points at replaced bytes.
- Recovery starts from consistent checkpoints plus ordered replay of the log. Fuzzy checkpoints are not proven correct for CAS replay and stay an experiment.
- Segment cleaning runs only below the compaction revision. It copies live data, syncs it, installs and syncs a new recovery root, and only then deletes the old segment. It keeps everything that outstanding roots, replay and readers need.
- The index is one arena B+tree with live subtree counts. A key-to-slot hash next to it is an experiment, judged by total bytes per key and core time.
- Compression is an experiment, judged by the ratio on a real Kubernetes dump, the CPU cost and the read latency.

### What is built

**MVCC index.** `internal/mvcc` is the key index of one node. A Google B-tree maps each key to all its versions, oldest first. A version holds the mod revision (main and sub), create revision, version, lease and the position of its value. A tombstone is a version with version 0. Range, Put, DeleteRange and Txn follow etcd v3.7.2 rule by rule, including the quirks: a request that changes nothing keeps the revision, Count ignores the revision filters, the limit goes into the scan only with the default order, compares and checks read the state before the transaction, reads inside a transaction see its earlier writes, and nested transaction responses carry an empty header. The validation that etcd does before a request enters the log (empty key, sort options, too many operations, duplicate keys across nested transactions) is `mvcc.Check*`, and errors are etcd's own `rpctypes` values. After each write, `Store.Changes` lists the changed keys, and `Change.Event` builds the watch event with or without the previous value. `Store.Hash` hashes the whole state so that the simulator can compare replicas.

`Store.Compact(C)` follows etcd: a revision at or below the last compaction is `ErrCompacted`, one above the current revision is `ErrFutureRev`, and the revision does not change. Per key it keeps the newest version at or below C and everything after; a tombstone from before C goes, with the key if nothing is left, and a tombstone at C stays so that a watch from C still gets that delete. Reads below C then fail with `ErrCompacted`, reads at C work. Compact walks every key on the committer: 30 ms at 1M keys with two versions each, so about 0.3 s at 10M keys, once per Kubernetes compaction (every 5 minutes by default). Compact goes through Raft as its own entry kind; physical compaction is the same, since it happens at once.

The index holds no values. Each version names its value by its Raft position (`mvcc.Ref`): the index of the entry that wrote it, the offset and length in the entry's data, and a CRC-32C of the bytes. The position is the same on every node, so `Store.Hash` covers it and replicas still compare. The apply step reads a put in place (`core.ParsePut`, protowire, no `proto.Unmarshal`) and notes where its value starts in the entry. Every other write (transactions, deletes, compactions and lease writes) is decoded with `core.DecodeAlias`, which follows `proto.Unmarshal` rule by rule but makes bytes fields slices of the input instead of copies; the decoder of a transaction notes where the value of each of its puts starts. Transactions and deletes have decoders written out per message; the rest go through protoreflect (`core.UnmarshalAlias`). A key is copied once, when the key is created, so the index keeps no entry alive.

Every value read goes through `mvcc.Values` and checks the length and the checksum: a range, a previous value of a put or delete, a compare on the value, a watch event. Bytes that do not match, such as damaged ones or ones read from the wrong place, are `mvcc.ErrBadValue`; the node stops instead of answering with them. The core's `Values` reads the value from its entry in Raft's in-memory log. A watch event copies its values, since a watcher can hold it for long; a response holds a slice of the entry until it is sent.

The B-tree stands in for the arena B+tree with live subtree counts. Count walks every key in the range, which took 61 ms at 1M keys in the [10M-key experiment](https://github.com/djosh34/tigerstore/issues/47); the B+tree with subtree counts replaces it.

**Raft log on disk.** `internal/wal` is the only durable copy of the data. The log is a sequence of segment files of 64 MiB. Each segment starts with a header of a magic string, the format version (2), its sequence number and the crc that its first record chains from. A record is `u32 length | u32 crc | u8 type | payload`, with four types: an entry (term, index, entry type, data), a hard state (term, vote, commit), a root (the index and term of a checkpoint, whether a snapshot reset the log there, keeping the entries up to a given index, and the numbers of the packs that cleaning made) and a value (the value of an entry this node does not hold, by entry index and offset, which a snapshot brought). The crc is CRC-32C over the segment's sequence number, the type and the payload, seeded with the crc of the record before it, so a stale or misplaced record does not verify, nor one that an earlier segment left in a reused file. Format 1 left out the sequence number; `wal.Open` still reads such segments and appends to a newest one in its format, and new segments are format 2. Every segment starts with a copy of the newest hard state and root, so the latest term and vote, and the root, survive when older segments go.

An entry record replaces every entry at or after its index. A truncated Raft suffix and its replacement therefore reach the disk in the same write and the same fsync, before any later acknowledgement.

`WAL.Append` only encodes into a buffer. `WAL.Flush` writes it with one write, and `WAL.Sync` writes it and syncs the newest segment, so whoever calls them decides the group commit. The node driver drains every queued append, writes it with `Flush`, and syncs the segment (`WAL.Segment`) on a sync goroutine while it writes the next group; one sync covers every group written before it started, and only `Sync` starts a new segment, once the groups in flight are synced (see Real node). A group whose jobs only move the commit index is written and not synced (`PersistJob.MustSync`), as etcd syncs only for entries, a new term or vote, or a snapshot: after a crash the node relearns its commit from the leader, and the responses such a job carries wait for every job before it, which earlier groups synced. A failed fsync is never retried; the node stops.

A new segment gets its header written and synced before its directory entry is synced and before any record goes in. So after a crash, a segment either has its full header or holds nothing else but stale bytes of a reused file. A removed segment becomes a spare (`spare-<n>`) instead of being deleted, up to `MaxSpares` (4), or an eighth of the disk budget; a new segment takes the oldest spare, writes its header over the old one and syncs it, then renames it and syncs the directory. From three quarters of the budget on, the node keeps no spares, and its disk goroutine, which starts segments, removes those on disk; they come back below half the budget. They hold nothing, and at NOSPACE a cleaning pass copies values that are nearly all live, so the spares its removals made held the files above the budget ([#181](https://github.com/djosh34/tigerstore/issues/181)). The log writes at its own offset (`pwrite`, no `O_APPEND`), and the disk adapter syncs with `fdatasync`, so a sync into a reused file allocates no blocks and changes no size, and on ext4 commits nothing to the journal: growing segments cost about 25 KiB of journal per sync, 5.4% of the bytes of a 1 KiB Put ([#134](https://github.com/djosh34/tigerstore/issues/134)). A segment that stops changing ends with its last record: rotation first cuts a reused file to it and syncs.

Recovery (`wal.Open`) first checks that the segment names are consecutive, then reads the segments in order, one in memory at a time, and keeps only where each entry and value record is: per run of entries, the segment, the offset of each record and the crc it chains from. `WAL.Entry` and `WAL.Value` read an entry or a value back by that map with `ReadAt`, and `Entry` checks the record's crc. In the newest segment, a record that does not verify starts a torn tail, which also holds whatever a reused file had after the new records. If the next record does not verify either, chained from the bad record's stored crc or from its computed one, the write was never synced and never acknowledged, so recovery truncates the tail and syncs. A newest segment that holds no more than a damaged header is removed. Everything else is `wal.ErrCorrupt`, and the node refuses to start without changing any file:

- a damaged record in an older segment;
- a damaged record (body, type or stored crc) followed by a record that verifies;
- a damaged header with records after it, a file name that does not match its header, or a gap in the segment sequence or crc chain;
- an entry that leaves a gap, a log without a root that does not start at index 1, or a gap between the root's index and the entries after it;
- a commit index past the last entry.

It also removes the checkpoint files that the newest root does not name: a checkpoint that a crash cut short, or an older one.

The second rule can also fence a node after a crash in which the disk wrote a later sector of the last write but not an earlier one. Refusing to start is the safe answer there: cutting the tail could roll back a synced vote.

Known limits: damage to a record's length field misframes everything after it and looks like a torn tail, and so does damage to the last synced record. A disk that lies about fsync can lose a synced tail the same way. Recovery cuts the log silently in these cases; they are outside the guarantee until records carry redundant headers.

`WAL.RemoveBelow(mark)` removes the oldest segments whose every entry and value is below `mark`, never the current segment or the one before it, and then syncs the directory; segments go only from the front, so the rest stay consecutive. `RemoveCheckpoints(keep)` removes the checkpoint files below `keep`; newer ones may still be being written.

Cleaning writes packs: files `pack-<n>` of value records, each with its Raft position (entry index and offset in the entry's data), framed and chained like a segment's records from crc 0, after a header of a magic string, the format version and the pack's number, and before an end record that holds the number of values. `WAL.NewPack` creates one, and `PackWriter.Finish` writes the end record and syncs the file and the directory. `WAL.InstallPacks` buffers a root that names the packs with the new one and without those it replaces; reads find its values at once. Once that root is synced, `WAL.RemoveCleaned` removes the oldest segments up to a given one, never the newest two with records, and the replaced packs. `wal.Open` reads the packs the newest root names, checks every record of them, and removes the others, which a crash left behind; a named pack that is missing or does not verify is `ErrCorrupt`. A value is read from a segment if one holds it, else from the newest pack that does.

The WAL does no I/O of its own. It goes through `wal.FS`, a directory with List, Create, Open, Rename, Remove and SyncDir, and files with ReadAll, ReadAt, Write (append), WriteAt, Truncate and Sync (fdatasync in `osfs`). It takes no locks: the node driver holds one lock around the appends and the reads, not around the fsync. `internal/osfs` implements it on the local file system. `internal/simfs` implements it in memory for the simulator.

**Simulated disk.** `simfs.Disk` keeps volatile and durable state per file and per directory. Write, WriteAt and Truncate change the volatile content, and the disk keeps the writes since the last Sync in order; Sync makes them durable. Create, Rename and Remove change the volatile directory; SyncDir makes it durable. `Crash` keeps the durable state plus a random prefix of the bytes of each file's unsynced writes, in the order they were made, and one time in four turns the last kept bytes into garbage, like a torn sector. `Erase` empties the disk for the erase-one-disk checks. A `Fault` hook runs before every operation and can fail it, which is where ENOSPC, EIO and stalled fsyncs come in. A sync that fails with EIO leaves zeros on the disk where its unsynced bytes were, while reads still see them, and a later sync does not write them, as Linux does after a writeback error.

The WAL crash test runs 500 seeds of random appends, suffix replacements and crashes, including crashes between the write and the fsync of one sync, and repeated crashes at the first writing operations of recovery (truncate and sync of a torn tail). A separate test crashes at each of the six writing steps of replacing a damaged header-only newest segment (remove, directory sync, and the create, write and syncs of the new segment). After each crash, recovery must return the synced log plus a prefix of the unsynced records. The test fails if recovery skips the torn-tail truncation or the crc check. A second crash test of 500 seeds also names roots and removes the segments below them, so that new segments reuse their files, and crashes in the middle of a sync and of the start of a new segment as well; without the sequence number in the crc, it finds stale records of a reused file taken for damage before valid ones. Separate tests damage the body, type and stored crc of a record in the middle of the newest segment and the header of the newest segment, and remove a middle segment, also right before an empty newest one; each must give `ErrCorrupt` and leave the files alone.

`osfs.New` creates the data directory and its missing parents, and on every start syncs the directory and every ancestor up to the root, so a setup that crashed halfway is finished by the next start.

**Design E: values in the log, a window in memory, checkpoints.** Decided on [#117](https://github.com/djosh34/tigerstore/issues/117) after the prototypes on [#133](https://github.com/djosh34/tigerstore/issues/133); it replaces the checkpoint design of [#111](https://github.com/djosh34/tigerstore/issues/111), which copied every value into each checkpoint.

- **Values stay where Raft wrote them.** The index names each value by its Raft position and checksum (see the MVCC index). Every node holds the same entries at the same indexes, so the index, and every checkpoint of it, is the same on every node.
- **A window of entries in memory.** Raft's in-memory log (`core.storage`, a `raft.MemoryStorage`) holds the applied entries of the last `WindowBytes` (64 MiB) and those not applied yet. On the leader the window grows up to `WindowMaxBytes` (128 MiB) while a follower still needs older entries. Applied entries leave memory by an eighth of the window at a time, whether or not a checkpoint holds them: the log on disk still has them. A value whose entry left memory is read from the log (`core.Log.Value`), never on the committer (see cold reads below). Every value read is a copy, from memory too, since a response or a watch event can wait behind a slow client long after its entry left memory. Entries not applied yet, those on their way to disk included, are bounded by `UnappliedBytes` (64 MiB): writes wait in the queue while it is full, and Raft's limits on uncommitted entries and on bytes in flight to a follower come from it. `TestWindowBound` writes 1 GiB through three in-memory nodes and checks after every step, also while the leader gets no acknowledgements and while a disk holds back its writes, that no node holds more entry bytes than the window maximum, the budget for unapplied entries and one entry.
- **Checkpoints.** A checkpoint is the replicated state at one applied index: the index with every version and the Raft position of its value, the revisions, and the leases with their stamps; never a value. Its file `ckpt-<index>` is a header (magic, the format version (5; this build reads 3 through 5), the index and its term, the members with the version each supports and the run that announced it, the removed member IDs, the cluster version, the revision, the compaction revision, the lease stamps, the base, the leases, the alarms, auth: whether it is on, its revision, the users and the roles, and etcd's cluster version with the downgrade info), the keys in order, and a CRC-32C trailer. Every node cuts one after applying the entry at which the entry bytes applied since the last one pass `CheckpointBytes` (256 MiB) and `CheckpointRatio` (64) times the base, the size of the newest checkpoint finished when the last one was cut, which the header records. Every node knows that size however far its own copy got, so all nodes cut at the same index and, from the log alone, write the same bytes; a copy still running at the next cut is finished then. A checkpoint writes the whole index again, every version included, so the ratio keeps its bytes to about 1/64 of the log's while the index does not grow much between cuts. With 16, Put at max in the bench, which never compacts, wrote 4.4% more bytes per write than `main` before E on the shared disk and its p99 was 11% higher; with 64 it wrote 2.7% more and its throughput and p99 were within the noise ([#143](https://github.com/djosh34/tigerstore/issues/143)). A restart replays about `max(CheckpointBytes, 64 × base)` of log, plus what was applied while the next checkpoint was being written and its root synced. The committer freezes the index at that revision and copies it in parts of `CheckpointChunk` (32 KiB), one part per `CopyCheckpoint`; the node driver calls it every millisecond while a copy runs and the writer has taken the last part. While the copy runs, compaction leaves versions in place and the copy leaves out versions after the frozen revision, so the parts add up to the index at that revision however they are paced. The driver writes the parts (`Effects.Checkpoint`) to the file on a goroutine of its own, syncs it and the directory, and reports `CheckpointWritten`. The core then asks for a root (`PersistJob.Root`), which goes into the log in order with the appends. Once the root is synced, the driver removes the segments below the lowest entry that a value of the checkpoint is in, and below the checkpoint's index, and the older checkpoint files. While a follower may be fetching a snapshot from the leader, the leader's roots remove nothing, and the driver skips the removal of any root while a fetch from it is under way; the next root removes it all. A follower that needs one snapshot after another keeps the leader from removing anything until it catches up. A checkpoint counts only once a synced root names it.
- **Cluster version.** The data of a Raft entry is in an entry format. Format 1 is the batch of writes (`internal/core/codec.go`). Every later format starts with a 0 byte and its number, which a format 1 batch never does, and format 2 is format 1 with that header. Each node announces through Raft the newest version it supports (`core.MaxVersion`, 3), again every election timeout until the announcement applies and, while a newer format waits, until the node has confirmed the current epoch. Once every voter has announced support for a newer format, every voter must confirm the same announcement epoch through Raft before the cluster version rises. A change of support, run or membership starts an epoch at its log index and invalidates all confirmations. Legacy logs and checkpoints use epoch zero until the first confirmation-aware announcement, so replay from either source agrees. A stopped voter cannot confirm an upgrade announced after it stopped. When it restarts on an older binary, it announces its lower support instead. The epoch and partial confirmations are replicated state in checkpoint format 5. Once all confirmations commit, the version never goes down. A rollback after that commitment is refused, even if the restarting node had not yet observed activation. An announcement carries the number of its node's run: the node driver keeps it in the file `run` of the log's directory and raises it, durably, at each start. The state keeps the run of each voter's announcement, in the checkpoint header too (format 4), and one from an earlier run changes nothing, whether it applies before or after the newer one, so an announcement of an earlier run that reaches the leader late cannot undo a rollback (#174). The run goes in field 2 of the `UInt32Value`, and the confirmed epoch in field 3. Entries without field 3 retain their original activation semantics when replayed. This protocol change requires all participating binaries to use confirmations; mixing it with the earlier unreleased implementation is not supported. A binary from before checkpoint format 5 cannot read the checkpoints this one writes, so it cannot be rolled back to, nor take a snapshot from it; no release has the older format. A node whose disk is erased starts again at run 1, so it should rejoin as a new member. Once a version is active, a binary that does not support it stops when it applies the announcement that made it active, and refuses to start, from the log or from a checkpoint, with `core.ErrTooOld` naming both versions ([#145](https://github.com/djosh34/tigerstore/issues/145)).
- **Restart.** `wal.Open` scans the segments and returns the newest root, the hard state and the last index; it keeps no entries in memory. `core.New` loads the checkpoint the root names and checks its trailer and that its header matches the root, then applies the committed entries after it, read one at a time from the log, and hands Raft the rest. No summary log exists. A damaged checkpoint that a root names keeps the node from starting, like a damaged log.
- **Snapshots.** A follower that needs entries the leader no longer holds in memory gets a Raft snapshot with no data: the leader's newest durable checkpoint if it is past the window's start, otherwise the window's start (`core.storage.Snapshot`). Raft hands the follower's core the snapshot in its append message; the core turns it into a persist job with an `Install`, and holds the job's responses until the state is there. The follower's driver opens a separate connection to the leader (`peer.Transport.Fetch`) and asks for the entries after its applied index up to the snapshot's index. The leader's driver (`core.ServeSnapshot`) sends them from its segments, or, when some are gone, its newest durable checkpoint at or before the snapshot's index whose file it still has, the values it names in entries after the follower's applied index, and the entries after the checkpoint. Every item of the stream carries a CRC-32C. The follower (`core.ReceiveSnapshot`) checks each item, that the entries follow each other up to the snapshot's index and term, that each value matches its checksum, and the checkpoint's trailer and header, writes it all to its own log (entries, value records, the checkpoint file), and only then writes the root, which resets its log to after the checkpoint. Entries the follower already holds with the leader's term are the leader's, and it may have acknowledged them, so it skips them and the root keeps them; the first entry it lacks replaces those after it. The core then empties memory at the snapshot, loads the checkpoint if one came, applies the entries after it from the log, and steps the job's responses: the state is at Raft's snapshot, and the root names the checkpoint below it. A follower whose state a checkpoint replaced ends its watch streams; the clients watch again from where they were. The leader reports `ReportSnapshot` when a fetch from it ends, or as failed when no fetch started within `SnapshotTicks` (20 s) or the message could not be sent. A root that becomes durable after Raft sent the snapshot therefore does not keep the leader from serving the checkpoint the snapshot named, as long as that checkpoint's file is still there: the leader's roots remove nothing while a follower waits to fetch (`snapWait`), and its driver removes nothing while a fetch runs. Raft cannot take back a snapshot it handed the follower, so when the fetch fails, because the leader crashed, could not serve the snapshot any more, or sent bytes that do not check out, the follower's driver syncs what the stream wrote and starts a new core from its log, as a restart does, without exiting. Its waiting requests fail with "server stopped" and its watch streams end; the clients try again. The leader hears that the fetch failed, and Raft sends another snapshot. A failed write during an install still stops the follower, except the creation of a checkpoint file that is already there: an install queued before this one wrote it, and this one asked from an older applied index, so it ends the run for the same restart from the log.
- **Cold reads.** The committer never reads the disk. A response or a watch event whose values left memory is built at once, with every other field and each value's Raft position (`mvcc.Fill`), so a later compaction cannot change it, and waits for a `core.ValueRead`: the core hands it to its driver in `Effects.Reads`, a helper reads the values from the log and checks their checksums, and `ValuesRead` hands it back. The real node runs 16 reader goroutines; the simulator runs each read after its own random delay. Replies then go out; a watch stream's responses stay in order, so one that waits holds back those after it, progress notifications included. This covers Range, RangeStream, LIST, Put and DeleteRange with `prev_kv`, the ranges of a transaction and watch events with previous values. A transaction that compares a value on disk, or a range sorted by values on disk, needs the bytes at once: it stops before it changes anything (`mvcc.ColdError`) and runs again once they are read. For a write, ordered apply waits with it, and so do the writes after it; the committer goes on with ticks, messages and reads. While a read is under way, a root removes no segment that holds a value it needs. A read that fails, or whose bytes do not match the checksum, stops the node, as before; after a snapshot install, which can take the files away, its clients get Unavailable instead. `TestColdReadsStall` holds every value read on three nodes for 2 s and checks that no answer with such values comes early, that compare-and-swap writes, a compaction and an election go on meanwhile, and that every answer is right.
- **Garbage collection.** With the values on disk, the heap is mostly the index, and every collection scans its pointers. At Go's default `GOGC` of 100 a node under load collected every few seconds, and with each node pinned to one CPU in the bench, each collection held up requests: mixed-k8s p99 at half of etcd's rate went from about 5 ms to 17 ms. `main` before E kept every entry in the heap, which put its next collection far off. `cmd/tigerstore` therefore runs with `GOGC` 400 unless `GOGC` is set; the memory budget still caps the heap.
- **Memory budget and value cache.** Each node has a memory budget: `--memory-budget-bytes`, else `GOMEMLIMIT`, else the memory limit of its cgroup (v2, the lowest `memory.max` of its cgroup and those above it), else the host's memory. `cmd/tigerstore` sets the Go memory limit to the budget less an eighth (`node.GoMemory`), so the collector works harder as the heap nears it. The eighth is for what a cgroup charges the node besides Go's memory: the log segments it maps, the page cache of its writes and kernel memory. With Go's limit at the whole budget, a node in a cgroup of that size got killed by the cgroup under a burst of writes (#202). When GOMEMLIMIT gives the budget, it stays the Go limit, as the user set it. A quarter of the Go limit stays free, so the collector does not run all the time there, and `node.BufferBytes` (64 MiB, a guess until the memory-limited runs measure it) goes to the buffers of clients, peers, the log and checkpoints, responses waiting for slow clients, and reads under way. The rest (`core.Config.MemoryBytes`) is shared by the index, the entries in memory and the value cache (`core.cache`): an LRU of the newest values of keys written or read lately, after their entries left memory. When applied entries leave the window, the newest value of each key they wrote moves into the cache (`mvcc.Store.Leaving`); a value read from the log that is still its key's newest goes in too. A put or a delete drops the value it replaces (`mvcc.Store.Replaced`), and a snapshot that loads a checkpoint empties the cache. After every turn the cache's limit is set to `MemoryBytes` less the estimated index bytes (`mvcc.Store.Bytes`) and the entry bytes in memory, and the least recently used values go until it fits, so the cache shrinks as the index grows. A value is named by its Raft position, which no later write changes, so a cached value is never stale, and it is checked against its checksum on every read like any other. `/metrics` reports the cache's bytes, its current limit, its hits and the values read from the log (`tigerstore_cache_*`). `bench/cluster.sh` and `scripts/local-cluster.sh` give each of the three nodes a quarter of the host's memory, or the bench's `GOMEMLIMIT`. The simulator runs without the cache.

Unary KV.Range answers also count against `MemoryBytes`. The core reserves space before reading their values, including candidate values for VALUE sorting, and reduces the cache first. The reservation allows for value copies, protobuf encoding, compression and per-key metadata. Concurrent answers share the node's budget across connections. A read waits if other answers occupy the space it needs, within its normal request timeout. With no other answer out, it goes even when the index and the entries leave it less room, so that a full index does not refuse every read. Only an answer larger than `MemoryBytes` gets `ResourceExhausted`; the client can request a smaller page. Without a sort on values, only the values of the page count, not those of keys the limit drops. The transport releases the reservation after the last socket write or after dropping the answer. Resetting a stream does not release memory still referenced by a socket writer. `/metrics` exposes the reservation as `tigerstore_range_reply_bytes`. This accounting applies to unary Range, not to values returned by Txn, Watch or RangeStream.

- **Cleaning.** With a disk budget (`--disk-budget-bytes`, `node.Config.DiskBudget`; none by default), a cleaner goroutine of the node driver keeps the log's files, segments, packs and checkpoints, within it. The oldest checkpoint whose file the node keeps names every value that recovery and a snapshot fetch still need from the segments at or below its index. The cleaner opens that file while it holds the log's lock, so a newer root cannot take it away, reads it twice off the committer, and copies the values it names out of such segments, oldest first, and out of packs, into a new pack that keeps their Raft positions, at most 64 MiB of values per pass. A segment goes when at most half of its bytes are live, or whatever its live share once space is short; a pack when at most half of it is live. Every copied value is checked against its checksum. The disk goroutine then installs and syncs a root that names the pack, and only then does the cleaner remove the files the pack replaced; while a snapshot fetch is under way, it waits. The index never changes. The cleaner measures the files every 20 ms, and the disk goroutines add what they write in between. From half the budget on it cleans at most half of the time, from three quarters on without pause, and then writes (puts, lease grants and transactions that are not read-only) wait before the node takes them, up to 10 ms near the budget. At the budget the core answers them with etcd's NOSPACE error, `etcdserver: mvcc: database space exceeded`, as etcd does while its NOSPACE alarm is active; reads, deletes and compactions go on. Each node answers from its own disk. A leader past its budget also refuses the writes that followers forward: in the entry it proposes, each becomes a record that answers its client with NOSPACE when it applies. A node past its budget also raises its NOSPACE alarm through the log, like etcd past its quota, so every member refuses those writes, before it proposes them and when they apply, and a follower past its budget gets no more appends of them ([#170](https://github.com/djosh34/tigerstore/issues/170)). Once its files are below the budget and its store under the quota, the node clears its own alarm, at most one change every lease retry interval; an operator can also disarm it, as in etcd. A member refuses those writes before proposing them as long as it has not applied the disarm, also after another member answered it; etcd refuses them only when they apply. While a value read or a snapshot fetch is under way, a root's removal of the files it made obsolete waits, and runs when the read or fetch ends ([#165](https://github.com/djosh34/tigerstore/issues/165)). The budget is where NOSPACE starts, not a cap: past it, writes still queued get NOSPACE too, but the files still grow by the entries already proposed (up to `UnappliedBytes`, 64 MiB), one pack (up to 64 MiB of values) and one checkpoint, so the disk needs that much room above it. Cleaning never removes the newest two segments or a checkpoint the node keeps, so a budget below two segments (128 MiB), those checkpoints and the live values stays at NOSPACE. A removal that waits for a snapshot fetch is lost when the run starts again, after a failed fetch or a restart; later passes copy those files into a new pack again, which is correct but wasted work. A value the oldest kept checkpoint names stays, and at NOSPACE little new log comes in for the size rule to cut the next checkpoint. So a compaction that applies while a NOSPACE alarm is active cuts a checkpoint at its index, on every member alike, as the alarm is replicated state; cleaning then drops what it freed, and deletes and a compaction lift NOSPACE without a restart ([#167](https://github.com/djosh34/tigerstore/issues/167)). `TestNoSpace` deletes every key at NOSPACE and compacts, and a put must go through within 20 s. `/metrics` reports the index, window and map bytes (`tigerstore_index_bytes`, `tigerstore_window_bytes`, `tigerstore_map_bytes`), the size of the files and the budget, and the bytes cleaning wrote. `TestCleaningCycles` overwrites 50 keys of 1 KiB and compacts, 200 times, on a 1 MiB budget: the disk stays within it, the map stays between 2 and 6 KB, and every value, also of 50 keys written once at the start, reads back after a restart. Without a budget, the cleaner runs only for Maintenance.Defragment (see below).

Not built yet, for the next outcome: compression.

**Committer.** `internal/core` is one node's committer as an event and effect machine. Its inputs are method calls: `Submit` (a client request), `Step` (a Raft message from a peer), `Tick` (one clock tick) and `Persisted` (a disk write finished). `Process` runs Raft until it has nothing left to do and returns `Effects`: persist jobs, messages to send and replies. The driver calls these from one goroutine and carries out the effects. In the real node that driver is the committer goroutine; in the simulator it is the event loop.

- **Writes.** `Submit` validates the request with `mvcc.Check*` and then, like etcd, limits the size of the marshaled `InternalRaftRequest` that wraps a write to 1.5 MiB. Its header holds a request ID; the core sizes it with a 10-byte varint ID. That is etcd v3.7.2's strictest case (a member ID with bit 15 set, as in the difftest), which this matches to the byte (#62); for other member IDs etcd accepts one or more bytes more. With client certificates required (`--client-cert-auth`), etcd also puts the certificate's common name and the auth revision (1 on a store that never changed auth) into that header as `username` and `auth_revision` fields, even with auth disabled, so a client's writes have the size of those two encoded fields less room (#99), except for requests with `grpcgateway-accept` metadata, for which etcd ignores the certificate. The server computes that size once per connection from the leaf of the first verified chain (`core.Caller`). Reads do not go through Raft and have only gRPC's limit. Then it queues the write. `Process` packs the queued writes into entries of at most `MaxBatchBytes` (4 MiB), so a batch holds whatever arrived since the last call. While Raft knows no leader the node proposes nothing: as in etcd, whose raft.Node takes no proposal without a leader, writes wait for one, up to their deadline, instead of failing at once with "no leader" (#105). There is no timer. Each write in the entry carries its origin node, the origin's boot ID and the request ID (`core/codec.go`). Every write a client sends keeps its wire form in the entry: the connection reader decodes it with the generated decoder only to check it, `Submit` checks the decoded request, and `Process` copies the body into the entry instead of marshaling the request again. A Put goes further and is never decoded into a struct: the connection reader checks it with `core.ParsePut`, `Submit` validates and sizes it from its fields, and `Process` copies the client's bytes into the entry, the one encode of the batch. The entry keeps the client's encoding, so a write that repeats a field logs more bytes than etcd's re-encoding would, up to the 2 MiB receive limit; the size limit counts the decoded request. Its reply is the revision, term and previous key, which the connection writer encodes as a PutResponse without building a protobuf message. Raft is `RawNode` with `AsyncStorageWrites`, so the local append comes out as a `PersistJob`. The driver appends every queued job to the WAL, syncs once and reports each job with `Persisted`. The core then appends the entries to its in-memory Raft log and steps the responses. When an entry commits, the core applies it to the index on the spot and answers the requests whose origin and boot match its own. A boot ID is random per process start, so an entry proposed before a restart never answers a request made after it. Within one boot, the driver never reuses a request ID, because a write that timed out can still commit later. A write that the index rejects at apply time (an unknown lease, a missing key for `ignore_value`, a range at a compacted or future revision) is answered with etcd's error on every replica and changes nothing.
- **Reads.** Linearizable reads and read-only transactions queue up, and each `Process` turns the queue into one `ReadIndex` request. The reads run against the index once the applied index reaches the read index. Raft drops a `ReadIndex` without a word when a follower knows no leader, when a message is lost, and on every term change. So a batch without an index asks again every 3 ticks and at once when a new leader appears, and batches are served in any order. Serializable reads run at once against local state. The read context carries the boot ID too.
- **Timeouts.** Every request has a deadline in ticks (`RequestTicks`, 7 s). After it, the request fails with etcd's "request timed out", which is ambiguous: it may still commit. Without a leader nothing is proposed and writes wait (see Writes); a write whose deadline passes before it was proposed leaves the queue and fails with `DeadlineExceeded`, "context deadline exceeded", as etcd v3.7.2 answers a write whose context ends while it waits for a leader. The core does not see the client's own deadline or a cancel: a write whose client gave up can still be proposed later, an outcome its client's answer already allowed. A proposal that Raft drops while a leader is known, during a leadership transfer, fails at once with "no leader".
- **Membership.** It follows etcd v3.7.2 (`core/members.go`). A new cluster's log starts with one Raft configuration change per member of `--initial-cluster` (`RawNode.Bootstrap`), so every node, one that joins later included, rebuilds the members from the log or a checkpoint. The members (Raft ID, peer URLs, learner or not, and the name and client URLs a member publishes once it starts) and the removed IDs are replicated state in checkpoints. MemberAdd, MemberRemove, MemberUpdate and MemberPromote propose a configuration change whose context carries the request's origin and the member; it is checked when it applies, as etcd's `ValidateConfigurationChange` checks it (a removed ID never comes back, an ID or a peer URL is taken once, at most `--max-learners` learners), and when it no longer fits, Raft hears of a change of nobody and the client gets etcd's error. Before proposing, `--strict-reconfig-check` refuses, as etcd's `mayAddMember` and `mayRemoveMember` do, adding a voter or removing one that would leave fewer started voters than a quorum, and any add, or the removal of a voter that is not down, after which the members this node has been connected to for etcd's 5 s would not be a quorum (`ErrUnhealthy`). A new member gets the next ID the cluster never had. The storage keeps the Raft configuration from each change's index on, so a Raft snapshot names the configuration of its own index. A learner serves only Status, serializable ranges and snapshots, and answers everything else with `ErrGRPCNotSupportedForLearner`. MemberPromote needs the learner to have 90% of the leader's log, which only the leader knows: another node hands it to the leader over a peer call. A removed node stops with "the member has been permanently removed from the cluster", when it applies its removal or when a peer tells it so in the handshake. Member changes are entries of cluster version 3 and wait for it. The leader queues both local and forwarded configuration proposals until Raft acknowledges applying the preceding change. A follower may answer before the leader has applied that change; sending the next proposal directly to Raft would turn it into an empty entry and leave its request to time out (#210). A new leader first applies an entry of its current term, which clears Raft's conservative barrier for its inherited log.
- **Fatal errors stop the node.** A failed disk write, an entry that does not decode, a value that does not match its checksum, or a snapshot whose checkpoint or entries do not apply stops the core. (A snapshot that cannot be fetched makes the driver start a new core from its log instead; see Snapshots.) A leader whose own append has been on its way to disk for two election timeouts does not stop: it asks Raft to hand leadership to the follower with the longest log among those it heard from in the last election timeout, and asks again each tick until one takes over, as Raft gives a transfer up after an election timeout (#156). A stalled leader still heartbeats, so the others would never replace it, and once its entries not yet on its disk fill their budget it holds up the writes of the whole cluster. As a follower it holds up only its own clients, which wait until its disk is back, as they would on any follower with a stalled disk. Stopping it instead turned a disk that is slow on two nodes at once into an outage, and a slow write in a test cluster at 10 ms ticks into a stopped node. A leader whose own entries have waited three election timeouts to commit stops (`ErrCommitStalled`): a gray leader whose heartbeats get through but whose appends do not passes Raft's quorum check while nothing commits. Three is above the disk watchdog's two, so a stalled disk is usually handed off first; an entry that already waited before the stall can reach three first. `Process` then returns the error, and every waiting request fails with "server stopped". Neither applies to a one-node cluster: with no other voter to lead in its place, the node waits for its disk. Raft's own logger is silenced but still panics on broken invariants. Tests can lower the three (`CommitStallElections`); the stress job sets it to one, at a real node's 100 ms ticks, to catch shorter stalls while values near the request limit are written from every node. To show where the time went, a node logs a log write that took longer than a tick, each change of leader or term, and, at most once a second per peer, messages that waited longer than 100 ms in their peer queue.
- **Responses are not prepared before commit yet.** Every node computes the results when it applies an entry, and the origin node replies right away. The apply step is a function of the index and the entry alone, so the leader can later run it ahead on a copy and hold the encoded replies until commit (see Seams).

**Leases.** The replicated state is `core.State`: the index and the leases, and `State.Apply` runs one committed write against both. The rules follow etcd v3.7.2 and the semantics pre-work on #47:

- **Grant.** A grant with ID 0 gets an ID from the node that takes the request, before it is proposed, so every replica applies the same one; it is positive and differs per node and boot. TTLs below 1.5 election timeouts, rounded up (2 s by default), become that; above 9,000,000,000 s is `too large lease TTL`; a taken ID is `lease already exists`; negative IDs are allowed. A grant does not move the revision.
- **Attach and detach.** After every write, the keys it changed leave the lease of their old version and join the lease of their new one, so a put without a lease or a delete detaches a key, and `ignore_lease` keeps it.
- **Revoke.** The lease's keys, in order, go in one transaction, so they share one new revision and watchers see all the deletes in it; a lease without keys moves no revision. A missing lease, lease 0 included, is `requested lease not found`.
- **Expiry.** Only the leader keeps expiry times, in ticks of its own clock. When a lease expires, the leader proposes an expiry like a write, again every 10 ticks until it applies, so every replica deletes the keys at the same revision. The expiry carries the lease's stamp, in a `LeaseCheckpoint` (etcd's only message with a lease ID and a number), and applies only if the stamp is still current. Every grant and keepalive takes a new stamp from one counter. So a keepalive that commits before the expiry keeps the lease, one that commits after it answers TTL 0, and a later grant of the same ID is a new lease that the old expiry cannot touch, the same on every replica. The leader arms a lease for its TTL plus one tick, since the current tick may be nearly over, so a lease never expires early. A node that becomes leader gives every lease its full TTL again; a leader change can make a lease live longer, never shorter. With etcd's LeaseCheckpoint feature gate (`core.Config.LeaseCheckpointTicks`, every 5 minutes as in etcd v3.7.2, which has no flag for it), the leader writes a lease's remaining TTL, in whole seconds rounded up, through Raft (`LeaseCheckpointRequest`, entry kind 15) 5 minutes after it armed the lease and again after each checkpoint, while more than 5 minutes are left and less than the TTL; the remaining TTL is replicated state, in checkpoints, a new leader arms the lease for it instead of the full TTL, and a keepalive ends it, as in etcd, whose checkpoints persist from cluster version 3.6 on whatever LeaseCheckpointPersist says.
- **Keepalive** is a Raft entry too: it is a write without a revision, and on the leader it renews the expiry when it applies. A missing lease answers TTL 0. **TimeToLive** and **Leases** are linearizable reads; TimeToLive reports the leader's remaining whole seconds, rounded down as in etcd, the granted TTL on other nodes, and TTL -1 for a missing lease.
- **Differences from etcd.** etcd renews a lease on the leader without Raft, so a keepalive here costs a WAL entry, in a log that nothing cleans yet. etcd forwards TimeToLive to the leader, so `etcdctl lease timetolive` counts down on any endpoint; here a follower reports the granted TTL. Kubernetes uses neither.

The gRPC Lease service serves all five, with KeepAlive as a stream of one request at a time.

**Watches.** Watchers live in the core (`core/watch.go`) and follow etcd v3.7.2's watch server. A driver hands the core the requests of a watch stream (`Node.Watch`) and closes the stream with `CloseWatchStream`; the responses come back as `Effects.Watch`. On create, watch ID 0 picks the next free ID of the stream, starting at 0. A taken ID, an empty range (an end at or below the key, other than `\x00`) and a negative start revision get etcd's created-and-canceled response with watch ID -1. A start revision below the compaction revision gets a response with `CompactRevision` that cancels the watch. A watcher that starts in the past catches up from `Store.History` at once, inside the call, in responses of at most 1,000 revisions that never split a revision, as etcd does. Then it is synced: after each applied write, the core matches the write's changes against every watcher and queues the events, and at the end of `Process` it sends each watcher one response with all of them and the current revision as header. `prev_kv` comes from the key's version list, so a create has no previous value and every update and delete has one. The NOPUT and NODELETE filters work. A watcher created with `fragment` gets a response of 2 MiB or more (etcd's `--max-request-bytes` and 512 KiB of gRPC overhead) with more than one event in parts below that size, each of at least one event and all but the last marked `fragment`, as etcd's `sendFragments` splits them; the core marks such a response and the server splits it once its values are read (`server/watch.go`). Progress follows etcd's `progressIfSync`: every watcher is always synced, so a progress request is answered at once with watch ID -1, except on a stream with no watchers or with a watcher that asked to start above the current revision. clientv3 resumes from a progress revision plus one, so a progress answer below a watcher's start would make it go back. Watchers that ask for progress notifications get one every `ProgressTicks` (etcd's 10 minutes; `--watch-progress-notify-interval` sets it, as in etcd) unless they got events since the last one or start above the current revision. A watch from below the compaction revision C gets the created response, then a cancel with `compact_revision` C, an empty reason and header revision 0, as in etcd. A watch with `prev_kv` from C itself is canceled the same way: the versions before C are gone, and etcd would send its first events without previous values, which Kubernetes rejects. The difftest allows exactly this answer for those steps.

The node driver keeps a queue of 4096 responses, and at most 64 MiB of them, per stream. A stream whose client falls further behind is closed with `Unavailable`, the code after which clientv3 resumes each watcher from its next revision. The gRPC handler honours etcd's `hasleader` metadata: it refuses to open without a leader, and like etcd's `monitorLeader` it closes the stream after three checks one election timeout (1 s) apart find no leader.

Matching walks every watcher for every change. An interval index over the watchers' ranges replaces that when Kubernetes' hundreds of watchers show up in profiles. Responses are never split into fragments.

**Deterministic simulator.** `internal/sim` runs the real `core.Node`, `wal.WAL` and `mvcc.Store` of all 3 nodes in one process. Everything is an event in one queue ordered by virtual time and sequence number:

- Ticks every 100 ms per node, with a random phase.
- A disk write writes at once and finishes its fsync 50 µs to 1 ms later, or 20 to 100 ms later for 2% of writes. A crash in between leaves a torn tail.
- Directed links are ordered streams: a message never overtakes an earlier one on the same link. Messages are marshalled at the sender and unmarshalled at the receiver, so nothing is shared between nodes. The simulator numbers the messages on each link and fails the run if one arrives after a later one. During the faults, delays come from each link's own profile (below), and 10% of messages take up to 5 ms; after healing, delays are 20 to 220 µs. A link that goes down, and every link of a node that crashes, drops what it carries.
- Faults in the first 20 virtual seconds: a node crash about every 3 s with a restart up to 2 s later, and a change of the set of up links about every 2 s, and at most 6 s apart. Half of those link changes heal every link; the other half pick a random one of the 64 directed-link masks.
- Disk faults in the same 20 s: about every 6 s, and once more in every run, the next write or sync of a node fails, with EIO on a sync, EIO on a write, or a short write with ENOSPC. The node stops at once, never retries the fsync, and restarts from its disk. A fault that hits recovery, which can truncate and sync, is a failed boot, and the node tries again later. About every 8 s a node's disk stalls for 1.5 to 4 s; healing ends a stall, and a write held back by it finishes then. At one crash in two, until it happens once, the crashed node gets a misdirected write: 16 to 64 synced bytes copied from another file or offset over a sealed segment. The simulator uses 8 KiB segments, so most of the log is sealed, and leaves the newest segment alone, where damage can look like a torn tail. The node must refuse to start (`wal.ErrCorrupt`) and stays fenced for the rest of the run, as if its disk awaited replacement. Lost writes are a lying disk and outside the guarantee. The extra fault becomes due in the first 5 s and fails the write of the next append with entries on any node; a write fault fires at once, while a sync can wait out a stall. If no node appends until healing, it stays due and fires on the first append after healing; the liveness rule then starts once the node is back (the restart bound plus 4 s), and the clients keep going until 3 s after that. The same holds for a node a watchdog stops after healing, if it stops within 4 s of healing; a later stop counts against the rule. `TestSeeds` requires a disk fault in every run, and a fenced node and a stalled leader that handed over somewhere in every set of 64 seeds or more.
- Network and process faults: every change of the link set also draws new delays for each directed link (a base of 20 µs to 2 ms plus jitter up to the base), so delays switch and the two directions of a pair differ; about every 4 s one directed link stalls for 0.5 to 2 s, including what is already on it, and then delivers everything in order, like a stalled TCP stream; about every 6 s a process pauses for 0.2 to 2 s and then handles everything at once, in order (a second pause can only make it longer, a crash ends it, and the simulator fails the run if a paused node does any work, closing a watch stream included); about every 8 s one directed link goes half-open: the sender still sees its connection, but what is on the link and what it sends vanish until, after 0.5 to 5 s (the peer write timeout), its connection fails and Raft hears that the peer is unreachable. Stalls and pauses end by healing at the latest, and healing ends half-open links. Each of these faults also comes once at a random time in every run, retried until it takes effect, and `TestSeeds` requires every one of them in every run, and a link at least 10 times slower than its other direction somewhere in every set of 64 seeds or more. Clocks run up to 5% fast or slow per node, and about every 6 s a node's clock jumps forward by up to 3 ticks, at most once per node in 10 s. That is the declared clock envelope: lease expiry is checked against it.
- Gray faults in the same 20 s: about every 8 s a gray period of 2 to 6 s starts. In half of them the leader is gray for the whole period; in the rest one node at a time is gray, and every 1 to 3 s the gray node may change to another one. Raft heartbeats, votes and responses to and from a gray node get through, but appends do not, and in half the cases its fsyncs take 0.5 to 3 s. One more gray period in every run lasts, past healing if need be, until its gray node has lost an append, and moves on from a node that is down. A gray fsync already in flight can finish after healing; the liveness rule below counts from it. A gray client opens a stream with 10 watches on the key range, a quarter of them from revision 1, and reconnects to a random node every 50 to 300 ms until healing; at the end every node must hold only the watchers of open streams. The core has no queue toward a client, so a client that reads slowly costs it nothing; the node driver's bounded watch queue (`ErrWatchTooSlow`) is left to the real-process tests. Restarts of a node with a log crash again inside `wal.Open`, at the first to sixth writing disk operation and every one after it: every restart until one such crash happened, then one in three. The repair of a torn tail writes twice and that of a damaged newest header six times, so until the first crash the cut is at one of the first two. Until then, the next node to write entries also crashes between the write and its sync, which leaves a torn tail to repair. `TestSeeds` requires a gray node that lost an append and gray-client streams in every run, a crash in recovery in every set of 64 seeds or more, and a gray leader stopped by the commit watchdog in every set of 2000 seeds or more: 22 of seeds 1 to 2000 had one, so a set of 64 or 400 misses it too often (#183).
- Six clients, each with one call in flight, on 8 keys, also compacting about once in 100 calls a little behind the newest revision they saw, and granting leases of 2 to 4 s, putting keys with the newest one, keeping it alive and revoking leases now and then: puts and deletes with and without previous values, range deletes of up to 3 keys, compare-and-swap transactions with a failure-branch range, transactions that put two keys, linearizable and serializable reads, prefix reads with limits, and reads at past revisions. A client gives up after 3 s.
- Four watch clients: a prefix and a single key with `prev_kv`, a sub-range with `prev_kv` and progress notifications, and an open-ended range with progress notifications. Each starts from revision 1 or from now. When its node crashes, and on purpose about every 3 s, it closes its stream and opens a new one on a random node up to 2 s later, from the revision after its last event or progress notification, as clientv3 does. The simulator sends progress notifications every 2 s instead of 10 minutes, and every response must carry the watch ID of the stream's watcher.
- Design E with tiny limits, so every seed uses it: a window of 16 bytes of applied entries (32 while a follower lags), a checkpoint after 256 bytes of entries and twice the base, copied 32 bytes at a time, 8 KiB segments, and a snapshot given up after 1 s without a fetch. A snapshot is fetched from the leader's simulated disk when the follower's install job starts; it fails if the leader is down, paused or cut off. A failed fetch syncs the follower's disk and starts a new core on it at once, as the real node does. Faults of E in the same 20 s: once per run a follower is kept down for 3 to 5 s, so it falls behind the window; the leader serving the first snapshot stream of a run crashes partway through it; the first stream that arrives whole, and one in four after it, arrives with a damaged byte; half the fetches start 0.2 to 2 s late, so the leader may make a newer checkpoint durable first, or give up on the snapshot and remove what it needs (`TestSlowFetch` requires both across its seeds); once per run a node crashes at a step of a checkpoint (after a part is written, after the file's sync, after the directory's sync, after the root), of a removal, or of an install (after each item it writes); and once per run, as the run's damage if it has none yet, a bit of the newest value of a key flips on the disk of a running node, in a sealed segment or with a durable entry after it in the newest one, so it never looks like a torn tail. The node must stop when it reads it and refuse its log on the next start.
- Then 10 healthy seconds with the clients still running, and 10 quiet seconds, so the last leases expire and their watch events arrive.

The seed drives a PCG generator for every choice. Raft draws its election timeouts from `crypto/rand`, which the test makes deterministic with `cryptotest.SetGlobalRandom` seeded from the same seed. Each event, each message, each reply and each restart goes into an FNV-64a trace hash. `TestSeeds` runs every seed twice and fails if the hashes differ.

The simulator keeps its own record of the committed history, apart from what the nodes retain: every entry as the first node applied it, and the hash of the state after it (`core.Config.Record` makes the core report both). Each time a node applies an entry, or loads a checkpoint at an index, its entry and its state's hash must match the record at that index. Each time a node writes a checkpoint, its bytes must match what the other nodes wrote at that index. A node must never hold entries in memory past its applied index plus one.

After a run, the simulator checks the following. Its own checks do not validate compaction errors or compaction cancels; those calls and watch parts are checked only by #56's `check.Revisions` and `check.Watches`. Because the cluster compacts, the checks read history from a model: the recorded committed log replayed into a fresh store without compactions, which must end at the cluster's revision with its keys and values, read through a node's own value reads.

- every node is up, has applied to the same index, and has the same state hash as the record;
- every successful read returns exactly what the final index holds at the revision the read saw, including reads inside transactions;
- every acknowledged put is in the final index at its revision, its previous value is the final index's value at the revision before, and an acknowledged delete removed a key that existed and left none behind;
- every compare-and-swap held at the revision before its write, or failed at the revision it saw;
- no call sees a revision older than one that another call returned before it started, every write gets a newer revision than that, and no two writes share a revision;
- every write is in the committed log at most once, every acknowledged write is in it, and no write that failed for certain is (each written value belongs to one call);
- every logical watch delivered exactly the history of its range from its start revision, to the final revision for the current one and up to its last event for one that a compaction canceled (the client then starts a new logical watch from now, as Kubernetes does), in order, without duplicates, with previous values where asked, and no event above its response's header revision;
- every lease still granted at the end was granted or kept alive within the last 8 s, the largest TTL plus a leader change, so leases do expire; and no lease expired, on any node, before its TTL ran out since its last successful grant or renewal, less what the clock envelope allows (5% of the TTL and one jump of 3 ticks);
- erasing each node's disk in turn, at a checkpoint during the faults, right after the first root a node syncs and right after its first segment removal (#163), and at the end, and cold-starting the other two alone from their synced bytes applies at least every entry that any node had applied by the checkpoint, and every entry and state the two reach up to there, from their checkpoints or by applying, is the one in the run's record. An acknowledged call was applied before it was answered, so this covers every acknowledged write, delete and lease change with its revision: the guarantee that an acknowledged write survives the loss of one node;
- every call that starts 4 s or more after healing, or after the last gray fsync that outlasted healing, gets a definite answer, except calls to a fenced node, which a real client would leave for another endpoint, and to a node whose disk is stalled at the call (success, or an answer such as a compacted revision), and at least 50 do. Four seconds is four election timeouts: a node restarted at healing may need two to elect, and a node that comes out of the faults with a higher term and a shorter log can then make the new leader step down once, which costs another election (seed 721530481). A gray fsync in flight at healing can finish up to 3 s after it. Until then its node's term and vote changes, and the peer messages that wait for them, are held, so a higher term can reach the new leader late and cost one more election (seed 745672193, before writes waited for a leader: an fsync started at 19,892 ms finished at 22,701 ms, and the delayed rejection of a pre-vote made the leader step down). So the rule starts 4 s after healing or after the last such fsync, whichever is later, and the clients run for at least 3 s under it. The guaranteed gray period's append drop does not move it: votes and heartbeats pass a gray node, and that drop can come only after an election, which the rule must bound. With a node fenced, the rule starts 2 s later: every election then needs both remaining nodes, and when one has the longer log and the other the higher term, they reject each other's pre-votes until the first learns the term from a rejection.

These checks catch a stale read (linearizable reads served without `ReadIndex`), a WAL that skips fsync, a transaction compare that is off by one, a proposal applied twice, watch events without previous values, a watcher that skips history, a watcher that gets only the first change of a write, a watcher that starts one revision late, a matcher that ignores the range end, and a progress notification 5 revisions ahead; each was planted by hand and failed. `core/watch_test.go` covers create rules, filters, cancel, progress, and catch-up of 1,100 revisions of three keys, which fails if a response is cut by event count instead of by revision. The checkers of package `check` ([#56](https://github.com/djosh34/tigerstore/pull/56)) are the independent oracle. `Result.Checkable` converts a run into their `history.History`: every call, the committed log, the watches with every response, and the final revision as the watch target. `TestSeeds` runs the durability, revision and watch checkers and the witness checker in both modes on every seed. Porcupine gets its own short runs in `TestLinearizable`, where the witness checker in both modes must agree with it (5 virtual seconds of faults with 4 clients, then 8 s of healing, without leases), because it searches too long on full runs: one 7,263-call history of seed 9 timed out after a minute, and with 6 clients one 1,481-call history took 12 s. With 4 clients, 200 seeds each checked in under a second. Leases are left out of these runs: every granted lease becomes an ambiguous expiry op that may apply at any time, and with leases two of three short runs timed out. The full runs keep leases, and the durability, revision and watch checkers see them. In the history, every granted lease gets such an expiry op from its own client, called with the grant, and keepalives are left out, since the format has none and they change no key. An ambiguous write that the committed log does not hold is left out. One that the log holds once, from a call whose request no other call has, gets an `Effect`: the revision the log gives it, and the time the next write after it in the log was acknowledged, by which it took effect. Porcupine then applies it without forking it into took effect or not, as etcd's robustness tests do with persisted requests. Seed 1320469923, with 8 such writes in its first 7.3 s, timed out after a minute without them and checks in 5 ms with them. `TestAllLinkMasks` holds each of the 64 sets of directed links for 3 s with no other fault, then heals for 8 s, and runs every checker, Porcupine included; each must be installed once. `TestSwitchingLinks` switches to a random set about every 300 ms for 10 s. `TestEachFaultTakesEffect` runs each network, process, gray and recovery fault alone and requires that it happened. `TestGrayClient` runs the gray client alone: every other call must succeed in under a second. `TestGrayLeaderIsReplaced` makes the leader gray for good with no other fault: it must stop within three election timeouts plus two ticks, and every call to the other two nodes that starts three election timeouts after that must succeed in under a second. `TestGrayFsyncOutlastsHealing` makes the leader gray with slow fsyncs 1.5 s before healing on five seeds, so that a gray fsync outlasts healing, replays each run, runs the independent checkers, and requires definite answers from two election timeouts after that fsync ends, before the general recovery allowance ends (it replaced a test pinned to one seed's schedule, #164). `TestGrayFsyncRecoveryBound` checks that only a gray fsync that outlasts healing moves the bound, that a healthy fsync and a crashed node's canceled fsync do not, and that clients still run long enough to check it; `TestGrayAppendRecoveryBound` checks that the gray period's append drop after healing does not move it. `TestDiskFaultAfterHealing` cuts every link before the first election, so the guaranteed disk fault fires after healing, and the run must still pass. `TestHalfOpenLink` makes the link from the leader to a follower half-open for 5 s: every call to the leader and the other follower must succeed in under a second, and the cut-off follower must serve again 2 s after its connection fails. `TestStalledLeaderIsReplaced` stalls the leader's disk for good with no other fault: the leader must stop within two election timeouts of the stall plus two ticks (one for an append already queued, one for the next client write), and every call to a healthy node 10 election timeouts later must succeed. A planted stale read fails both Porcupine and the revision checker on seeds 1 to 4 of the full runs and 1 to 3 of the short runs, with the simulator's own checks bypassed. The converter refuses anything the format cannot hold (a compare over a range, nested transactions, sort options, revision filters, `ignore_value`, `ignore_lease`, an unknown event type) instead of dropping it.

**Real node.** `internal/node` is the driver of `core.Node` outside the simulator. One committer goroutine owns the core. It waits for an input (a client request, a peer message, an unreachable report), a finished disk write or a 100 ms tick, takes up to 4096 more inputs that are already queued, calls `Process` once, and carries out the effects. One disk goroutine takes every queued persist job, appends them to the WAL, writes them and hands the group to a sync goroutine. The sync goroutine syncs the segment, records each group's durable roots and removals, and reports it to the committer before returning it to the disk goroutine. A later blocked write cannot hold back an earlier durable append's response. That is the group commit: while one fsync runs, the next group is written, and one fsync covers every group written before it started, so the disk always has the next group to take. Up to four groups wait for their sync; a full segment, a snapshot install or a cleaning root first waits for all of them. After a failed sync no later group is reported. The committer never blocks on the disk: persist batches wait in a list that it hands to the disk goroutine as space frees up. With 64 batches waiting, it stops taking new inputs but keeps ticking and taking finished writes, so a slow disk slows down clients and peers instead of stopping the node. gRPC handlers call `Node.Do(ctx, op)`, which queues the request with a reply channel and waits for the reply or the context. A request whose client gave up still runs; its reply is dropped. A failed write or sync stops the node. A third goroutine writes checkpoint parts, which the committer hands it the same way, and reports each written checkpoint back through the inbox. With a disk budget, one more goroutine cleans (see Cleaning). A persist job with a snapshot makes the disk goroutine fetch it from the leader and write it to the log before the rest of the job, syncing every 16 MiB; a job with a root makes it remove the old segments and checkpoints once the root is synced. `Node.Serve` answers a follower's snapshot fetch from the WAL and the durable checkpoints whose files are still on disk, which the disk goroutine records when a root or an install is synced; while a fetch is under way, it removes nothing. When a fetch fails, the disk goroutine syncs what it wrote and ends the run; `Run` fails the waiting requests, ends the watch streams, reopens the WAL and starts a new core from it, and runs again with the same inbox. The WAL's map of entries is behind one lock that the appends and the reads take, the readers' value reads included, but not the fsync. Sixteen reader goroutines run the core's value reads (`Effects.Reads`), which wait in a list on the committer while all are busy, and hand them back on their own channel.

**Peer transport.** `internal/peer` implements the decided transport. `peer.Transport` has three methods, `Send`, `Fetch` and `Close`, so other transports can replace it. The TCP implementation keeps one outbound TLS 1.3 connection per peer, with the peer CA verified on both ends. After the version handshake (see Node-to-node transport), the dialer sends frames of a 4-byte length and a `raftpb.Message` in its protobuf encoding, so every Raft field survives. The decision said no gRPC or protobuf between nodes; the architect accepted protobuf frames for now ([clarification on #47](https://github.com/djosh34/tigerstore/issues/47)), since raft v3.7's message types are protobuf and the writer goroutines, not the committer, do the encoding. A hand-written codec is an outcome-4 experiment. Each peer has a writer goroutine with two queues: appends and snapshots, empty appends included, go on the data queue so they stay in order, and so do proposals that a follower forwards with whole write batches; everything else (heartbeats, votes, ReadIndex and their responses) goes on the control queue, which the writer empties first. Each queue holds at most 64 MiB of entries and contexts. A message over the 64 MiB frame limit is dropped before it is sent, received frames are capped at 64 MiB, and each write has a 5 s deadline. `Send` never blocks: a full queue or a broken connection drops the message and reports the peer unreachable to Raft, which falls back to probing. The writer marshals messages, not the committer. A `MsgSnap` carries no data. A follower fetches what it lacks on a connection of its own: its preface carries its ID with the top bit set, then it sends the first and last index it needs, and reads the snapshot stream until the leader closes it (`Transport.Fetch`, `Config.Serve`); each read and each write has the 5 s deadline.

**gRPC server.** `internal/server` serves the client port with its own HTTP/2 and gRPC code on x/net's Framer and HPACK, decided in the [design change on #50](https://github.com/djosh34/tigerstore/issues/50). grpc-go's server is not used; clients and tests still use grpc-go's client. KV.RangeStream is served as etcd v3.7.2 serves it: chunks of keys, the first of 10 and each next one doubled below half of 1.5 MiB or halved above twice that, every chunk read at the revision of the first, and the header (with the store's revision at the first read), count and more on the last chunk only; custom sort orders and revision filters answer Unimplemented, as in etcd. The Auth service is described under Auth below. Compression is grpc-go's, which etcd v3.7.2 runs with gzip registered (`server/compress.go`): a call with `grpc-encoding: gzip` may send compressed messages and gets every response message that is not empty compressed, under `grpc-encoding: gzip`; another encoding than gzip or identity fails the call with grpc-go's Unimplemented "Decompressor is not installed" before its handler runs, and a compressed message without an encoding with grpc-go's Internal error. Every other method of etcd's services answers Unimplemented with grpc-go's message. `/metrics` is described under Metrics below. For versioning ([#145](https://github.com/djosh34/tigerstore/issues/145)) it adds `tigerstore_cluster_version_min` and `_max`, the cluster versions the binary supports, `tigerstore_cluster_version`, the one the member has applied, `tigerstore_peer_protocol_min_version` and `_max_version`, the peer protocol versions it speaks, and `tigerstore_peer_protocol_version` by peer (its Raft ID in hex) and direction (`out` for the connection this node dialed, `in` for the one the peer dialed), 0 while there is none. Status reports version 3.7.2, storage version 3.7.0 (the target during a downgrade, see Downgrade), the downgrade info, the leader, the term, the commit and applied indexes, the 2 GiB default quota, "etcdserver: no leader" in Errors without a leader, and the estimated log size as the database size, never 0 because etcdctl divides by it.

**Metrics.** `/metrics` answers as etcd v3.7.2's does: the families of etcd's server, its `grpc_server_*` metrics, the Go and process collectors, `promhttp`'s own counters, etcd's names, help texts, labels, buckets and content type (`text/plain; version=0.0.4; charset=utf-8; escaping=underscores`). **Tracing.** `--enable-distributed-tracing` and its address, service name, instance ID and sampling rate flags do what etcd's do: spans go in batches over OTLP gRPC without TLS, and a trace is sampled as its parent was or, at its root, the rate in a million times. The server feeds otelgrpc's server stats handler, the one etcd installs in grpc-go, the events grpc-go would (the tag with the call's `traceparent`, `tracestate` and `baggage` metadata, the local address and the end with the status), so every gRPC call gets etcd's server span. Inside it come the spans etcd's server starts, with their names and attributes: `range`, `put`, `delete_range`, `txn`, `compact`, `lease_grant` and `lease_revoke` for the unary calls the node runs, `range_streaming` and `lease_renew` per keepalive. A unary call that fails with one of the errors etcd's gRPC layer answers before its server runs (an empty key, a duplicate key in a transaction and the like) leaves its inner span unended, so it is never exported, as etcd starts none. etcd's `watch` span is never ended, so never exported, and tigerstore has none.

Each connection has a reader goroutine, which decodes frames and copies each request message once out of the Framer into a buffer of its own size, and a writer goroutine, which is the only one that writes and which keeps to the client's flow-control windows. A streaming call runs in a goroutine from its first headers. Status and MemberList run in a goroutine of their own.

The unary calls that the node runs (KV, Compact and the unary Lease calls) take the whole-batch path. The reader decodes each complete request and hands all of them to the committer with one `Node.SubmitBatch` call. It does this when reading the next frame could wait for the client, because that frame is not buffered whole or starts a header block that continues in later frames, or at 256 requests or 4 MiB. There is no timer. The committer submits each request to the core, and after each `Process` it hands every connection all of its replies of that turn with one `Complete` call. `Complete` only pushes them onto a lock-free list, adds their size (`proto.Size`, or a fixed estimate) to the connection's count of waiting replies, and wakes the writer, which encodes the replies. So such a call costs no goroutine, context, channel or inbox send of its own. Each call holds its request bytes plus 512 from when the reader hands it over until the node answers, and its reply bytes from then until the reply is sent or the client resets the call. A call whose deadline passed before its batch goes out is not handed over. Once a connection's calls and its waiting replies hold more than 64 MiB, its receive window is not credited back, so the client stops sending while the reader still reads pings, resets and window updates. If the node stops, every call it held fails with "server stopped" after the replies it already gave are sent. Response header and trailer blocks are HPACK literals that are never indexed, each after a dynamic table size update to 0, so they are built once and are valid whatever table size the client set. The server follows grpc-go and etcd where clients can see it:

- The receive limit is etcd's 1.5 MiB request limit plus 512 KiB, with grpc-go's ResourceExhausted "received message larger than max". Compressed messages are refused with Unimplemented.
- `grpc-timeout` ends the call with DeadlineExceeded when it passes, whether or not the request is complete or the handler started; `0n` has passed already. etcd's `hasleader` metadata fails a call without a leader with "etcdserver: no leader", unary calls included, and ends a Watch or LeaseKeepAlive stream after three checks one second apart find no leader, as etcd's interceptors do.
- A stream the client resets is canceled, and a reply that comes after the reset is dropped. When the server ends a stream that the client has not ended, it sends RST_STREAM with NO_ERROR, as grpc-go does.
- A streaming call may queue 4 MiB of replies for the writer; a watch stream that cannot send waits there, and the node closes it when it falls 4096 responses behind (see Watches), which also ends the waiting send. A stream that fails drops the replies its client has not taken, so its status goes out at once. A unary reply is queued whole, as grpc-go does, so a client that stops granting flow-control window keeps its unary replies in memory until it goes away. At most 10,000 control frames (ping and settings acknowledgements, resets, window updates) wait for the writer; past that the connection closes. A write that blocks for 20 s closes the connection.
- The reader decodes header blocks with one HPACK decoder per connection, which fills the request's fields without allocating once they are in the dynamic table. It keeps x/net's checks: a string over 1 MiB, or a fragment that could decode past 1 MiB for the block, ends the connection; so does a fragment after a broken field and a HEADERS frame that cannot be parsed. A malformed block (a field name that is not a lowercase token, an invalid value, a pseudo-field after a regular one, an unknown or repeated pseudo-field, a block over 1 MiB) on a new stream, or as trailers on an open one, resets that stream with PROTOCOL_ERROR; on any other stream ID it ends the connection.
- The writer sends at most one frame of each ready stream per turn, so one large reply does not hold up the others.
- A second end of a stream (DATA or trailers after END_STREAM) resets it with STREAM_CLOSED, and data past a stream's receive window resets it with FLOW_CONTROL_ERROR. Padding is credited back at once. HEAD gets headers without a body.
- The receive window per stream is 4 MiB, or the largest request (`--max-request-bytes` plus etcd's 512 KiB overhead) with its 5-byte gRPC prefix if that is more, and 16 MiB per connection, credited back as data arrives. A connection allows `--max-concurrent-streams` concurrent streams, etcd's 2^32 - 1 by default.
- Stop sends GOAWAY, lets streams in flight finish for one second, and then closes every connection.

The same port answers `GET /version`, `GET /health`, `GET /readyz` and `GET /livez`, over HTTP/2 and, for a TLS client that does not offer h2, over HTTP/1.1. `/version` answers `{"etcdserver":"3.7.2","etcdcluster":"3.7.0","storage":"3.7.0"}`, which kubeadm's preflight reads; during a downgrade, the cluster and storage versions are the target's. `/health` follows etcd: without `?serializable=true` it needs a leader, then it makes a one-key keys-only read with etcd's 7 s request timeout, and it answers `{"health":"true","reason":""}`, or 503 with `RAFT NO LEADER` or `RANGE ERROR:<error>`, written as `http.Error` writes them; `health` is a JSON string. `/readyz` and `/livez` run etcd v3.7.2's named checks: `/readyz` runs `data_corruption` (no CORRUPT alarm), `serializable_read`, `linearizable_read` (the same one-key read as `/health`) and `non_learner` (the member is not a learner); `/livez` runs `serializable_read`. The root path skips the checks named in `?exclude`, ignoring names that are not checks, and each check has its own path, such as `/readyz/linearizable_read`. Success answers `ok`, after a `[+]<check> ok` line per check with `?verbose`; a failure answers 503 with those lines and `[-]<check> failed: <error>`. Any method but GET answers 405 with `Allow: GET`. etcd lists the checks of a root path in map order, which varies; tigerstore lists them in etcd's registration order. Every HTTP request goes through etcd's access controller first (`server/gateway.go`): `/v3beta/` becomes `/v3/`, a request without TLS must have a Host in `--host-whitelist`, CORS headers go on every answer for the origins of `--cors` (all by default, as in etcd), and OPTIONS answers 200. Under `/v3/` runs etcd's gRPC gateway (`--enable-grpc-gateway`, on by default): grpc-gateway's mux with etcd's marshaler options (proto field names, no unpopulated fields, unknown fields ignored), the handlers generated for etcd's services, and the websocket proxy etcd puts in front of them, so every unary call, the streams (Watch and LeaseKeepAlive as newline-separated JSON) and grpc-gateway's JSON errors are etcd's own. etcd's gateway is a gRPC client of its own client port; tigerstore's is a client of the same server through an in-process connection without a certificate, and, as in etcd, it forwards `Authorization` as the token, and with client certificates required and auth on a gateway request whose certificate has a common name is refused with 400. On HTTP/2, an HTTP request runs as soon as its headers arrive, with the stream's DATA as its body and its response written onto the stream as the handler writes it; HTTP/1.1 clients get net/http's server, as in etcd. Without TLS, the port serves HTTP/2 with prior knowledge only, which is for tests. Client TLS takes a certificate, and with `--client-cert-auth` it requires client certificates from `--trusted-ca-file`.

**Command.** `tigerstore` runs one node with etcd v3.7.2's command line, parsed by etcd's own `embed.Config` (`cmd/tigerstore/config.go`): every flag with etcd's default, the same names as `ETCD_*` environment variables for the flags not given, or a YAML `--config-file` instead of both, the deprecated and ignored flags of etcd, `--version`, `--help`, and etcd's checks of the result (`embed.Config.Validate`, then `VerifyBootstrap` or `VerifyJoinExisting` on a first start). It logs through etcd's zap logger (`--log-level`, `--log-outputs`, `--log-format`). On top come tigerstore's `--disk-budget-bytes` and `--memory-budget-bytes`, which a configuration file may set too. Every URL of `--listen-client-urls` gets a listener that serves gRPC and HTTP, or gRPC only when `--listen-client-http-urls` is set, whose listeners serve HTTP only; unix and unixs URLs listen on sockets. As in etcd, a listener without TLS hands HTTP/2 to gRPC alone, so other HTTP/2 requests get 415, and HTTP/1.1 to the HTTP endpoints; a TLS listener of gRPC alone offers only h2. Unlike etcd, one address cannot serve http and https at once. HTTP/2 connections that serve gRPC alone, where etcd runs grpc-go's own server (without TLS, or with TLS when `--listen-client-http-urls` takes HTTP), keep alive as grpc-go's server does with etcd's settings (`internal/server/keepalive.go`); a TLS address that serves gRPC and HTTP answers every ping and sends none, as net/http's HTTP/2 server does for etcd there: `--grpc-keepalive-min-time` is the least time between a client's pings while a call is open, two hours while none is, and the third ping too soon, with no HEADERS or DATA sent in between, gets GOAWAY ENHANCE_YOUR_CALM `too_many_pings`; after `--grpc-keepalive-interval` without a frame from the client the server pings it and drops it when nothing arrives within `--grpc-keepalive-timeout`. As etcd hands grpc-go a setting only when it is above 0, a 0 gives grpc-go's default (5 minutes, 2 hours, 20 seconds). `--max-request-bytes`, `--max-txn-ops`, `--max-concurrent-streams`, `--pre-vote`, `--heartbeat-interval`, `--election-timeout`, `--initial-election-tick-advance` (with etcd's wait for the peers), `--wal-dir`, `--unsafe-no-fsync`, `--memory-mlock`, `--warning-apply-duration`, `--warning-unary-request-duration`, `--socket-reuse-address` and `--socket-reuse-port` act as etcd's; `--raft-write-timeout` bounds writes to peers and `--raft-read-timeout` the reads of a peer connection's preface and of a snapshot fetch, both at least 5 s as in etcd. `--force-new-cluster` on a node with data drops the entries after its commit index and commits configuration changes that remove every other member, as etcd does (`core.Node.ForceNewCluster`). Flags for bbolt and etcd's snapshots (`--snapshot-count`, `--snapshot-catchup-entries`, `--max-snapshots`, `--max-wals`, `--backend-*`, `--compaction-batch-limit`, `--compaction-sleep-interval`) are accepted and do nothing, because tigerstore has no bbolt and cuts checkpoints by bytes, and so is `--downgrade-check-time`. `--initial-cluster` may name a member several times, once per peer URL, as in etcd; the transport dials the first. In a new cluster (`--initial-cluster-state new`), a node's Raft ID is the position of its name in `--initial-cluster`, and the cluster ID is a hash of the token and that list. A node that joins a running cluster after MemberAdd (`--initial-cluster-state existing`) asks the other nodes of `--initial-cluster` for the members over a peer call with no Raft ID, and takes the ID of the member with one of its peer URLs and the cluster ID. A node keeps both, with the members it started with, in `<data-dir>/member` from its first start on, and a restart takes them from there instead of `--initial-cluster` or discovery; the data directory defaults to `<name>.etcd`. A new cluster may also come from etcd's discovery (`cmd/tigerstore/discovery.go`). With `--discovery-endpoints` and `--discovery-token`, a node registers with etcd's v3 discovery service, etcd's own code, and takes the cluster it reports, whose members come in the order they registered, the same for every node; the cluster ID hashes the discovery token and that list. With `--discovery-srv`, etcd's lookup of the `_etcd-server-ssl._tcp` SRV records gives the members, but names the node's own entry after it and the others with numbers in the order of the answers, which differ between nodes; so tigerstore orders the members by their peer URLs, leaves their names empty until each publishes its own, and hashes the URLs alone. CI's smoke job bootstraps three nodes through v3 discovery against its cluster; the SRV ordering has a unit test, since the lookup reads the host's resolver. `--max-learners` and `--strict-reconfig-check` are etcd's. Peer URLs must be https, which etcd's default `--initial-cluster` is not, and a node needs `--peer-cert-file` and `--peer-key-file` or `--peer-auto-tls`. As in etcd v3.7.2, `--peer-cert-allowed-cn` and `--peer-cert-allowed-hostname` take comma-separated lists, and at most one of them may be set. When one is set, both ends of a peer connection also require the other node's certificate to have one of those common names, or to be valid by its SANs for one of those hostnames (`internal/peer/cert.go`). The TLS flags are etcd's too. Client connections take etcd's own TLS configuration (`transport.TLSInfo.ServerConfig`): the certificate files are read again for every handshake, `--trusted-ca-file` alone already asks clients for a certificate, `--client-cert-allowed-hostname`, `--client-crl-file`, `--cipher-suites`, `--tls-min-version` and `--tls-max-version` apply, and an https metrics URL also checks a client certificate's SANs against the client's address, as etcd's metrics listener does. The peer transport reads its certificate files for every handshake, dials with `--peer-client-cert-file` and `--peer-client-key-file` when set, refuses a dialing peer whose certificate `--peer-crl-file` revokes, and, unless `--peer-skip-client-san-verification`, one whose certificate is not valid for its address by an IP SAN or by a DNS SAN that a reverse lookup gives, all as etcd's peer listener does. It speaks TLS 1.3 alone, so `--tls-max-version TLS1.2` is refused, and `--cipher-suites`, which Go applies to TLS 1.2 only, concern clients. `tigerstore grpc-proxy start` is etcd v3.7.2's gRPC proxy, the same code, with its flags, `--namespace` among them; as in etcd, the certificate it dials the cluster with must have no CommonName, which `scripts/dev-certs.sh`'s `proxy` certificate does not. `tigerstore gateway start` is etcd's TCP gateway in the same way. The difftests `TestProxy` and `TestGateway` run the same steps through a proxy with `--namespace /ns/`, and through a gateway, in front of etcd and in front of tigerstore, and CI's smoke job puts and reads a key through each. `scripts/dev-certs.sh` and `scripts/local-cluster.sh` start a local cluster. CI's `smoke` job runs etcdctl v3.7.2 put, get, del, watch and endpoint status against it over TLS, reads `/version` and `/health`, and checks that a client without a certificate is refused. `internal/server` has a Go test that runs 3 nodes in one process over real TLS, restarts one from its disk and reads its data back.

**Benchmarks.** `cmd/loadgen` is the load generator for etcd and tigerstore alike. It speaks gRPC over raw HTTP/2 and TLS 1.3 with client certificates, with many streams per connection, fixed-size requests stamped out from prebuilt DATA frames (mixed encodes and frames each variable-size request at send time), request headers encoded per connection as grpc-go's encoder does, which adds each field to the HPACK table the first time and sends one-byte references after that, and either every stream busy or open-loop Poisson arrivals. Its workloads are Put, CAS Txn, Delete, Range, LIST, Watch and mixed Kubernetes operations on Kubernetes-shaped keys. Latency covers every request that arrived in the window, from its scheduled send time, however late it completes. A unary call succeeds only with exactly one response message, and any error, including a failed CPU sample, marks the result invalid. It reports server CPU per operation per node from `/proc` and its own CPU per operation. `bench/run.sh` runs named targets (etcd and two tigerstore builds) back to back, in reversed order on even repetitions, each on a fresh 3-node cluster with client and peer TLS. `bench/cluster.sh` pins the generator, the leader and the followers to their CPUs after the election, and `cmd/benchreport` makes the tables and refuses invalid results. The `bench` workflow, started by hand, does this on an `ubuntu-24.04-arm` runner with disk write barriers on: generator on CPU 3, leader on CPU 0, followers on CPUs 1 and 2, 5 repetitions per target. Every reported statistic has its minimum, median and maximum over those repetitions, including generator CPU in both modes. Invalid results and unequal target run counts stop the report. The put-1k and txn-1k jobs also measure the speed target of [#146](https://github.com/djosh34/tigerstore/issues/146) in the same job: `loadgen -disk` counts the device bytes written per operation from `/proc/diskstats`, `cmd/diskbench` measures the device's maximum with O_DIRECT writes and fdatasync into a file already written, and each tigerstore build runs again with all three nodes on tmpfs (`TMPFS_NODES`), its CPU reference, and with only the leader on the disk (`LEAD` moves the leadership there). `benchreport` then gives each run's share of the lower of its disk ceiling (the device's maximum over its bytes per operation) and its CPU reference. The `etcd-tool` job runs etcd's own `tools/benchmark` of v3.7.2, built from its source tag, against each store as a second view (`bench/etcdbench.sh`): put, txn-put, and linearizable and serializable range, with 1 KiB values, 100 connections and 1,000 clients, as etcd's performance documentation does.

`mixed-k8s` preloads 1,000,000 keys, then grows the live set with creates during the run. Namespaced keys have the form `/registry/<resource>/<namespace>/<name>`, across about 1,024 namespaces. Cluster-scoped resources instead use `/registry/<resource>/bench-<owner>-<group>-object-<id>`, with owned group prefixes ending in `-` rather than `/`. `internal/k8ssize/k8ssize.go` embeds the length-only histogram of a Kubernetes 1.37 cluster [measured on #50](https://github.com/djosh34/tigerstore/issues/50#issuecomment-6153233467): one row per resource and exact value size, with its object count, 416 rows over 27 resources, 6,345 objects and 9,253,583 value bytes. A value size is drawn from those rows by count, so resource shares follow object counts and sizes within a resource follow their measured counts. An update draws a new size from the same resource. This is a size model, not a copy of object content. Values use disjoint windows of random bytes from each worker's pool, as the other workloads do.

The default mix is 25% point GET, 10% namespace LIST, 40% update, 15% create and 10% delete. `-mix` takes those five percentages in that order, and `MIX` passes them through `bench/run.sh`. Create compares create revision with zero in a Txn. Update and delete compare with the key's known mod revision. Ten percent of GETs read known absent keys when any exist, so deletes are checked by Range too. LIST asks for the first 500 keys, including the full count and more flag. Each worker owns its namespaces and keys, and selection skips LIST groups with active calls and keys whose group is already LISTing. A started LIST blocks that group's mutations until it completes, without holding back arrivals for other groups. That permits exact validation of count, ordering, values and every KV revision field without a global state lock. Deletes make keys absent; creates reuse some absent keys and allocate new ones too. Watches run on every resource prefix from the revision after preload. Every event, including its previous value, matches an acknowledged mutation and is checked in revision order. Missing, duplicate or changed events fail the result.

Preload uses Txns of up to 128 puts, capped at 60 KiB and the connection's stream window, with at most eight in flight per connection and 300 Txn arrivals/s over all connections by default. `-preload-rate` changes the setup rate. Preload is not a maximum-throughput measurement. It does not raise etcd v3.7.2's default transaction limit. Preload and watch setup finish before CPU and latency measurement. Mixed opens six request connections round robin across all three endpoints, rather than only the leader. Server CPU still sums all three node processes. A rate-only mixed job first measures one maximum-throughput run per store at the same six connections and 16 streams. Its open-loop rate is half of etcd's median maximum from those calibration results (one sample by default), rounded down; `MIXED_RATE` can override it. All three stores then get five rate repetitions at that same measured load. In [run 38444109849](https://github.com/djosh34/tigerstore/actions/runs/38444109849), etcd's one max sample was 2,838.7 ops/s, so the five rate runs used `floor(2838.7/2) = 1419` arrivals/s. The baseline and candidate max samples were 12,148.8 and 12,711.8 ops/s; neither was used to choose the rate. The workflow allows 75 minutes for the extra preloads; it does not reduce the five repetitions. The other benchmarks keep max mode and rate mode at half of etcd's median maximum throughput. The default three-second warmup and ten-second measurement keep log growth small. The preload holds about 1.47 GB of value bytes per node before log and index overhead. Servers have a 3 GiB Go memory target for this workload. Targets run sequentially, with fresh data directories, so values and logs from earlier targets do not remain on the 16 GB runner. The GitHub run checks the actual fit; this is not a capacity test.

## Testing

### Deterministic simulation

- The core is an event and effect machine. Inputs are requests, cancels, peer bytes, ticks, and I/O and send completions. Outputs are disk operations, sends, replies and timers.
- Four adapters sit at the edge: disk, network, clock and randomness. Core packages may not call `time.Now`, use global randomness, make syscalls or start goroutines. A lint in CI enforces this.
- The simulator runs the real core of all 3 nodes in one process from one seed. Stock raft v3.7.0 becomes deterministic through `testing/cryptotest.SetGlobalRandom`, with one seed per process and a pinned Go version. Every PR replays seeds twice and compares trace hashes.
- Buffers are poisoned after release at every asynchronous boundary.

### Simulated faults

- A byte-level disk with volatile and stable state and directory operations: torn, lost and misdirected writes, slow, stalled and failing fsync, and ENOSPC. Disks that lie about fsync are outside the guarantee, but detectable damage must fence the node.
- TCP as ordered streams: head-of-line blocking, stalls and half-open connections. All 64 directed-link reachability masks run on every PR, plus switching between them. Short, long, switching and asymmetric delays, and one link much faster than another.
- Crashes at every persistence step, and repeated crashes during WAL recovery and snapshot install. At checkpoints, each node's disk is erased in turn and the other two cold-restart.
- Gray nodes and barely alive clients, each with a numeric liveness bound. For example, writes commit within 10 election timeouts while two nodes are healthy. A gray leader is fenced, not only asked to transfer leadership.
- Process pauses, clock skew and clock jumps.

### Checkers

- Porcupine with the ported etcd model, on isolated small histories, as the independent oracle.
- The revision-witness checker for large histories, `check.Witnessed` ([#112](https://github.com/djosh34/tigerstore/issues/112)). Every write that changes the store gets its own revision, and every response names the revision it was served at, so the revisions name the order. The checker builds it, replays it through Porcupine's model, and checks that every acked op gets its response and that the order follows real time. A pass is a linearization, whatever the revisions or the log claim. It has two modes. `FromLog` takes the order of the writes from the committed log. `FromRevisions` uses neither the log nor the Effects: an ambiguous write goes where a client saw its value, and a revision that no acked write holds is filled by a bounded search over the ambiguous mutations, with a key no client saw unchanged there. An acked op that changed nothing goes at the first state of its header revision that answers it, and a rejection the model decides at the first state within its call and return. With every past version at hand, the model also answers reads at past revisions, inside transactions too. The difftest case `txn-revisions` records etcd v3.7.2's answers for such a read, for reads at a transaction's start revision and the current one after its own write, and for failure branches that write; `TestWitnessedTxnRevisions` holds the model to them.
- A strict watch checker. The previous value is required on update and delete events of watches that ask for it, and not on creates. Kubernetes rejects a non-create event without it. Each watch must be complete up to a target revision, in order and without duplicates.
- Durability of acked and returned data, revision rules, always-on invariants and a coverage floor.
- Sequential differential tests against etcd v3.7.2 for the boundaries: compaction at R-1, R and R+1, error codes, and the maximum request size, for a Put and a Put inside a Txn with keys of 37, 39, 136 and 3,036 bytes. etcd runs there with client TLS and `--client-cert-auth`, as tigerstore does, so the certificate's name counts on both. A watch step ends on a progress notification, which both servers send only for a caught-up watch, never on a timer; only a watch that starts above the current revision, which neither server confirms, ends after 500 ms without a response.
- About 18 planted bugs behind a test-only build tag. CI fails if one is not caught within its fixed seed budget.

### Real processes

The fault proxy on every link, tc netem, SIGKILL, SIGSTOP, CPU throttling and a fault-injecting file layer. Each job checks that every requested fault was actually installed. Bugs in TLS, HTTP/2 or the Go scheduler get their regression test at the layer that reproduces them.

Built so far: the seeded fault proxy (`chaos/proxy`) on every client and peer link, SIGKILL and SIGSTOP of the leader and of a follower, and the `chaos` CI job (`cmd/chaos`), which runs the checkers of package check on every history, the witness checker in both modes among them, and fails when a requested fault was not installed or had no effect. [docs/testing.md](testing.md#real-process-chaos) describes the job and its faults. Later pieces of #49: tc netem packet faults and 1 to 10 ms between nodes, CPU throttling, the fault-injecting file layer and real ENOSPC, crashes timed inside WAL recovery, gray nodes and barely alive clients, several faults at once, and nightly campaigns.

### Budgets and regressions

The first measurement is the full harness cost per seed on `ubuntu-24.04-arm`, capped at 256 MiB per simulator worker. PR, nightly and release campaigns are sized from that. A failing seed becomes a shrunk schedule and a named scenario test that fails on the bad commit.

## Seams for later pieces

Later pieces plug in here without reshaping what exists.

- **Values point into the log.** Every write applies from its entry without copying values. Writes other than puts are still decoded into request structs on every replica. Transactions and deletes use decoders written out per message (`core.DecodeAlias`), which took 445 ns for a 1 KiB compare-and-swap where `proto.Unmarshal` took 1,021 ns and the protoreflect `UnmarshalAlias` 1,796 ns on this host; executing them without structs is the next step. LeaseKeepAlive, a stream, still goes through `Node.Do` and is marshaled into the entry. Segment cleaning has to copy live values out before it frees a segment.
- **Segment cleaning.** The real node cleans under a disk budget (see Cleaning). The simulator does not run the cleaner yet; its crash points, read faults and planted bugs come with [The hardest tests pass](https://github.com/djosh34/tigerstore/issues/148).
- **Disk faults.** `simfs.Disk.Fault` can fail any operation on any file; the simulator fails only writes and syncs so far. Not covered yet: read errors; random crashes inside the steps of `wal.Open` in the simulator (the WAL crash tests cover them); replacing a fenced node with a fresh member that catches up by snapshot; and restarting an erased node with an empty disk, which with fixed membership can lose an acknowledged write, so it waits for member changes.
- **More simulated faults.** `sim.Faults` holds the fault rates. A gray node, with slow disk writes and delayed links at once, is not a fault of its own yet. The half-open model trusts the peer transport to fail a dead connection within its 5 s write timeout; with only small Raft messages on it, a real socket buffer may not fill, and Go's default TCP keepalive takes longer than 5 s to notice. Peer connections need `TCP_USER_TIMEOUT` or a heartbeat timeout of their own; they have neither yet.
- **Responses prepared before commit.** `core.Node.apply` runs one entry against the index and answers its requests. To prepare responses before commit, the leader runs the same function on its proposals while they replicate, keeps the encoded replies, and releases them when the entry commits at the expected index and term. A leader change drops them. The followers keep applying at commit.
- **Other transports.** The core only produces and consumes `raftpb.Message` values, and `node.Node` only needs a `peer.Transport` for sending and `Node.Deliver` for receiving. A tournament transport implements those two.
- **Alarm.** Alarms follow etcd v3.7.2's alarm store: an alarm is a type raised for a member ID. Activating and deactivating go through the log (`core/alarm.go`), and the active alarms are in every checkpoint. A list is a linearizable read, which answers what etcd's pass through Raft answers. While a NOSPACE alarm is active, puts, transactions with a put in either branch and lease grants fail with `ErrNoSpace`; while a CORRUPT alarm is active, every write but keepalives and alarm changes fails with `ErrCorrupt`, compactions and lease revokes and expiries included. Status lists the alarms in Errors as etcd's release binary prints them. etcd v3.7.2 crashes on an alarm action it does not know; tigerstore answers it with no alarms. Past its disk budget, a node answers writes with NOSPACE as etcd does with its NOSPACE alarm active, but lists no alarm and needs none disarmed: writes go on once cleaning brings the files back within the budget.
- **Lock and Election.** etcd v3.7.2 serves these services with a client of itself that runs clientv3's concurrency recipes, and holds no state of its own. Tigerstore runs the same requests in the same order on the node (`internal/server/lock.go`, `election.go`, `concurrency.go`): a Txn that puts the caller's key, the name, a slash and its lease in hex, then a Range for the newest older key and a watch on it until it is deleted, again and again. The oldest key holds the lock or leads. A request with lease 0 grants a lease of 60 s that nothing keeps alive, as etcd's orphaned session does; Proclaim and Resign do that too. A Lock or Campaign whose caller gives up deletes its key. etcd's in-process client turns etcd's errors into plain errors, which grpc-go sends with code Unknown, so these services answer Unknown with etcd's text, as do etcd's own `election: no leader`, `election: not leader`, `"leader" field must be provided` and `mutex: session is expired`. A watch that the node drops, for falling behind or for a snapshot, starts again after its last event, as clientv3 resumes it. Observe ends without an error when a read or watch fails, as in etcd. Each waiting call holds a goroutine and one watch, as in etcd; nothing on the write path changes. The difftest cases `lock` and `election` compare them with etcd.
- **Quota.** The space quota follows etcd v3.7.2's (`core/quota.go`), with `--quota-backend-bytes`: 0 means 2 GiB, a negative value no quota. etcd compares its database file's size; tigerstore compares what that database would hold for the versions in the index, every version since the last compaction at etcd's row size (`mvcc.Store.Size`), which is the same on every member and is Status' DbSizeInUse. A put, a transaction with a put or a lease grant whose cost, by etcd's estimate, would reach the quota is refused with `ErrNoSpace` before it is proposed, and the member raises a NOSPACE alarm for itself and answers once it applied. One that was let in and reaches the quota when it applies still applies, as in etcd, but its client gets `ErrNoSpace`, and every member raises its own alarm. The way out is etcd's: compact, then disarm. A compaction frees the quota at once; etcd needs a defragmentation for that. The log on disk is bounded by the disk budget instead. Alarm changes need cluster version 3, the entry format with their kind; until every voter announced it, they wait for it up to their deadline, as writes wait for a leader.
- **Hash and HashKV.** Both answer from the member's own state, without Raft, as etcd does. HashKV (`mvcc.Store.HashKV`) follows etcd v3.7.2's rules for which versions count up to the hash revision: a version at or below the compaction revision C counts only if a read at the hash revision sees it, unless no key exists then, and a tombstone at C never counts; a revision below C is `ErrCompacted`, one above the current revision `ErrFutureRev`, and before any compaction the compaction revision is -1. etcd hashes its database rows in revision order with their values; tigerstore walks the index in key order on the committer and hashes each version's revision key, fields, value length and value checksum, so it reads nothing from disk and costs one walk of the index, like a compaction. Replicas with the same state agree on the hash, but the number is not etcd's. Hash is a CRC-32C of every version in the index and of the leases, where etcd hashes its database file.
- **Compaction hashes and corruption checks.** As in etcd, a compaction takes the HashKV of its revision, with the compaction revision before it, in the same walk of the index, and each node keeps the last 10; HashKV of such a revision answers with it. The corruption checks follow etcd v3.7.2's (`internal/node/corrupt.go`), and a node asks its peers for their HashKV with a call on the peer transport (`peer.Transport.Call`, a connection of its own like a snapshot fetch). With the feature gate `InitialCorruptCheck`, a node compares its hash with its peers' before it serves clients and does not start if one with the same compaction revision differs. With `--corrupt-check-time`, the leader compares as etcd's periodic check does and raises CORRUPT for a follower that is ahead of it or has another hash at the same compaction revision, or for itself if its own hash of one revision changed. With the feature gate `CompactHashCheck`, every `--compact-hash-check-time` the leader compares the hashes its compactions took with its peers' and raises CORRUPT for the members outside the majority, or for member 0 when no majority agrees. `--feature-gates` takes etcd's gates and errors.
- **Snapshot.** Maintenance.Snapshot streams tigerstore's own format ([#123](https://github.com/djosh34/tigerstore/issues/123)), `internal/node/snapshot.go`: a header (magic `tigersnp`, the format version, the cluster ID, the applied index, its term and the revision there), the stream a follower fetches from index 1 to the applied index (the newest checkpoint with every value it names and the entries after it, or every entry while the log still starts at 1), zero padding to a multiple of 512 bytes and the SHA-256 of all of it, so it ends as etcd's does and `etcdctl snapshot save` accepts it (the smoke job saves one). A first pass counts the bytes without reading values, so the messages carry the bytes still to come as etcd's do, 32 KiB each, with the storage version, and the digest comes in a message of its own. Nothing is removed from the log while a snapshot is sent. The checkpoint plus the log keep point-in-time recovery possible. `tigerstore snapshot restore <file> --name --initial-cluster [--initial-cluster-token] [--data-dir] [--skip-hash-check]` writes such a file into a new data directory, as `etcdutl snapshot restore` does (`node.Restore`): it checks the digest, writes the stream into a new log as a follower writes a fetched snapshot, commits everything up to the snapshot's index in the hard state, and writes the node's `member` file with the cluster ID of the token and `--initial-cluster`. Every node of the new cluster restores the same file; the new cluster has as many members as the old one. `TestSnapshotRestore` saves a snapshot of a cluster whose first segment is gone, restores it into three new data directories, starts a cluster on them and compares every key now and at the compaction revision, the leases with their keys and the alarms.
- **Auth.** Users, roles and permissions follow etcd v3.7.2's auth store (`core/auth.go`, `server/auth.go`) and are replicated state, in checkpoints: whether auth is on, the auth revision, the users with their bcrypt hashes and roles, and the roles with their key permissions. Every Auth request goes through the log as an `InternalRaftRequest` (entry kind 13) and applies with etcd's checks and errors: enabling needs the user root with the role root, root and its role cannot go while auth is on, every change counts the revision up, and a user's permissions are merged into sorted spans after each change, which answer whether a key or a range is covered, as etcd's interval tree does. The server hashes passwords with bcrypt (`--bcrypt-cost`) before the request goes into the log, and Authenticate reads the user's hash with a linearizable read, checks the password on the call's goroutine, never on the committer, and then has the log make the token, again if auth changed in between. A request's identity is its token (`token` metadata, or `authorization` with or without `Bearer `), or else the client certificate's common name, as etcd's `AuthInfoFromCtx`. Writes carry the user and the auth revision it was taken at in their entry (kind 14 wraps them), and each replica checks them when they apply: a write taken before an auth change fails with `ErrAuthOldRevision`, as in etcd. Reads, watches, leases, Status, Alarm, Hash, HashKV, Snapshot, Compact and the member changes are checked when the node serves them, with etcd's rules for each. Tokens are simple tokens (`--auth-token simple`, the default): the node that takes an Authenticate picks a 16-letter prefix, and every node makes `<prefix>.<entry index>` a token when the entry applies, so a token works on every member; a request with a token whose entry has not applied on that member yet waits for it, as in etcd. A token not used for `--auth-token-ttl` (300 s) goes, as do a user's tokens when the user changes password or goes, and every token when auth is turned off. Tokens are not replicated state: a restart forgets them, as etcd's does. With `--auth-token jwt,priv-key=<file>,pub-key=<file>,sign-method=<alg>,ttl=<duration>` (`server/jwt.go`), the server signs a JWT with the user, the auth revision and an expiry once the Authenticate applied, and checks the signature and expiry of every token it gets; the node takes the user and revision from the claims, so any auth change makes a token old (`ErrAuthOldRevision`), as in etcd. The options, sign methods (RS, PS, ES, HS and EdDSA), key checks and verify-only public keys are etcd's, and `--auth-token ""` hands out no tokens, as etcd's. The difftest runs an auth case on a server of its own, once with simple tokens and once with JWT.
- **Auto compaction.** `--auto-compaction-mode` and `--auto-compaction-retention` are etcd's (`node/compact.go`): a number is hours in periodic mode and revisions in revision mode, anything else a duration, and 0 or a negative duration turns it off. etcd v3.7.2 compacts nothing with a negative revision retention either, but with a negative periodic one it compacts at about the current revision in a loop that never waits; tigerstore does not copy that. As in etcd v3.7.2, only the leader compacts, through the log like a client's Compact, as the root user. The periodic compactor notes the revision every tenth of the retention (at most every 6 minutes) and compacts at the revision it noted a retention ago, first once a retention has passed and then every retention up to an hour, or every hour; the revision compactor compacts at the current revision less the retention every 5 minutes. A difftest suite checks the periodic mode with a retention of 2 s.
- **Downgrade.** Maintenance.Downgrade follows etcd v3.7.2 (`core/downgrade.go`). Its state is etcd's and replicated, in checkpoints: etcd's cluster version, 3.7.0, and whether a downgrade to the minor version below is enabled, with its target. This is the version clients see, not tigerstore's entry format (Cluster version), which never goes down. VALIDATE checks, after a linearizable read, the version's format (major.minor, with or without a patch), that the target is the minor version below the cluster version, and that no downgrade is on. ENABLE writes etcd's `DowngradeInfoSet` through Raft, which makes the same checks when it applies, so that of two at once one fails; CANCEL writes it off, and answers without error when none is on, as etcd does. Every 4 s, as etcd's version monitor, the leader writes etcd's `ClusterVersionSet` to move the cluster version to the target while a downgrade is on, and back to 3.7.0 once none is; the storage version in Status, `/version` and Snapshot follows it. etcd ends a downgrade by itself once every member runs the target version; every tigerstore member runs 3.7.2, so a downgrade ends only by CANCEL. The answers carry etcd's errors and the cluster version as major.minor, as the difftest checks.
- **Defragment and MoveLeader.** Both follow etcd v3.7.2: an admin may call them with auth on, and their responses have no header. etcd's Defragment rewrites its database file without the free pages; tigerstore's log has none, and the space it can give back is in the segments below the oldest checkpoint the node keeps, which values still in use hold. Defragment runs cleaning passes over them, as the disk budget's cleaner does when space is short (see Cleaning), after any snapshot being sent, until nothing more goes or a removal waits for a snapshot fetch, so that every old segment goes and its live values move into a pack. MoveLeader is taken only by the leader (`ErrGRPCNotLeader` elsewhere), only for a voting member (`ErrGRPCBadLeaderTransferee`), and starts Raft's leadership transfer; it answers once the node sees the transferee lead, or with etcd's "leader transfer took too long" at the request's deadline, where etcd waits as long as the client does (`core/moveleader.go`).
- **Backpressure.** With 64 persist batches waiting, the committer takes no new inputs. A peer connection then blocks in `Node.Deliver` once the inbox of 8192 inputs is full, and client requests wait in `Node.Do`.
- **Membership details.** `--listen-client-urls`, `--advertise-client-urls` and `--listen-peer-urls` take one URL each, where etcd takes lists; a list is refused with an error.

## Open for the architect

- How the committer prepares responses before commit: which node executes a batch, and when, so that the prepared revisions and results match the committed order.
- The hash index, fuzzy checkpoints, compression, and the batch byte cap.

## Expected numbers

Hypotheses from [#32](https://github.com/djosh34/tigerstore/issues/32), for a GitHub runner with one pinned core per replica and one for the load generator:

- At 1 KiB, about 90k writes/s with the lean generator (the shared disk caps near 98k/s), and about 30k/s with the stock etcd client. etcd measured 27k/s ([#26](https://github.com/djosh34/tigerstore/issues/26)).
- At 10 KiB, about 11k writes/s, or about 20k/s if compression reaches 2x.
- Besides throughput, the benchmarks report server CPU microseconds per operation per node.
