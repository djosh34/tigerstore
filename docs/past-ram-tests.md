# Past-RAM checks for #148

This branch starts at `63219a94`. It adds tests and measurements, not a server fix.
All execution runs in GitHub Actions on `ubuntu-24.04-arm`.

## Running

`.github/workflows/past-ram.yml` is reusable and dispatchable after merge.
On the prework branch, dispatch `ci.yml`. Its `capacity` input can be false
when only the storage tests need another run. Drop the final `prep only:`
commit before integration and add the storage checks to the normal CI gate.

The capacity jobs build `cmd/pastram` and either tigerstore or the
checksum-pinned etcd v3.7.2 release binary. `scripts/past-ram.py` starts three
members, each in a separate cgroup with `memory.max=671088640` and no swap.
The kernel charges each member's page cache to that cgroup. The controller
and client stay outside those limits. Both products get `GOMEMLIMIT=560MiB`.
Tigerstore gets no memory flag in that comparison because its flag overrides
GOMEMLIMIT. This explicit configuration is not a fix for #202's default
budget calculation. No CPU quota is imposed. Peers use automatic TLS certificates;
client connections use plaintext on loopback.

Each server retains its normal storage defaults. Tigerstore has no disk
budget in the capacity tests. Etcd gets an 8 GiB quota in one max-objects
case and `9223372036854775807` in the other. The latter makes its quota
irrelevant to this runner's capacity, rather than using zero, which selects
etcd's default quota.

The first run, `38941733754`, used the main server's normal memory-budget
path, a 640 MiB flag for tigerstore, no GOMEMLIMIT, and a 32 GiB etcd quota.
Keep those results separate from the equal-GOMEMLIMIT comparison.

## Workload and measurements

The driver repeats the measured Kubernetes 1.37 size histogram, 6,345 objects
and 9,253,583 value bytes per cycle. The shared `internal/k8ssize` files come
unchanged from `work/148-soak`; do not add a second copy when integrating.
Values are deterministic generated bytes, not captured Kubernetes contents.
Preload uses 64 Put operations per Txn. An atomic file records the exact
last acknowledged object and value-byte counts. An interrupted Txn can add
up to 64 more objects than that count; the report does not call an unknown
outcome a definite rejection.

The proof preloads at least 3.1 times the cgroup limit in live values. Its
single sequential client then runs for three minutes. Requests include
point reads, LIST, MOD-compare updates, deletes and recreations. The runner
kills member 2 after 30 seconds and restarts it after another five seconds.
Every successful value response is checked against the client's own
history. After load ends, every member is scanned and checked byte for
byte, including deleted-key counts. Verification uses eight concurrent bounded-range readers per member,
so it does not repeatedly count all remaining keys for each small page.
The workload's LIST requests still use ordinary etcd Range semantics.

Reports contain throughput and p50/p99 latency per logical workload
operation. An update includes its preceding Get and CAS, so these are not
single-RPC latency numbers. CPU comes from per-member `cpu.stat`, sampled
around the mixed interval. Reports also retain OOM counters, anonymous
memory, page cache, cache metrics, index bytes and block read bytes.
The driver waits for the controller's samples before starting load and
before starting verification. This keeps verification reads out of the
mixed interval. The two-second sampling interval adds idle time at the
boundaries, but no subsequent workload.
Index bytes per key are estimates from metrics and the sampled acknowledged
count, not measured Go heap occupancy. Etcd exposes no equivalent index
metric, so its index bytes per key are not measured by this runner.

Max-objects runs continue until a member or request fails. Their reports
name that failure and the last acknowledged count. An OOM here is the
capacity boundary being sought, not by itself a new tigerstore defect.
The 45-minute controller limit is a censored result, not a store limit.

The cache experiment uses the same preload, with eight reads in ten aimed
at the first one percent of keys and two in ten at the whole set. It does
not kill a member. The control changes only `fitCache` to set a zero cache
limit in the experimental build. The patch is retained as an artifact.
Cache hits/misses and physical storage reads can compare the allocation
choices. `io.stat` does not count kernel page-cache hits directly; do not
report a kernel hit percentage from those numbers.

## Storage checks

Already on the baseline:

- `internal/wal/pack_test.go` checks pack creation, root buffering and sync,
  segment removal, pack merging, damaged packs and shrinking lookup maps.
- `internal/node/clean_test.go` churns 200 rounds under a disk budget,
  checks NOSPACE recovery, verifies that the first segment is gone and
  compares surviving values after restart. `TestDefragment` does the same
  without a disk budget. The existing log reports copied pack bytes; this
  branch also divides them by acknowledged Put operations, not Txns.
  These are copied pack bytes at each sample, not total disk write
  amplification. WAL, root, checkpoint and filesystem journal writes are
  outside that counter.
- `internal/core/cache_test.go` checks LRU eviction, accounting, fills,
  overwrite/delete invalidation, budget shrinkage and snapshot installs.
- `internal/core/coldread_test.go` holds all value-bearing response forms,
  compacts while reads wait, checks watch progress ordering and VALUE
  compare ordering. These are virtual-time component tests, not a measured
  two-second three-member election test.
- `TestReadHoldsRemoval` checks a real reader against checkpoint-driven
  removal. `simfs` already exposes EIO hooks on reads. Simulator value
  completions already have independently drawn delays and can reorder.

Added here:

- `TestPastRAMRecovery` enables the cache for sixteen simulator seeds,
  runs all six checkers and compares recovered values with the simulator's
  independent committed history. It checks the exact durable commit prefix,
  since the persisted commit hint can lag applied. It packs a durable copy,
  crashes at pack-sync, buffered-root, synced-root and removed-segment
  boundaries, and checks every retained checkpoint reference too. It
  explicitly checks that the original files are absent after removal.
- Two cleaning protocol mutations drop one checkpoint value or remove segments
  before root sync. Seed 1 must catch each with a lost-checkpoint-value
  error. These mutate the test's cleaner protocol, not `node.cleaner`.
- `TestColdReaderDuringCleaning` holds a real disk reader while the real
  cleaner packs its segment, then checks that removal waits for the reader
  and runs after release without another write.
- `TestColdReadEIO` checks typed failure through the helper and core.
  `TestColdReadsCompleteInReverse` completes delayed helpers out of order
  after an overwrite and compaction, and checks that no stale value wins.
- `TestCacheReferenceIdentity` rejects an old value at the same offset in
  another Raft entry. CI plants an index-blind cache lookup and requires
  this test to catch it in one fixed scenario.

## Recorded results

[Run 38944867881](https://github.com/djosh34/tigerstore/actions/runs/38944867881)
tested `74a47e67`. The runtime code of the server is unchanged from main at
`63219a94`. Main later advanced to `e6c654e8`, which changes only CI.
The matrix is red because the capacity runs terminate at their limits and
etcd cannot finish the proof preload. Tigerstore's proof and both cache
experiments passed their value checks.

### Memory proof

[The tigerstore job](https://github.com/djosh34/tigerstore/actions/runs/38944867881/job/117121331447)
preloaded 1,426,880 objects and 2,080,401,455 value bytes in 60.22 seconds.
All three members reached the preload count before load began. Over 180
seconds it completed 45,720 logical operations, 254.0/s, with p50 1.533 ms
and p99 46.014 ms. Aggregate server CPU was 199.91 CPU-seconds. One member
was killed and restarted. Every member passed the final byte checks;
2,073,765,930 live value bytes remained. No cgroup recorded an OOM kill.

[Etcd's proof job](https://github.com/djosh34/tigerstore/actions/runs/38944867881/job/117121331287)
recorded an OOM kill during preload, after 463,744 acknowledged objects and
678,348,675 value bytes. There is no etcd mixed-load throughput or latency
at the requested population to compare. This is a failed reference run,
not a passing full #144 proof.

### Storage and cleaning

[The storage job](https://github.com/djosh34/tigerstore/actions/runs/38944867881/job/117121330839)
passed formatting, vet, lint, driver tests and the selected storage tests
under race. Sixteen cache-enabled simulator histories passed all six
checkers and recovered after removal of 61 original segments in total.
The held-reader, reversed-read and EIO tests passed. Both cleaning mutation
controls and the stale cache lookup were caught within their fixed
one-scenario budgets. The final branch tightens the checkpoint mutation
from dropping all eligible values to dropping exactly one.

At round 200 of `TestCleaningCycles`, 157,600 copied pack bytes divided by
10,051 acknowledged Put operations gave 15.68 bytes per Put. At that sample
the index was 16,433 bytes, window 21 bytes, lookup map 1,896 bytes and disk
474,221 bytes. The original first segment was absent; restart returned the
expected values. This small synthetic churn test is not a production
write-amplification estimate.

## Remaining limits

This is not the complete #144 proof yet. The real-process driver has exact
response and final-state checks, but no watch traffic, leases, compaction
or recorded history for the six general checkers. Its mixed load is one
sequential client, not the existing concurrent mixed-k8s load generator.
A passing simulator history does not fill that gap in a real-process run.

The simulator's cleaner checks operate on durable copies after a seed.
They do not schedule the paced production cleaner concurrently with
clients, snapshot transfers and arbitrary I/O faults. The real-reader test
covers one such overlap. The normal planted-bug catalog and its main CI
workflow still need the new cases integrated.

The cache measurement is one run per allocation choice, not a statistically
stable performance decision. Compression and #101 integration are outside
this prework assignment. #148 remains open until its task worker completes
these gaps and runs the required checks on main.
