# Reusable paired Put comparison

Adapted from `exp/bench-68`, `experiments/pre47groupcommit`, and its pre50 direct protobuf/grpc-go client. Experiment code only. Never merge this branch.

`.github/workflows/bench75.yml` runs only on `exp/bench-75`, by manual dispatch. It accepts `candidate_ref`, optional `second_candidate_ref`, `baseline_ref`, and optional `capture_profiles`. The defaults compare current main, `work/50-frontend`, `work/50-batch` and stock etcd v3.7.2. Each run has its own output directory, so archived earlier evidence never contaminates a later run. A short first job resolves current refs once, so both matrix jobs use the same immutable commits. Each matrix job has its own free `ubuntu-24.04-arm` runner and uses either 64 or 256 closed-loop clients. Five repetitions run all stores sequentially, reversing the order in even repetitions. Each cluster is fresh. Builds and benchmarks belong on Actions, not this host. The scripts refuse new starts after 2026-10-13T22:00:00Z.

Each leader receives 4,096 seed Puts, 20,000 warmup Puts, a one-second pause and 60,000 measured Puts. The same generator uses 16 TLS 1.3 grpc-go connections, client certificates, 1,024-byte independent SHA-256-derived values reused on overwrite, and 4,096 Kubernetes-shaped keys. One outstanding RPC per worker, leader endpoint only. Client connections complete a Range probe before timing. These are fixed-concurrency results, not open-loop latency or a capacity limit. No watches, leases, compaction, auth policy or injected peer delay. Both client and peer links require TLS certificates. Etcd has its safe persistence defaults and an 8 GiB backend quota. All data directories use the root ext4 mount after a runner-only remount with `barrier=1`. The script rejects `nobarrier` and `barrier=0` afterward. This does not prove physical power-loss protection. Three processes share one disk and VM.

The elected leader is pinned to CPU 0, followers to CPUs 1 and 2, generator to CPU 3. `GOMAXPROCS=1` is the environment for all processes. Current tigerstore commits force at least two Go processors per server, even on one pinned physical CPU; etcd and the generator keep one. The runtime count and every server thread's final affinity are recorded. Placement uses `taskset -apc` after election.

Production source is extracted with `git archive`. Each tigerstore archive gets the identical loopback debug HTTP listener from `observe.go.txt`, installed with a single hook in `cmd/tigerstore/main.go`. It reports atomic leader metadata and `runtime/metrics`. Core, Raft, WAL, peer transport, frontend and disk calls do not change. No CPU profile capture, allocation sampling changes, timed file-call wrappers, forced GC or background scrapes run in the comparison windows. When `capture_profiles` is true, the 256-client job starts a separate fresh second-candidate cluster after all comparison repetitions. Only that profile cluster exposes pprof endpoints. These are instrumented executables of the named commits, not byte-identical release binaries. The observer's few allocations are included in process totals.

CPU is process user plus system time from `/proc/PID/stat` fields 14 and 15, parsed after the last `)`, with field 22 identity checks and `getconf CLK_TCK`. The generator samples immediately around the successful-operation interval through drain. Sum three process deltas for total server CPU; do not add thread CPU. This excludes I/O wait and uncharged kernel-worker/IRQ work. Allocation snapshots bracket that CPU interval, immediately before and after, so the allocation interval is slightly wider. Tigerstore leader totals use `/gc/heap/allocs:objects` and `/gc/heap/allocs:bytes`. Etcd uses `go_memstats_mallocs_total` and `go_memstats_alloc_bytes_total` from its metrics endpoint. Divide cumulative deltas by successful Puts. These include Raft, peer, runtime, observation and idle/background allocations, not only the handler. The endpoint counter reads are not synchronized across separate processes.

GC share for tigerstore is `delta /cpu/classes/gc/total:cpu-seconds / delta of total minus idle CPU classes`. It is the runtime's estimated non-idle CPU share, not GC wall pauses or a ratio to the independently sampled process CPU ticks. Runtime GC CPU accounting includes estimates such as stop-the-world processor time and may lag the endpoint reads. Etcd's stock endpoint does not expose cumulative GC CPU, so its GC share is unavailable. Heap object bytes after the window are retained bytes before a forced GC, not a measured live-set minimum.

Validation requires no RPC errors, exactly 60,000 successes, one response term, revision delta equal to successes, stable before/after leadership, and pinned thread affinities. Every replica must apply the measured revision after drain. Etcd additionally fences its post-WAL-save committed gauge. Those later fences are outside the CPU/allocation interval; trailing follower work can fall outside it. JSON files preserve all counters and identities. Latency includes all successful RPCs through drain and client context setup. Medians are medians of five per-run statistics, not pooled percentiles.

```sh
# On a fresh disposable Actions runner only, after setup-go 1.27.2:
CLIENTS=64 BASELINE_REF=<sha> CANDIDATE_REF=<sha> SECOND_CANDIDATE_REF=<sha> \
  timeout --kill-after=5s 820s bash experiments/bench75/run.sh
python3 experiments/bench75/summarize.py evidence/bench75
```

The original PR 75/76 evidence is in `evidence/bench75/c64` and `c256`. Later runs write `evidence/bench75/run-<Actions run ID>/c64` and `c256`. `summarize.py` rejects invalid windows and missing repetitions, then emits `runs.csv` and `summary.csv`. The optional profile cluster gets the same seed and warmup, then 25 seconds of closed-loop arrivals with drain. The generator writes an arrival-start marker after its connection probes. One second later, the driver requests concurrent 20-second leader CPU and allocation-delta profiles. The allocation profile uses Go's default sampling rate and yields both `alloc_space` and `alloc_objects`, not exact allocation counts. Heap-profile accounting can lag GC; warmup records may appear in the delta. `go tool pprof` emits the top 25 flat and cumulative functions for CPU, allocated bytes and allocated objects. Profile timing metadata, the profile-run workload result and the gzip-compressed matching symbol binary are archived separately under `c256/profile-second`. No profile-run numbers enter the five-repetition medians.

Channel operations and full-value copies require a source audit of every measured tigerstore SHA. They are not runtime metrics; their source-counted report must state fixed per-request versus amortized/conditional work and name every counted site with `file:line`.
