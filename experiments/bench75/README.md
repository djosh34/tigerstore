# Reusable paired Put and CAS comparison

Adapted from `exp/bench-68`, `experiments/pre47groupcommit`, and its pre50 direct protobuf/grpc-go client. Experiment code only. Never merge this branch.

`.github/workflows/bench75.yml` runs only on `exp/bench-75`, by manual dispatch. It accepts `candidate_ref`, optional `second_candidate_ref`, optional `third_candidate_ref`, `baseline_ref`, and optional `capture_profiles`. The defaults compare current main, `work/50-txn` and stock etcd v3.7.2. Optional second and third candidates still support multi-PR comparisons. PR-head refs remain usable after a branch is deleted; a failed ref lookup aborts the resolver. Each run has its own output directory, so archived earlier evidence never contaminates a later run. A short first job resolves current refs once, so all matrix jobs use the same immutable commits. The `suite` input selects `put-cas-256`, `put-64-256` or `all`. The first runs Put and CAS at 256 clients; the second runs Put at 64 and 256; `all` runs all three cells. Each cell uses its own free `ubuntu-24.04-arm` runner. Put compares every supplied candidate; CAS compares main, the third candidate when supplied or otherwise the first candidate, and etcd. Five repetitions run all stores sequentially, reversing the order in even repetitions. Each cluster is fresh. Builds and benchmarks belong on Actions, not this host. The scripts refuse new starts after 2026-10-13T22:00:00Z.

Each leader receives 4,096 seed Puts, 20,000 warmup Puts, a one-second pause and 60,000 measured Puts. All new Put/CAS jobs use the lean raw HTTP/2 generator adapted from `exp/pre-47-grpc` commit `d2408301966b99471bfed06d4c2dc1cd1e5af462`, `experiments/grpc/lean.go`. It retains prebuilt requests, warm HPACK, coalesced writes and two goroutines per active connection, one reader and one owner. The 64/256 outstanding RPC slots are split across 16 TLS 1.3 connections with client certificates. One extra idle grpc-go connection supplies untimed revision probes and CAS cache seeding. All stores, including etcd, use the same lean engine, 1,024-byte independent SHA-256-derived values reused on overwrite, and all 4,096 Kubernetes-shaped keys. The original global multiplicative key permutation is unchanged. Every active connection completes a SETTINGS handshake and one valid untimed warm RPC before measurement/revision snapshots. Each subprocess therefore adds 16 untimed warm RPCs outside its requested operation count; successful warm writes are reported separately. Lean header blocks do not contain grpc-timeout. A client-side 10-second stall/RPC guard remains. Client slots replenish after replies through the owner, not per-RPC goroutines. Before the architect's change, archived runs used grpc-go v1.84.0 for the timed workload. The loader retains `-generator grpc` for historical reproduction, but new Actions jobs explicitly pass `-generator lean`. These are fixed-concurrency results, not open-loop latency or a capacity limit. No watches, leases, compaction, auth policy or injected peer delay. Both client and peer links require TLS certificates. Etcd has its safe persistence defaults and an 8 GiB backend quota. All data directories use the root ext4 mount after a runner-only remount with `barrier=1`. The script rejects `nobarrier` and `barrier=0` afterward. This does not prove physical power-loss protection. Three processes share one disk and VM.

The elected leader is pinned to CPU 0, followers to CPUs 1 and 2, generator to CPU 3. `GOMAXPROCS=1` is the environment for all processes. Current tigerstore commits force at least two Go processors per server, even on one pinned physical CPU; etcd and the generator keep one. The runtime count and every server thread's final affinity are recorded. Placement uses `taskset -apc` after election.

Production source is extracted with `git archive`. Each tigerstore archive gets the identical loopback debug HTTP listener from `observe.go.txt`, installed with a single hook in `cmd/tigerstore/main.go`. It reports atomic leader metadata and `runtime/metrics`. Core, Raft, WAL, peer transport, frontend and disk calls do not change. No CPU profile capture, allocation sampling changes, timed file-call wrappers, forced GC or background scrapes run in the comparison windows. When `capture_profiles` is true, the 256-client Put job starts a separate fresh last-candidate cluster after all comparison repetitions. Only that profile cluster exposes pprof endpoints. These are instrumented executables of the named commits, not byte-identical release binaries. The observer's few allocations are included in process totals.

CPU is process user plus system time from `/proc/PID/stat` fields 14 and 15, parsed after the last `)`, with field 22 identity checks and `getconf CLK_TCK`. The generator samples immediately around the successful-operation interval through drain. It also reads leader `/proc/PID/io` `syscr` and `syscw` at those boundaries, rejects missing or decreasing counters, and divides deltas by completed operations. These are Linux I/O-accounting syscall counters for the whole leader process, not a partition of all Syscall6 samples or solely client socket calls. Sum three process deltas for total server CPU; do not add thread CPU. This excludes I/O wait and uncharged kernel-worker/IRQ work. Allocation snapshots bracket that CPU interval, immediately before and after, so the allocation interval is slightly wider. Tigerstore leader totals use `/gc/heap/allocs:objects` and `/gc/heap/allocs:bytes`. Etcd uses `go_memstats_mallocs_total` and `go_memstats_alloc_bytes_total` from its metrics endpoint. Divide cumulative deltas by completed operations. These include Raft, peer, runtime, observation and idle/background allocations, not only the handler. The endpoint counter reads are not synchronized across separate processes.

GC share for tigerstore is `delta /cpu/classes/gc/total:cpu-seconds / delta of total minus idle CPU classes`. It is the runtime's estimated non-idle CPU share, not GC wall pauses or a ratio to the independently sampled process CPU ticks. Runtime GC CPU accounting includes estimates such as stop-the-world processor time and may lag the endpoint reads. Etcd's stock endpoint does not expose cumulative GC CPU, so its GC share is unavailable. Heap object bytes after the window are retained bytes before a forced GC, not a measured live-set minimum.

Validation requires no RPC errors, exactly 60,000 successes, one response term, revision delta equal to completed Puts or CAS compare passes, stable before/after leadership, and pinned thread affinities. Every replica must apply the measured revision after drain. Etcd additionally fences its post-WAL-save committed gauge. Those later fences are outside the CPU/allocation interval; trailing follower work can fall outside it. JSON files preserve all counters and identities. Latency includes all successful RPCs through drain and client context setup. Medians are medians of five per-run statistics, not pooled percentiles. Reports include generator CPU microseconds per operation and occupied cores next to leader and total server CPU. The earlier grpc-go 256-client Put generator used about 0.96 cores, so its throughput may be generator-bound; leader CPU per operation is the better comparison there. New runs measure the lean generator's actual cost rather than assuming the pre47 result of about 2.8 microseconds per Put.

```sh
# On a fresh disposable Actions runner only, after setup-go 1.27.2:
CLIENTS=64 WORKLOAD=put GENERATOR=lean BASELINE_REF=<sha> CANDIDATE_REF=<sha> \
  SECOND_CANDIDATE_REF=<sha> THIRD_CANDIDATE_REF=<sha> \
  timeout --kill-after=5s 820s bash experiments/bench75/run.sh
python3 experiments/bench75/summarize.py evidence/bench75
```

The original PR 75/76 evidence is in `evidence/bench75/c64` and `c256`. Later Put/CAS runs write `evidence/bench75/run-<Actions run ID>/put-c64`, `put-c256` and `cas-c256`. Earlier Put-only runs keep their `c64`/`c256` directories. `summarize.py` rejects invalid windows and missing repetitions, then emits `runs.csv` and `summary.csv`. CAS jobs seed with ordinary Puts, then warm up and measure 20,000 and 60,000 transactions. Before each CAS subprocess, one untimed keys-only prefix Range loads the existing keys' mod revisions. Each transaction compares one cached positive mod revision, then puts the same 1 KiB value on success, else ranges that key and validates its returned value. The client refreshes the revision from the branch response and never replaces a newer cached revision with an older one. Lean CAS requests have prebuilt comparison/key and success/else bytes. The owner encodes only the current positive mod revision and comparison length as minimal varints into reusable slot scratch; it does not build request protobuf structs per operation. The original global key permutation is unchanged. There are no separate per-operation pre-reads or client retries. Actual compare-pass/fail counts are reported, and the revision delta must equal compare passes. A completed compare failure is a valid transaction, not an RPC error. CPU, allocations and syscall deltas divide by completed transactions in CAS jobs. The original allocation JSON names ending in `_per_put` remain for compatibility; operation-neutral aliases and report columns ending in `_per_op` give the same counters for new jobs.

The optional profile cluster gets the same seed and warmup, then 25 seconds of closed-loop arrivals with drain. The generator writes an arrival-start marker after its connection probes. One second later, the driver requests concurrent 20-second leader CPU and allocation-delta profiles. The allocation profile uses Go's default sampling rate and yields both `alloc_space` and `alloc_objects`, not exact allocation counts. Heap-profile accounting can lag GC; warmup records may appear in the delta. `go tool pprof` emits the top 25 flat and cumulative functions for CPU, allocated bytes and allocated objects, plus `-peek=Syscall6` to preserve the syscall's caller times. Profile timing metadata, the profile-run workload result and the gzip-compressed matching symbol binary are archived separately under `put-c256/profile-<last candidate>`. No profile-run numbers enter the five-repetition medians.

Channel operations and full-value copies require a source audit of every measured tigerstore SHA and the exact etcd release source. They are not runtime metrics; their source-counted report must state fixed per-request versus amortized/conditional work and name every counted site with `file:line`.
