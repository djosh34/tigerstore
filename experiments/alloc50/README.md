## Matched timed workload and validity

The bench75 generator uses the generated protobuf/grpc-go client, 16 established client-certificate TLS 1.3 connections, leader-only closed-loop Puts, independent deterministic 1KiB values, and 4096 Kubernetes-shaped overwrite keys. Fresh clusters get 4096 seed, 20000 warmup and **60000 successful timed Puts**. The leader is pinned to CPU0, followers CPU1/2, generator CPU3. `GOMAXPROCS=1` is passed to all processes; tigerstore's existing minimum gives **two** Go processors per server, checked explicitly; the generator stays at one. No watches, compaction, injected delay or compression during timing.

Client and peer certificate-authenticated TLS flags, election discovery, role pinning, all-replica applied/revision/term fences, process start identities and every-thread affinity checks are inherited from bench75. Data resides on the runner's ext4 filesystem remounted with `barrier=1`; the script records the mount and rejects `nobarrier`/`barrier=0`. Guest barriers and fsync do **not** prove physical power-loss protection. All three replicas share a VM and disk.

The generator rejects RPC errors, incorrect counts, response/revision/term mismatches and process changes. The driver requires exactly 60000 successes, no errors, identical terms before/after, unchanged leader, expected Go processors, live processes and affinity. Summary rejects missing variants, duplicate/missing repetitions and failed diagnostics. Invalid raw evidence remains uploaded but is not a result.

CPU is process user+system `/proc/PID/stat` delta divided by successful Puts; the generator's own interval covers execution and drain, not later replica fences. Allocation objects/bytes and GC CPU are whole-leader runtime counter deltas over a slightly wider bracketing interval, not handler-only attribution. Metrics flags are attached only to the primary 60000-Put timing cohort, not seed, warmup, case or 2000-Put profile cohorts: runtime CPU-class counters can stay stale when a short cohort has no GC. Primary metrics still use the exact copied generator's strict delta checks; no forced GC is added inside or before timing to make them pass, and a stale/invalid primary delta remains a failed window. GC CPU share is estimated GC CPU divided by estimated runtime non-idle CPU, **not** GC pause time or `/proc` CPU share. Throughput and p99 are medians of five independent per-run statistics, never pooled percentiles. The unchanged generator does not retain every latency sample. A saturated generator or short window limits conclusions; these are not capacity or open-loop latency claims.

## Retention and profiles, separate from timing

Each timed window ends before replica fencing and the leader's `/debug/retained` call. That endpoint forces GC and records heap allocated/object/in-use/reserved bytes and optional allocator gauges. Forced-GC retained heap is reported separately from the unforced heap snapshot in timed counters; it includes live MVCC/log history, runtime and connection state. It is **not** all transient workspace or proof of a zero-allocation runtime.

Fresh separate profile clusters warm up normally, then set a process-start diagnostic allocation sampling rate of **1** and run exactly **2000 sequential successful Puts**. Before/after allocation profiles each force two GCs to flush delayed accounting. The exact successful count, sample rate, and matching binary are recorded in `profile-cohort.json`; profiler-run throughput is not added to primary medians. Exact success, revision, term and process-CPU checks remain active for profile cohorts even though runtime allocation/GC metrics flags are omitted; their allocation attribution comes from before/after pprof deltas. Profile blocks/objects need not equal runtime malloc counts because the tiny allocator can pack several small objects in a block; do not sum profile rows or equate profile block totals with `Mallocs`.

Artifacts retain both raw profiles and symbol binaries, plus `go tool pprof -base=<before> -sample_index=alloc_space|alloc_objects|inuse_space|inuse_objects <binary> <after>` text and proto deltas. Allocation attribution views additionally ignore only identified observation stacks (`runtime/pprof`, `main.bench75Observe`, `net/http.`). Raw deltas remain available: before-profile serialization itself appears after the baseline snapshot and must not be attributed to Put. GC/background accounting and observation overhead still mean a profile delta is not an exact census of just 2000 RPCs.

## Separate size and stalled-reader diagnostics

Fresh case clusters run the same valid Put cohort outside primary summaries, then execute `cases` (also on CPU3):

1. Build the canonical `InternalRaftRequest` with etcd's request-header sizing ID `1<<63`; determine the largest value whose entire request is 1536KiB. Verify just-below and equal-request-boundary Puts and exact byte roundtrips; reject the next byte and **exact 1536KiB value payload** with `request too large`. After each rejected Put, verify the previous accepted value was not changed. A 1536KiB payload is **not** a legal 1536KiB request because keys, protobuf framing and request header also count.
2. Open raw mTLS HTTP/2 with `INITIAL_WINDOW_SIZE=0`, read and ACK only handshake SETTINGS/window credit, then stop all reply reads and updates. Plan **4096 valid 1KiB Puts** on distinct streams, with the whole plan's DATA bytes checked against advertised stream and connection credit. Clear the handshake deadline and launch one bounded sender goroutine with a 20-second write deadline; immediately begin healthy traffic rather than waiting for raw writes. Atomics record actual attempted streams, completed HEADERS, completed DATA and complete-DATA bytes. Baseline must finish all 4096 sends; a managed strategy may stop at a blocked prefix only after verified saturation/refusal and healthy progress. No flow-control violations or HTTP/2 floods are needed. Unsent replies retain prototype managed slots; an independent healthy TLS connection must complete **at least 1536 Puts** while the slow connection remains open. Before close, that healthy connection also reads `/alloc50/slow`: its `Version` is reported as **`slow_committed_puts`**, separately from **`slow_planned_puts=4096`**, actual **`slow_attempted_puts`**, completed frames and reserved capacity. Actual commits must not exceed completed DATA plus one last in-progress frame. Singleton HEADERS sent in separate TLS records can seal an eight-slot arena region for one active stream: charging 256 slots can therefore mean only 32 actual committed stalled calls, versus 256 on ring. The harness measures and reports the actual count rather than assuming equivalent admissions. Capture forced-GC/allocator snapshots before, three stalled phases, and after closing the slow connection; verify healthy values, replica completion/term, process liveness and affinities.

`cases.json` retains sizes, errors/revisions, successful healthy counts and snapshots. The optional `Server.AllocationStats() map[string]uint64` interface is absent on pristine base and mandatory for prototypes. Checks require the expected mode (0/1/2), actual stalled occupancy at least `per_connection_slots`, quota refusal (`denied_count` grows) reached within five seconds, at least one second of sustained quota while healthy Puts continue, stable held slots/bytes in the last two stalled phases, held/peak slots and bytes within declared budgets, zero fallback allocations, and release to no more than before-slow occupancy within five seconds after close. A blocked prefix requires a **before-close** `/debug/goroutines` text dump; any failure also attempts a dump before cleanup when reachable. Close the underlying TCP socket (Framer I/O remains TLS), then require the sender to terminate within three seconds. Premature errors/timeouts are failures, not expected backpressure; only close-induced `net.ErrClosed`/`io.ErrClosedPipe` is accepted after deliberate close. Healthy Puts alone are not sufficient saturation evidence. Implemented budgets are 4096 slots, 256 capacity units / 8MiB per connection, and 64MiB globally; the recorded gauges, not these prose values, determine validity. Ring uses a circular 4096-slot queue; arena uses 512 preseeded pooled eight-slot regions, so `held_slots` counts reserved capacity, not necessarily active streams. Both strategies pay startup allocation costs rather than obtaining a lazy-heap advantage. The byte budget includes a conservative 8MiB driver list/map reserve, also exposed as `driver_reserve_bytes`; `held_bytes` includes this baseline reserve. Recovery therefore compares against the before-slow baseline, never against zero. `fallback_allocations` counts only explicit managed-Put heap fallback (none is implemented), not the known generic RPC/debug allocations still included in whole-leader runtime counters. Additional `per_connection_bytes`, `timer_allocations` and `unmanaged_rpc_count` gauges are preserved in raw snapshots without being mislabeled as managed fallback. This case covers isolation between connections, not same-connection fairness or every cancellation/leadership/retransmission lifetime.

`TestAllocationPath` runs alone in fresh, separately preserved census test-binary processes after all ordinary gates, for pristine base and experiment base/ring/arena. Gate regex `Allocation(ValueLifetimes|Workspace.*|Shutdown.*)` excludes Path so its rate-1 profiling cannot perturb other tests. Logs/profiles use `tests/*-census`; gzip symbol binaries and hashes identify the actual executable. These in-process census counters include client plus all three replicas, unlike the subprocess leader-only measurements.
