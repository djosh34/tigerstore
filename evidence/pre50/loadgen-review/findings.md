# Load generator snapshot review

Reviewed the supplied `loadgen-snapshot`, all `cmd/loadgen` files, both `bench/*.sh` scripts and `cmd/benchreport/main.go`. Read #46 with all comments, #1, #50 and #54 through gh. References below are relative to that snapshot, not the original worker checkout. No worker changes, subagents, issue comments or pushes.

## Proven defects and measurement limitations

1. **Slow completions disappear from latency summaries.** `cmd/loadgen/workload.go:33-43,341-344` measures successful responses and watch events only when their completion falls inside the window. `cmd/loadgen/worker.go:59-63` counts only queued, unsent arrivals, not sent requests completing later. A 100 ms window with 200 ms responses yielded six successful drained requests, zero measured ops, zero latency samples, zero p99, zero unsent and no errors. Thus a small unsent count does not establish that the server kept up. Keep completion-window throughput, but collect arrival-cohort latency through drain, with explicit failed, timed-out and censored counts. Apply the same distinction to watch latency.

2. **Failed or CPU-invalid runs can become clean-looking report rows.** `cmd/loadgen/main.go:139-145,325-353` writes a result even when run-level errors occurred. Those errors are not included in the JSON request-error map. A missing server PID produced seven ops, `errors={}`, CPU/op zero and a returned CPU error. `main.go:564-571` also uses zero for unavailable CPU or a zero-op denominator. `cmd/benchreport/main.go:23-44,80-84` ignores request errors and does not validate CPU availability, latency counts, offered rates or complete repetition sets. A fixture with 100 request errors was reported without a warning. Add explicit run status and CPU validity, use null for unavailable metrics, and reject or visibly flag invalid runs. `bench/run.sh:79-93` does propagate loadgen's nonzero exit, but the failed JSON remains available to later reporting.

3. **Unary response cardinality is unchecked.** `cmd/loadgen/conn.go:387-406,434-445` permits zero or multiple response messages followed by successful trailers. Fake Put responses with no body or two bodies both produced seven successful ops and no errors. Missing CAS/Delete/Range responses also bypass their message validators. Require exactly one validated message for unary calls, while preserving multi-message watches.

4. **The claimed actual-send timestamp precedes the write.** `cmd/loadgen/worker.go:53,81,97-99` assigns every stream in a batch the same loop timestamp before key/value preparation and flush. The socket write happens at `cmd/loadgen/conn.go:249`. Service latency therefore includes generator preparation, lock wait and batching time, not just time after send. Stamp a documented write-start boundary or rename the metric. Also, `worker.go:77` checks stop but not start for closed-loop requests. A request completed about 200 ms before its scheduled phase start. Respect start in both modes, especially with zero configured warmup.

5. **Old files change the benchmark.** `bench/run.sh:95-107` overwrites current repetition filenames but retains older repetitions, then derives its rate from every matching max JSON. With a fresh repetition at 100 ops/s and a leftover repetition at 10,000, the exact expression selected 5,000 arrivals/s rather than 50. `cmd/benchreport/main.go:59,84` likewise merges every JSON under the directory without matching run configuration. Use a fresh run directory or an explicit manifest, and verify identical settings and repetition counts before aggregation.

6. **The 10 KiB values have substantial cross-request correlation.** `cmd/loadgen/keys.go:46-49,67-69` advances only 4,099 bytes through a shared random pool. Adjacent 10,240-byte values share 6,141 bytes. A 256-value gzip batch compressed to 42.25% of its original size; non-overlapping random data compressed to 100.01%. This is a proven input property, not a measured server speedup. If the intended workload is incompressible across a batch, generate non-overlapping or independent values. Otherwise document and vary the correlation.

7. **Failed startup leaves other nodes running.** `bench/cluster.sh:81-91` exits without stopping previously started nodes, and `bench/run.sh:76-77` has no failure cleanup trap. With one dummy node exiting, startup returned 1 while two sibling processes remained running. I killed those owned test processes. Install cleanup for failed start and interruption, and preserve failure logs. Leftover processes can consume CPU or occupy ports in later runs.

8. **Nonfinite rates pass validation.** `cmd/loadgen/main.go:81` accepts both NaN and positive infinity. NaN follows the closed-loop branch; infinity gives one-nanosecond gaps through `worker.go:130-131`. Reject nonfinite rates before dialing or allocating. Acceptance was tested; the infinity load was not run.

## Confirmed gaps in the snapshot

- `cmd/loadgen/conn.go:109` dials plain TCP and `wire.go:167` hardcodes HTTP. `bench/cluster.sh:44,50-64` uses plaintext client and peer URLs without certificates. Add client mTLS with ALPN h2 and HTTPS headers, peer encryption for both stores, and readiness checks using the same certificates. These scripts cannot currently measure encrypted operation.
- `bench/run.sh:30,77` and `bench/cluster.sh:54-65` neither configure nor verify filesystem write barriers. No delay or fault-proxy option exists in these scripts. These are missing controls, not proof that this host has barriers disabled. The later runner setup must verify the actual data mount and implement #50's 0/1/5/10 ms peer-only delay, with one-way versus RTT semantics stated.
- `bench/run.sh:28,77,79` applies configurable CPU lists equally to the two targets, which is useful. But `cmd/loadgen/main.go:88-120` and `cmd/benchreport/main.go:149-159` do not record those lists or distinguish host from runner results. `server_cores_by_node` is CPU utilization, not affinity. Record the selected layout, hardware, venue, actual leader and any proxy placement. Neither `bench/run.sh:61` nor cluster startup checks the etcd version or records binary identity. Require etcd 3.7.2 and identify both measured builds.

## Untested concerns to check before publishing numbers

- `cmd/loadgen/main.go:311-318,564-584` samples CPU on timer wakeups, but divides CPU by completions from fixed nominal boundaries. `cpu.go:61-70` timestamps before sequential process reads. Scheduling delays may change the numerator interval without changing the denominator interval. Export actual sample times and skew, and align or reject materially misaligned samples. The /proc user-plus-system summation itself appears appropriate for process CPU; its resolution is 10 ms.
- The all-streams-busy run is named max throughput, but there is no concurrency sweep or evidence that the pinned generator can supply the server's maximum. Check generator utilization and lateness, then sweep connections/streams or generator budget identically for both stores. Queued arrivals can reflect a client bottleneck as well as a server bottleneck.
- `bench/run.sh:96-113` always uses the same target order. Thermal or disk drift may bias paired results. Alternate order while keeping targets in the same job. If a fault proxy is added, report its CPU cost and placement rather than silently excluding it from the comparison.

## Evidence and limits

Copied source and all throwaway tests are under this review directory. `go test -short -v ./cmd/loadgen ./cmd/benchreport`, `go vet`, and `go test -race -short -v` passed. The final overlap and validation probes also passed under `go test -short -run TestReview -v`. Passing probes assert the defects above; they are not fixes. Bash syntax checks passed. See `test-results.txt`, `race-results.txt`, `review-results.txt`, `stale-results.txt` and `startup-results.txt`. `snapshot-sha256.txt` identifies the reviewed files.

The three etcd integration tests were skipped by `-short`. Installed etcd is 3.5.17, so I did not use it as evidence for the required 3.7.2 baseline. No full server benchmark, TLS run, barrier verification, proxy-delay run or end-to-end compression comparison was performed. Private build caches and temporary build output were removed after testing. The parent can post these findings in its consolidated #50 report.
