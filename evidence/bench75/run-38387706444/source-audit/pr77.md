Part of #50. Stacked on #76 (and #75); the base becomes `main` as those merge.

The second step of the whole-batch write path: values stored once in the log and referenced by the index, and the batch encoded once and applied in place, from the [design change on #50](https://github.com/djosh34/tigerstore/issues/50) as corrected. This PR does it for Put, the request every benchmark measures. Txn, DeleteRange and the lease writes still decode at apply.

Put path after this PR:

1. The reader copies the request message out of the Framer once, into a buffer of its own size (as in #75).
2. `core.ParsePut` reads key, value, lease and flags in place with protowire. It follows protobuf's rules (the last value wins; unknown and mistyped fields are skipped), and `TestParsePutMatchesProtobuf` compares it with `proto.Unmarshal` on every truncation of tricky encodings.
3. `Submit` validates with `mvcc.CheckPutOp` and limits the size of the put as protobuf marshals it after a decode: the fields it holds plus unknown fields, as etcd does. A value field that a later one replaces does not count. `TestRequestSizeLimitMatchesEtcd` checks the wire form at etcd's boundary and a non-canonical put. `TestParsePutMatchesProtobuf` compares the size with `proto.Size` on every truncation. The difftest passed locally.
4. `Process` copies the client's bytes into the Raft entry. That is the one encode, into a buffer sized for the whole batch, so `append` never regrows it.
5. Every replica applies puts by walking the entry in place (`walkBatch`). The index keeps the key and value as slices of the entry. Previously each replica decoded a new `PutRequest` with fresh copies of key and value.
6. The reply is the revision, term and previous key (`core.Reply.Rev/Term/PrevKv`). The connection writer encodes the PutResponse by hand (`appendPutResponse`, compared byte for byte with protobuf in `TestPutResponseEncoding`), without building a response message.

Copies of a put value per node, counted from the code. The leader before this PR made a reader copy, the decode, the entry marshal and the apply decode, plus WAL and peer copies. After it, the reader copy and the entry copy remain, plus WAL and peer copies. Followers lose the apply decode copy.

The simulator now submits its puts in wire form, so it runs `ParsePut`, `checkPut` and the in-place apply. Its checks turn the reply back into a message with `core.Node.PutResponse`. The server's own PutResponse encoding is covered only by `TestPutResponseEncoding` and the server tests. 64 seeds of `TestSeeds` passed locally; CI runs the full campaigns and the planted bugs.
