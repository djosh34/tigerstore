## Conclusions / limits for #484

- A sustained guest disk-byte ceiling near **343–345 MiB/s** is reproducible. diskbench maxima are 343.333 / 343.338 / 345.293 MiB/s (min/median/max, 0.57% range/median). Adding writers does not triple disk bandwidth: 3-writer fio prewritten O_DIRECT+fdatasync 1 MiB is 343.434 / 343.570 / 345.866 MiB/s total. No-sync qd4 gives the same write plateau. This is a guest-device limit, not a physical-media limit.
- Group size and allocation matter below that plateau. Buffered allocating fdatasync, one writer: 4 KiB cycle p50 214.643 / 362.578 / 389.810 us, versus prewritten 65.708 / 117.689 / 118.121 us. At 1 MiB, prewritten 3-writer per-writer p50 is about 9 ms and total remains ~343 MiB/s; 4 MiB ~35 ms per writer. The full tables show fsync as well as fdatasync, all writers and tails. Bulk group commit can reach the byte ceiling; single small durable writes cannot.
- **Conditional model, not a new workload measurement:** using the brief's old 3,520 disk bytes/put and this median diskbench gives 102,277 put/s. Old observed 91,698 put/s is 89.66% of that quotient. Assumes bytes/op and workload/disk/kernel comparability; do not present it as a universal ops ceiling or apply to txn/mixed without their bytes/op.
- Primitive AES128-GCM 1 KiB seal/open costs 294.5 / 303.7 ns median (0.288 / 0.297 ns/byte); 16 KiB ~0.240 ns/byte. This cipher is actually negotiated. ChaCha is much slower here. Whole TLS/TCP sender on a saturated 0-ms stream is ~0.660 ns/plaintext byte on CPU0, including syscalls/protocol/handshake. Neither should be confused with full server CPU per request.
- Memory copy useful bandwidth is 15,655–20,847 MiB/s single core and 55,426–63,913 MiB/s all four. Write-all-core varies much more: 152,570–231,133 MiB/s, 40.4% range/median. These are libc stream/copy limits, not measured DRAM bus counters. 1 KiB hot memcpy is ~22 ns; cache residency is critical.
- Peer ping at configured 0/2/10 ms has measured plain CPU0->1 median p50 31.406 / 2051.441 / 10066.510 us; TLS 35.614 / 2060.081 / 10078.142 us. Client port stays ~30–39 us even at peer RTT10. No physical NIC involved.
- TCP default-buffer plain throughput CPU0->1 (1 stream) drops from 5,972 MiB/s at RTT0 to 1,757 at RTT2 and 379.6 at RTT10; two streams approximately double at RTT2/10. TLS 1 stream: 1,441 / 1,016 / 310 MiB/s; 2 streams at RTT10 ~657 MiB/s. **Inference/guess:** much of the long-RTT per-stream limit is a TCP window/send-buffer limit, not netem's fixed byte-rate ceiling. Reason: actual BDP is 3.51 MiB at RTT2 and 3.80 MiB at RTT10, close to 4 MiB tcp_wmem maximum; preserving 0-ms 5,972 MiB/s would need 11.94 / 59.72 MiB windows. Not conclusively isolated because no tuned-socket experiment was run. netem code configures delay, not a rate limiter.
- UDP64 delivered ~362,746 pps without qdisc, ~366,111 with zero-delay qdisc, ~296,416 at2 ms and ~287,061 at10 ms (runner medians). Full raw sender/receiver CPU and loss are tabulated. Every recorded qdisc has **zero drops**; packet losses therefore are not the configured qdisc limit. **Not measured:** a qdisc-only ns/packet cost or loss-free maximum pps. The unlimited UDP test saturates sender/receiver/kernel work, not a standalone netem microbenchmark. No hard pps ceiling for batched TCP can be inferred from UDP results.
- **Not measured / guesses:** physical flush honesty/power-loss persistence, disk controller backing media, CPU frequency, exact DRAM-controller bandwidth, production-NIC throughput, precise p99.9 of multi-MiB syncs. Guest reports write-through, so Linux considers completed writes persistent and may elide redundant flushes; no destructive test verifies the hypervisor contract.
- Large-write p99.9 is under-sampled in 2-second tests; samples column exposes it. Do not sum fio write and sync phase percentiles; use the separately measured whole-cycle values. TLS stream measures sender-accepted plaintext, not receiver-confirmed application bytes; a final bounded socket backlog can remain.
